# 消息来源差异化处理方案

## 一、问题背景

### 1.1 问题描述

当前 IFlowModule 完整记录 iflow 返回的所有消息（✦ 和 ✻），无论请求消息来自哪里。但是，对于不同来源的请求消息，回复消息的发送方式应该有所区别：

1. **企业微信/飞书/模拟器等渠道发送的消息**：
   - 有明确来源（MessageStore 中有记录且 source 字段不为空）
   - 期望：实时响应，逐条发送回复消息

2. **用户在 tmux 中手动输入的消息**：
   - 无明确来源（MessageStore 中无记录或 source 字段为空）
   - 期望：完整回复，避免碎片化信息

### 1.2 当前问题

**问题1：所有回复消息都逐条发送**
- 用户手动输入时，也会收到多条碎片化消息
- 缺乏完整的上下文体验

**问题2：无法区分请求来源**
- IFlowMonitor 提取回复消息时，不知道请求消息的来源
- 无法智能选择发送方式

## 二、核心思想

**根据请求消息的来源状态，决定回复消息的发送方式：**

- **有明确来源** → 逐条实时发送（流式模式）
- **无明确来源** → 等待完整后整合发送（缓冲模式）

## 三、判断依据

### 3.1 消息来源判断

**判断标准**：请求消息的 source 字段（来自 MessageStore）

**判断时机**：每次扫描 tmux 输出，提取到请求消息时

**判断方法**：
1. IFlowMonitor 扫描 tmux 输出，提取请求消息（以 > 开头的内容）
2. 在 MessageStore 中查找匹配的记录（根据消息内容精确匹配）
3. 检查匹配记录的 source 字段：
   - source 不为空 → 有明确来源
   - source 为空或未找到 → 无明确来源

### 3.2 匹配规则

**精确匹配**：
- 消息内容完全相同
- 状态为 PROCESSING（处理中）
- 时间窗口：5分钟内（避免误匹配）

### 3.3 接收目标

使用消息的 chat_id（实际对话ID）作为接收目标，而非 source 字段的模块ID。这是因为：
- chat_id 确保消息发送到正确的对话
- 模块ID只是标识来源，不一定是接收目标

## 四、两种模式

### 4.1 流式模式（Stream Mode）

**触发条件**：
- 请求消息匹配到 MessageStore 中的记录
- 该记录的 source 字段不为空

**发送行为**：
- 每提取到一条 ✦ 消息 → 立即发送到目标对话
- ✻ 消息不发送（被过滤）
- 每条消息独立发送，不等待其他消息

**适用场景**：
- 企业微信发送的消息
- 飞书发送的消息
- 模拟器发送的消息
- 任何通过接口进入的消息

**用户体验**：
- 实时看到回复
- 逐条到达
- 感觉流畅

### 4.2 缓冲模式（Buffer Mode）

**触发条件**：
- 请求消息未匹配到 MessageStore 中的记录
- 或者匹配记录的 source 字段为空

**发送行为**：
- 每提取到一条 ✦ 消息 → 暂存到缓冲区
- ✻ 消息不处理
- 生成结束时（GENERATING → IDLE）→ 整合缓冲区的所有 ✦ 消息为一条
- 发送整合后的消息到消息总线（receiver 为空，广播模式）

**无来源消息格式增强**：
为帮助用户理解消息来源，整合消息会添加说明前缀：
```
未知来源消息回复结束！
原请求消息内容是：{原始请求}
回复内容如下：
{整合后的回复内容}
```

**适用场景**：
- 用户在 tmux 中手动输入的消息
- 任何不经过接口直接进入 iflow 的消息

**用户体验**：
- 等待完整回复
- 一次性收到
- 内容完整

## 五、完整流程

### 5.1 场景A：渠道发送消息（流式模式）

```
步骤1：消息接收
  用户 → 渠道（企微/飞书/模拟器）→ 消息总线 → IFlowModule
  → IFlowModule.send()
  → MessageStore.add(source="渠道模块ID", content="1+1=?", chat_id="实际对话ID")
  → 注入到 iflow

步骤2：请求消息扫描
  IFlowMonitor 扫描 tmux 输出
  → 提取请求消息："> 1+1=?"
  → MessageStore.find_by_content("1+1=?")
  → 找到匹配记录（source="渠道模块ID"）
  → 判断：有明确来源
  → 设置模式：流式模式（STREAM_MODE）

步骤3：回复消息处理
  iflow 回复：
  ✦ 1+1=2 → IFlowMonitor 提取 → 立即发送到 chat_id
  ✻ 思考中... → IFlowMonitor 提取 → 不发送（过滤）
  ✦ 详细解释... → IFlowMonitor 提取 → 立即发送到 chat_id

步骤4：用户收到
  渠道用户收到 2 条消息，实时到达
```

### 5.2 场景B：tmux 手动输入（缓冲模式）

```
步骤1：消息发送
  用户在 tmux 中输入："1+1=?"
  → 消息直接进入 iflow
  → MessageStore 中无记录（未经过接口）

步骤2：请求消息扫描
  IFlowMonitor 扫描 tmux 输出
  → 提取请求消息："> 1+1=?"
  → MessageStore.find_by_content("1+1=?")
  → 未找到匹配记录
  → 判断：无明确来源
  → 设置模式：缓冲模式（BUFFER_MODE）

步骤3：回复消息处理
  iflow 回复：
  ✦ 1+1=2 → IFlowMonitor 提取 → 暂存到缓冲区
  ✻ 思考中... → IFlowMonitor 提取 → 不处理
  ✦ 详细解释... → IFlowMonitor 提取 → 暂存到缓冲区

步骤4：生成结束
  状态变化：GENERATING → IDLE
  → IFlowMonitor._flush_buffered_messages()
  → 整合缓冲区："1+1=2\n详细解释..."
  → 添加说明前缀："未知来源消息回复结束！..."
  → 发送到消息总线（receiver=""，广播模式）

步骤5：订阅者收到
  订阅者收到 1 条整合后的消息
```

## 六、消息路由机制

### 6.1 有来源消息的路由

当 receiver 不为空时：
- 消息通过消息总线的绑定关系进行路由
- 消息发送到 IFlowModule，IFlowModule 再发送到消息总线
- 消息总线根据绑定关系将消息发送到对应的渠道模块

### 6.2 无来源消息的路由

当 receiver 为空时：
- 消息通过广播机制发送到所有绑定者
- 消息总线遍历所有绑定关系，找出绑定了发送者的模块
- 向这些模块广播消息

### 6.3 渠道模块的消息处理

渠道模块（如 FeishuChannel）在接收消息时：
- 优先从消息的 metadata.receiver 获取接收者ID
- 其次从 metadata.chat_id 获取
- 最后使用消息的 chat_id
- 根据接收者ID类型（open_id 或 chat_id）发送消息到对应平台

## 七、实现要点

### 7.1 MessageStore 扩展

**新增字段**：
- requires_buffering：是否需要缓冲回复（无来源时为 True）
- buffered_replies：缓冲的回复内容列表

**新增方法**：
- find_by_content()：根据内容查找消息记录
- add_buffered_reply()：添加缓冲的回复
- get_buffered_replies()：获取缓冲的回复
- get_recent_processing()：获取最近的处理中消息（用于恢复消息归属）

### 7.2 IFlowMonitor 扩展

**新增字段**：
- _send_mode：发送模式（STREAM_MODE 或 BUFFER_MODE）
- _current_request_record：当前请求的记录
- _no_source_buffer：无来源消息的独立缓冲区
- _no_source_request_content：原始请求消息内容

**核心逻辑**：
- _extract_messages()：提取请求消息时，匹配 MessageStore，判断发送模式
- _send_message()：根据 send_mode 决定立即发送或缓冲
- _send_immediately()：立即发送消息（流式模式）
- _buffer_message()：缓冲消息（缓冲模式）
- _flush_buffered_messages()：发送缓冲的消息（生成结束时调用）

### 7.3 IFlowModule 扩展

**消息处理**：
- _on_monitor_message()：处理监控器输出的消息
- should_send_message()：根据 reply_mode 过滤消息
- 根据 message.receiver 是否为空决定路由方式

**状态变化处理**：
- _on_state_change()：处理状态变更
- 生成结束时调用刷新缓冲区的逻辑
- 发送完成通知

## 八、关键差异

| 项目 | 流式模式 | 缓冲模式 |
|------|---------|---------|
| 触发条件 | 请求有明确来源 | 请求无明确来源 |
| 发送时机 | 每条立即发送 | 生成结束后整合发送 |
| 发送目标 | 特定对话（chat_id） | 消息总线（广播） |
| 消息数量 | 多条（逐条） | 1条（整合） |
| 用户体验 | 实时响应 | 完整交付 |
| 消息格式 | 直接发送 | 添加说明前缀 |

## 九、优势

### 9.1 用户体验优化
- **渠道消息**：实时看到回复，感觉流畅
- **手动输入**：获得完整回复，避免碎片信息

### 9.2 逻辑清晰
- 有来源 = 实时响应
- 无来源 = 完整交付

### 9.3 自动判断
- 系统自动检测消息来源
- 无需人工配置
- 智能切换发送模式

### 9.4 向后兼容
- 有来源的消息保持原有逻辑（流式发送）
- 无来源的消息使用新逻辑（缓冲发送）

### 9.5 消息可追溯
- 即使状态变化太快导致当前消息ID被清空，也能通过 get_recent_processing() 恢复消息归属

## 十、风险评估

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|----------|
| 消息匹配失败 | 中 | 中 | 使用精确匹配 + 时间窗口 + 状态过滤 |
| 缓冲区泄漏 | 低 | 高 | 生成结束时自动清空 |
| 状态同步问题 | 低 | 中 | 使用状态机确保一致性 |
| 性能影响 | 低 | 低 | 缓冲区大小可控，发送模式切换开销小 |

### 补充风险

**消息格式差异导致匹配失败**：
- 如果 tmux 输出的请求消息与原始消息有微小差异（如多了一个空格），匹配可能失败
- 解决：确保消息内容完全一致后再注入到 iflow
