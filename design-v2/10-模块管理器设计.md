# 模块管理器设计

## 一、核心设计

### 1.1 概述

ModuleManager（模块管理器）是 Ling-iflow 项目的控制层组件，负责模块生命周期管理、状态监控、健康检查和消息应答检查。与 MessageBus 配合，实现控制逻辑和业务逻辑的分离。

### 1.2 核心理念

- **职责分离**：控制逻辑（ModuleManager）与业务逻辑（MessageBus）分离
- **集中管理**：统一管理所有模块的生命周期和状态
- **状态感知**：实时监控模块健康状态和运行状态
- **错误处理**：在发送前检查接收方状态，提供友好的错误响应

### 1.3 设计背景

**当前问题**：
1. **启动逻辑分散**：模块创建、注册、启动逻辑分散在多个地方
2. **状态管理缺失**：没有统一的模块状态管理
3. **错误处理不足**：消息发送前不检查接收方状态
4. **健康监控缺失**：没有自动化的健康检查机制
5. **启动顺序固定**：无法灵活控制模块启动顺序

**解决方案**：
创建独立的 ModuleManager 组件，负责：
- 模块生命周期管理
- 模块状态管理
- 健康监控
- 消息应答检查
- 启动顺序控制

## 三、功能划分

### 3.1 ModuleManager 职责

**核心职责**：

1. **模块生命周期管理**
   - 创建模块实例
   - 销毁模块实例
   - 启动模块
   - 停止模块
   - 重启模块

2. **模块注册协调**
   - 创建模块后注册到消息总线
   - 销毁模块前从消息总线注销
   - 设置模块的消息总线引用

3. **模块状态管理**
   - 记录模块运行状态
   - 记录模块健康状态
   - 记录模块启动时间
   - 记录模块停止时间

4. **健康监控**
   - 定期检查模块健康状态
   - 检测模块异常
   - 触发状态变更通知

5. **启动顺序控制**
   - 定义模块启动顺序
   - 按顺序启动模块
   - 按顺序停止模块

6. **依赖管理**
   - 定义模块依赖关系
   - 启动前检查依赖
   - 确保依赖满足

7. **消息应答检查**
   - 路由前检查接收方状态
   - 检查模块是否可用
   - 生成错误响应

9. **IFlow 状态管理**
   - 记录 iflow 生成状态
   - 记录生成持续时间
   - 检查 iflow 可用性

10. **故障恢复**
    - 自动重启故障模块
    - 尝试恢复异常模块
    - 记录恢复日志

### 3.2 MessageBus 职责

**核心职责**（保持简单）：

1. **模块注册**
   - 注册模块实例
   - 注销模块实例
   - 查询模块列表

2. **绑定管理**
   - 建立模块间绑定关系
   - 解除绑定关系
   - 查询绑定关系

3. **消息路由**
   - 根据绑定关系路由消息
   - 直接发送到指定模块
   - 发布消息到主题

4. **发布订阅**
   - 订阅主题
   - 取消订阅
   - 发布消息

## 四、职责边界

### 4.1 MessageBus 负责

| 功能 | 说明 | 边界 |
|------|------|------|
| 模块注册 | 维护模块注册表 | 只管理注册表，不负责创建 |
| 消息路由 | 根据绑定关系路由 | 不检查模块状态 |
| 绑定管理 | 管理模块绑定关系 | 只管理关系，不管理依赖 |
| 发布订阅 | 实现发布订阅机制 | 不关心订阅者的状态 |

### 4.2 ModuleManager 负责

| 功能 | 说明 | 边界 |
|------|------|------|
| 模块创建 | 创建模块实例 | 创建后注册到消息总线 |
| 模块启动 | 启动模块 | 启动前检查依赖 |
| 状态管理 | 管理模块状态 | 独立的状态存储 |
| 健康监控 | 监控模块健康 | 不修改消息总线 |
| 依赖管理 | 管理模块依赖 | 独立的依赖配置 |
| 消息应答 | 检查接收方状态 | 检查后再路由 |

## 五、交互流程

### 5.1 模块创建和注册流程

```
外部管理工具
    ↓
模块管理器创建模块
    ↓
模块管理器初始化模块
    ↓
模块管理器注册模块到消息总线
    ↓
模块管理器设置模块的消息总线引用
    ↓
模块管理器启动模块
    ↓
模块开始运行
```

### 5.2 消息发送流程（带应答检查）

```
WeChatModule 发送消息
    │
    ▼
调用模块管理器的发送方法
    │
    ▼
模块管理器检查接收方状态
    │
    ├─ 接收方不存在 → 返回错误响应
    │
    ├─ 接收方存在但状态异常 → 返回错误响应
    │
    └─ 接收方存在且状态正常 → 调用消息总线路由
    │
    ▼
消息总线路由到目标模块
    │
    ▼
目标模块接收并处理消息
```

### 5.3 模块启动流程

```
外部管理工具启动模块
    │
    ▼
模块管理器检查依赖关系
    │
    ▼
模块管理器按拓扑排序顺序启动模块
    │
    ▼
每个模块启动前检查依赖
    │
    ▼
依赖满足则启动，否则等待
    │
    ▼
所有模块启动完成
```

### 5.4 健康监控流程

```
模块管理器启动健康监控
    │
    ▼
定期检查每个模块的健康状态
    │
    ├─ 模块状态正常 → 继续监控
    │
    └─ 模块状态异常
       │
       ├─ 记录异常状态
       ├─ 触发状态变更通知
       └─ 尝试自动恢复
```

## 状态管理与健康监控

### 一、状态管理优化

#### 1.1 背景问题

当前状态管理存在以下问题：

1. **双重监控，不协调**
   - IFlowModule 有自己的监控任务，每 60 秒检查一次
   - ModuleManager 也有健康监控，每 30 秒检查一次
   - 两者独立运行，没有信息共享，可能导致冲突

2. **健康检查不准确**
   - ModuleManager 的健康检查依赖模块的 `health_check()` 方法
   - 但 IFlowModule 没有实现这个方法
   - 默认返回"健康"，实际可能 tmux/iflow 已崩溃

3. **状态上报不完整**
   - IFlowModule 只在状态变化时（idle/generating）通知 ModuleManager
   - 崩溃、未运行等异常状态没有上报机制
   - ModuleManager 无法感知真实状态

4. **恢复机制混乱**
   - IFlowModule 内部有自动重启逻辑
   - ModuleManager 也有自动恢复机制
   - 可能同时尝试恢复，产生冲突

5. **其他模块缺失监控**
   - WeChatChannel、SimulatorChannel 等没有健康检查
   - 这些模块异常时无法被检测和恢复

#### 1.2 关键问题场景

**场景 1：tmux/iflow 崩溃**
- IFlowModule 的监控任务会检测到并尝试重启
- ModuleManager 的健康检查认为模块健康（因为默认返回 true）
- 用户发送消息时，ModuleManager 认为接收方可用，实际 iflow 未运行
- 用户只收到"正在处理中..."，没有后续回复

**场景 2：WeChatChannel 崩溃**
- 完全没有健康检查机制
- ModuleManager 认为模块健康
- 无法自动恢复，需要手动重启

### 二、优化方案

#### 2.1 核心原则

1. **统一健康检查接口**
   - 所有模块必须实现健康检查方法
   - 返回真实的健康状态和详细信息

2. **集中式监控管理**
   - 移除模块内部监控任务
   - ModuleManager 统一负责健康监控和恢复
   - 避免双重监控和冲突

3. **状态实时上报**
   - 模块检测到异常时主动通知 ModuleManager
   - ModuleManager 健康检查作为后备机制
   - 确保状态准确性

4. **分级恢复策略**
   - 轻度异常：模块自行处理（如 token 刷新）
   - 严重异常：ModuleManager 强制重启
   - 多次失败：标记为不可用，停止自动恢复

#### 2.2 IFlowModule 实现真实健康检查

**检查项**：
- 模块是否运行
- tmux 会话是否存在
- iflow 进程是否运行
- iflow 是否就绪（可选，更严格）

**返回信息**：
- 健康状态（true/false）
- 不健康原因（tmux_session_not_found、iflow_not_running 等）
- 详细信息（tmux 会话名、当前状态等）

#### 2.3 移除 IFlowModule 内部监控任务

**改动**：
- 删除 `_monitor_task()` 方法
- 停止创建内部监控任务
- 依赖 ModuleManager 统一监控

**优势**：
- 避免双重监控
- 状态统一管理
- 减少代码复杂度

#### 2.4 修改 ModuleManager 健康检查

**改进点**：
- 对于没有实现健康检查的模块，检查运行状态作为后备
- 默认不再假设模块健康，而是基于实际状态
- 增强日志，记录健康检查详情

**处理逻辑**：
- 优先调用模块的 `health_check()` 方法
- 如果模块未实现，检查 `running` 属性
- 如果都没有，返回不健康（保守策略）

#### 2.5 WeChatChannel 实现健康检查

**检查项**：
- 模块是否运行
- HTTP 客户端是否初始化
- access_token 是否过期（自动刷新）
- 回调服务是否运行（可选）

**自动恢复**：
- token 过期时自动刷新
- HTTP 客户端异常时尝试重新初始化

#### 2.6 增强自动恢复策略

**恢复流程**：
1. 停止模块
2. 等待配置的延迟时间
3. 重启模块
4. 检查恢复结果

**失败处理**：
- 记录失败次数
- 达到最大失败次数时停止自动恢复
- 标记模块为不可用状态
- 记录错误信息

**恢复成功**：
- 重置失败计数
- 更新模块状态为健康
- 记录恢复日志

#### 2.7 优化状态变更通知

**通知内容**：
- 模块 ID
- 新状态（healthy/unhealthy）
- 详细信息（原因、错误详情等）

**调用时机**：
- 健康检查发现状态变化时
- 自动恢复成功/失败时
- 模块主动上报异常时

**回调机制**：
- 支持多个状态回调函数
- 同时调用所有回调
- 捕获回调异常，不影响主流程

### 六、优化后的优势

#### 6.1 状态准确
- 基于真实的健康检查结果
- 不再依赖假设或默认值
- 用户发送消息时能准确判断接收方状态

#### 6.2 及时恢复
- 检测到异常立即尝试恢复
- 减少服务中断时间
- 提高系统可用性

#### 6.3 避免冲突
- 移除模块内部监控
- ModuleManager 统一管理
- 恢复过程可控

#### 6.4 易于扩展
- 其他模块可以轻松实现健康检查
- 统一的接口和流程
- 便于维护和调试

#### 6.5 用户体验
- 用户能立即收到明确的错误通知
- 不再出现"正在处理中..."后没有回复的情况
- 异常自动恢复，减少人工干预

## 总结

### 核心特点

1. **消息总线（MessageBus）**
   - 职责单一：专注于消息路由
   - 解耦清晰：模块间通过消息通信
   - 扩展灵活：支持点对点路由和广播发布

2. **模块管理器（ModuleManager）**
   - 集中管理：统一管理模块生命周期
   - 状态感知：实时监控模块健康状态
   - 自动恢复：检测异常并自动恢复

3. **状态管理优化**
   - 统一接口：所有模块实现健康检查
   - 集中监控：ModuleManager 统一监控
   - 分级恢复：不同级别的异常采用不同策略

### 设计原则

- **单一职责**：每个组件职责明确
- **职责分离**：控制逻辑与业务逻辑分离
- **依赖倒置**：模块不直接依赖，通过消息总线通信
- **开闭原则**：添加新功能无需修改核心代码
- **异步优先**：所有操作使用 async/await

### 关键优势

1. **架构清晰**：分层设计，职责明确
2. **易于维护**：组件独立，降低耦合
3. **灵活扩展**：支持新模块和新功能
4. **稳定可靠**：健康监控和自动恢复
5. **开发友好**：支持快速测试和迭代

这个架构设计满足了当前项目需求，并为未来扩展预留了充分的空间。
