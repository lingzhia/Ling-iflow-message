# 消息总线与模块管理

## 概述

本文档整合了 MessageBus 消息总线、ModuleManager 模块管理器、状态管理优化和单进程多组管理的核心设计，是 Ling-iflow 项目的核心架构文档。

---

## 第一部分：MessageBus 消息总线

### 一、核心设计

#### 1.1 概述

MessageBus（消息总线）是 Ling-iflow 项目的核心组件，负责模块间消息路由和分发。采用**发布-订阅模式**实现模块解耦。

#### 1.2 核心理念

- **解耦**：模块间不直接依赖，通过消息总线通信
- **路由**：根据绑定关系自动路由消息
- **广播**：支持发布-订阅模式广播消息

#### 1.3 架构设计

```
┌─────────────────────────────────────────────────────────────┐
│                       MessageBus                            │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐         │
│  │   modules   │  │  bindings   │  │ subscribers │         │
│  │  模块注册表  │  │  绑定关系   │  │  订阅者列表  │         │
│  └─────────────┘  └─────────────┘  └─────────────┘         │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │                   核心方法                           │   │
│  │  register / bind / route / publish / subscribe      │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
        ↑                    ↑                    ↑
        │                    │                    │
   ┌────┴────┐         ┌────┴────┐         ┌────┴────┐
   │ WeChat  │         │ IFlow   │         │ Command │
   │ Module  │         │ Module  │         │ Handler │
   └─────────┘         └─────────┘         └─────────┘
```

### 四、消息路由流程

#### 4.1 点对点路由

```
消息到达 MessageBus.route()
        │
        ▼
检查 source_module 的绑定关系
        │
        ▼
bindings[source_module] → target_module_id
        │
        ▼
modules[target_module_id].receive(message)
```

**示例**：

```python
# 配置绑定
bus.bind("wechat_bot1", "iflow_bot1")

# 微信消息自动路由到 iflow
message = Message(
    from_module="wechat_bot1",
    content="你好"
)
await bus.route(message)  # 自动发送到 iflow_bot1
```

#### 4.2 广播发布

```
消息到达 MessageBus.publish(topic)
        │
        ▼
获取主题的所有订阅者
        │
        ▼
并发调用所有订阅者回调
        │
        ▼
返回成功/失败统计
```

**示例**：

```python
# 订阅主题
async def on_reply(message):
    print(f"收到回复: {message.content}")

bus.subscribe("iflow_reply", on_reply)

# 发布消息
await bus.publish("iflow_reply", message)
```

### 五、典型使用场景

#### 5.1 场景1：微信 ↔ iflow 双向绑定

```python
# 创建消息总线
bus = MessageBus()

# 创建模块
wechat = WeChatModule(module_id="wechat_bot1", ...)
iflow = IFlowModule(module_id="iflow_bot1", ...)

# 注册模块
bus.register_module(wechat)
bus.register_module(iflow)

# 设置双向绑定
bus.bind("wechat_bot1", "iflow_bot1")  # 微信 → iflow
bus.bind("iflow_bot1", "wechat_bot1")  # iflow → 微信

# 启动模块（由控制层管理）
await wechat.start()
await iflow.start()
```

#### 5.2 场景2：多机器人配置

```python
# 机器人1：企业A
wechat1 = WeChatModule(module_id="wechat_bot1", corp_id="corp_a", ...)
iflow1 = IFlowModule(module_id="iflow_bot1", tmux_session="iflow1")

# 机器人2：企业B
wechat2 = WeChatModule(module_id="wechat_bot2", corp_id="corp_b", ...)
iflow2 = IFlowModule(module_id="iflow_bot2", tmux_session="iflow2")

# 注册
bus.register_module(wechat1)
bus.register_module(iflow1)
bus.register_module(wechat2)
bus.register_module(iflow2)

# 绑定（各自独立）
bus.bind("wechat_bot1", "iflow_bot1")
bus.bind("iflow_bot1", "wechat_bot1")
bus.bind("wechat_bot2", "iflow_bot2")
bus.bind("iflow_bot2", "wechat_bot2")
```

#### 5.3 场景3：命令处理器集成

```python
# 创建命令处理器
command = CommandHandler(module_id="command_handler")

# 注册
bus.register_module(command)

# 绑定命令处理器
bus.bind("wechat_bot1", "command_handler")  # 先路由到命令处理器
bus.bind("command_handler", "iflow_bot1")   # 非命令消息转发到 iflow
```

```
         │   route()       │
         └────────┬────────┘

                  ▼
         ┌─────────────────┐
         │  WeChatModule   │
         │  send_message() │
         └─────────────────┘
```

**命令路由优化：**
```python
# 在 WeChatModule 中处理命令
if parsed.get("is_command"):
    result = await self.command_handler.execute(parsed, chat_id)
    if result:
        # 已知命令，发送回复
        await self.send_message(result, chat_id, is_group)
        # 已知命令不继续发送到消息总线
        return
    else:
        # 未知命令，透传给 iflow 处理
        logger.info(f"未知命令，透传给 iflow: {parsed.get('cmd_name')} {parsed.get('cmd_args')}")

# 创建消息对象并发送到消息总线
message = self.converter.create_wechat_inbound_message({...})
await self.send_to_bus(message)
```

**优化效果：**
- 已知命令执行后直接返回，不发送到消息总线
- 避免已知命令被重复发送到 iflow
- 提高系统效率和响应速度

### 七、设计原则

#### 7.1 单一职责

- MessageBus 只负责消息路由和分发
- 不处理消息内容，不关心业务逻辑
- 模块职责独立，通过消息通信

#### 7.2 依赖倒置

- 模块不直接依赖其他模块
- 模块通过 MessageBus 通信
- 绑定关系运行时配置

#### 7.3 开闭原则

- 添加新模块无需修改 MessageBus
- 添加新绑定无需修改代码
- 扩展功能通过订阅机制

#### 7.4 异步优先

- 所有消息处理使用 async/await
- 并发处理提高性能
- 非阻塞操作

### 八、错误处理

#### 8.1 错误类型

| 错误 | 处理方式 |
|------|---------|
| 模块不存在 | 记录日志，返回 False |
| 绑定不存在 | 记录日志，返回 False |
| 消息发送失败 | 记录异常，更新错误计数 |
| 订阅者处理失败 | 记录异常，继续处理其他订阅者 |

#### 8.2 容错机制

```python
async def publish(self, topic: str, message: Message) -> bool:
    # 使用 return_exceptions 捕获所有异常
    results = await asyncio.gather(*tasks, return_exceptions=True)

    # 统计成功/失败
    success_count = sum(1 for r in results if not isinstance(r, Exception))

    # 记录错误但不影响其他订阅者
    if success_count < len(results):
        errors = [r for r in results if isinstance(r, Exception)]
        logger.error(f"{len(errors)} 个订阅者处理失败")
```

## 第二部分：ModuleManager 模块管理器

### 一、核心设计

#### 1.1 概述

ModuleManager（模块管理器）是 Ling-iflow 项目的控制层组件，负责模块生命周期管理、状态监控、健康检查和消息应答检查。与 MessageBus 配合，实现控制逻辑和业务逻辑的分离。

#### 1.2 核心理念

- **职责分离**：控制逻辑（ModuleManager）与业务逻辑（MessageBus）分离
- **集中管理**：统一管理所有模块的生命周期和状态
- **状态感知**：实时监控模块健康状态和运行状态
- **错误处理**：在发送前检查接收方状态，提供友好的错误响应

#### 1.3 设计背景

**当前问题**：
1. **启动逻辑分散**：模块创建、注册、启动逻辑分散在多个地方
2. **状态管理缺失**：没有统一的模块状态管理
3. **错误处理不足**：消息发送前不检查接收方状态
4. **健康监控缺失**：没有自动化的健康检查机制
5. **启动顺序固定**：无法灵活控制模块启动顺序

**解决方案**：
创建独立的 ModuleManager 组件，负责：
- 模块生命周期管理
- 模块状态管理
- 健康监控
- 消息应答检查
- 启动顺序控制

### 三、功能划分

#### 3.1 ModuleManager 职责

**核心职责**：

1. **模块生命周期管理**
   - 创建模块实例
   - 销毁模块实例
   - 启动模块
   - 停止模块
   - 重启模块

2. **模块注册协调**
   - 创建模块后注册到消息总线
   - 销毁模块前从消息总线注销
   - 设置模块的消息总线引用

3. **模块状态管理**
   - 记录模块运行状态
   - 记录模块健康状态
   - 记录模块启动时间
   - 记录模块停止时间

4. **健康监控**
   - 定期检查模块健康状态
   - 检测模块异常
   - 触发状态变更通知

5. **启动顺序控制**
   - 定义模块启动顺序
   - 按顺序启动模块
   - 按顺序停止模块

6. **依赖管理**
   - 定义模块依赖关系
   - 启动前检查依赖
   - 确保依赖满足

7. **组管理**
   - 定义模块组
   - 按组启动模块
   - 按组停止模块

8. **消息应答检查**
   - 路由前检查接收方状态
   - 检查模块是否可用
   - 生成错误响应

9. **IFlow 状态管理**
   - 记录 iflow 生成状态
   - 记录生成持续时间
   - 检查 iflow 可用性

10. **故障恢复**
    - 自动重启故障模块
    - 尝试恢复异常模块
    - 记录恢复日志

#### 3.2 MessageBus 职责

**核心职责**（保持简单）：

1. **模块注册**
   - 注册模块实例
   - 注销模块实例
   - 查询模块列表

2. **绑定管理**
   - 建立模块间绑定关系
   - 解除绑定关系
   - 查询绑定关系

3. **消息路由**
   - 根据绑定关系路由消息
   - 直接发送到指定模块
   - 发布消息到主题

4. **发布订阅**
   - 订阅主题
   - 取消订阅
   - 发布消息

### 四、职责边界

#### 4.1 MessageBus 负责

| 功能 | 说明 | 边界 |
|------|------|------|
| 模块注册 | 维护模块注册表 | 只管理注册表，不负责创建 |
| 消息路由 | 根据绑定关系路由 | 不检查模块状态 |
| 绑定管理 | 管理模块绑定关系 | 只管理关系，不管理依赖 |
| 发布订阅 | 实现发布订阅机制 | 不关心订阅者的状态 |

#### 4.2 ModuleManager 负责

| 功能 | 说明 | 边界 |
|------|------|------|
| 模块创建 | 创建模块实例 | 创建后注册到消息总线 |
| 模块启动 | 启动模块 | 启动前检查依赖 |
| 状态管理 | 管理模块状态 | 独立的状态存储 |
| 健康监控 | 监控模块健康 | 不修改消息总线 |
| 依赖管理 | 管理模块依赖 | 独立的依赖配置 |

## 第三部分：状态管理与健康监控

### 一、状态管理优化

#### 1.1 背景问题

当前状态管理存在以下问题：

1. **双重监控，不协调**
   - IFlowModule 有自己的监控任务，每 60 秒检查一次
   - ModuleManager 也有健康监控，每 30 秒检查一次
   - 两者独立运行，没有信息共享，可能导致冲突

2. **健康检查不准确**
   - ModuleManager 的健康检查依赖模块的 `health_check()` 方法
   - 但 IFlowModule 没有实现这个方法
   - 默认返回"健康"，实际可能 tmux/iflow 已崩溃

3. **状态上报不完整**
   - IFlowModule 只在状态变化时（idle/generating）通知 ModuleManager
   - 崩溃、未运行等异常状态没有上报机制
   - ModuleManager 无法感知真实状态

4. **恢复机制混乱**
   - IFlowModule 内部有自动重启逻辑
   - ModuleManager 也有自动恢复机制
   - 可能同时尝试恢复，产生冲突

5. **其他模块缺失监控**
   - WeChatChannel、SimulatorChannel 等没有健康检查
   - 这些模块异常时无法被检测和恢复

#### 1.2 关键问题场景

**场景 1：tmux/iflow 崩溃**
- IFlowModule 的监控任务会检测到并尝试重启
- ModuleManager 的健康检查认为模块健康（因为默认返回 true）
- 用户发送消息时，ModuleManager 认为接收方可用，实际 iflow 未运行
- 用户只收到"正在处理中..."，没有后续回复

**场景 2：WeChatChannel 崩溃**
- 完全没有健康检查机制
- ModuleManager 认为模块健康
- 无法自动恢复，需要手动重启

### 二、优化方案

#### 2.1 核心原则

1. **统一健康检查接口**
   - 所有模块必须实现健康检查方法
   - 返回真实的健康状态和详细信息

2. **集中式监控管理**
   - 移除模块内部监控任务
   - ModuleManager 统一负责健康监控和恢复
   - 避免双重监控和冲突

3. **状态实时上报**
   - 模块检测到异常时主动通知 ModuleManager
   - ModuleManager 健康检查作为后备机制
   - 确保状态准确性

4. **分级恢复策略**
   - 轻度异常：模块自行处理（如 token 刷新）
   - 严重异常：ModuleManager 强制重启
   - 多次失败：标记为不可用，停止自动恢复

#### 2.2 IFlowModule 实现真实健康检查

**检查项**：
- 模块是否运行
- tmux 会话是否存在
- iflow 进程是否运行
- iflow 是否就绪（可选，更严格）

**返回信息**：
- 健康状态（true/false）
- 不健康原因（tmux_session_not_found、iflow_not_running 等）
- 详细信息（tmux 会话名、当前状态等）

#### 2.3 移除 IFlowModule 内部监控任务

**改动**：
- 删除 `_monitor_task()` 方法
- 停止创建内部监控任务
- 依赖 ModuleManager 统一监控

**优势**：
- 避免双重监控
- 状态统一管理
- 减少代码复杂度

#### 2.4 修改 ModuleManager 健康检查

**改进点**：
- 对于没有实现健康检查的模块，检查运行状态作为后备
- 默认不再假设模块健康，而是基于实际状态
- 增强日志，记录健康检查详情

**处理逻辑**：
- 优先调用模块的 `health_check()` 方法
- 如果模块未实现，检查 `running` 属性
- 如果都没有，返回不健康（保守策略）

#### 2.5 WeChatChannel 实现健康检查

**检查项**：
- 模块是否运行
- HTTP 客户端是否初始化
- access_token 是否过期（自动刷新）
- 回调服务是否运行（可选）

**自动恢复**：
- token 过期时自动刷新
- HTTP 客户端异常时尝试重新初始化

#### 2.6 增强自动恢复策略

**恢复流程**：
1. 停止模块
2. 等待配置的延迟时间
3. 重启模块
4. 检查恢复结果

**失败处理**：
- 记录失败次数
- 达到最大失败次数时停止自动恢复
- 标记模块为不可用状态
- 记录错误信息

**恢复成功**：
- 重置失败计数
- 更新模块状态为健康
- 记录恢复日志

#### 2.7 优化状态变更通知

**通知内容**：
- 模块 ID
- 新状态（healthy/unhealthy）
- 详细信息（原因、错误详情等）

**调用时机**：
- 健康检查发现状态变化时
- 自动恢复成功/失败时
- 模块主动上报异常时

**回调机制**：
- 支持多个状态回调函数
- 同时调用所有回调
- 捕获回调异常，不影响主流程

### 三、状态历史记录

#### 3.1 状态转换记录

```python
@dataclass
class StateTransition:
    """状态转换记录"""
    module_id: str
    from_state: str
    to_state: str
    timestamp: datetime
    reason: Optional[str] = None
    details: Optional[Dict[str, Any]] = None
```

#### 3.2 历史管理方法

```python
class ModuleManager:
    def __init__(self, message_bus: MessageBus):
        # ... 现有代码

        # 状态历史
        self.state_history: Dict[str, List[StateTransition]] = {}
        self.max_history_size = 100  # 每个模块最多保留 100 条记录

    def _record_state_transition(
        self,
        module_id: str,
        from_state: str,
        to_state: str,
        reason: str = None,
        details: Dict = None
    ) -> None:
        """记录状态转换"""
        if module_id not in self.state_history:
            self.state_history[module_id] = []

        transition = StateTransition(
            module_id=module_id,
            from_state=from_state,
            to_state=to_state,
            timestamp=datetime.now(),
            reason=reason,
            details=details
        )

        self.state_history[module_id].append(transition)

        # 限制历史记录数量
        if len(self.state_history[module_id]) > self.max_history_size:
            self.state_history[module_id] = self.state_history[module_id][-self.max_history_size:]

    def get_state_history(self, module_id: str, limit: int = 10) -> List[StateTransition]:
        """获取状态历史"""
        if module_id not in self.state_history:
            return []
        return self.state_history[module_id][-limit:]
```

#### 4.1 性能指标定义

```python
@dataclass
class ModuleMetrics:
    """模块性能指标"""
    module_id: str
    start_time: Optional[datetime] = None  # 启动时间
    startup_duration: float = 0  # 启动耗时（秒）
    message_count: int = 0  # 处理消息数量
    avg_processing_time: float = 0  # 平均处理时间（秒）
    max_processing_time: float = 0  # 最大处理时间（秒）
    error_count: int = 0  # 错误数量
    last_message_time: Optional[datetime] = None  # 最后消息时间

    def update_processing_time(self, duration: float) -> None:
        """更新处理时间"""
        self.message_count += 1
        self.max_processing_time = max(self.max_processing_time, duration)
        self.avg_processing_time = (
            (self.avg_processing_time * (self.message_count - 1) + duration) / self.message_count
        )
```

#### 4.2 性能监控方法

```python
class ModuleManager:
    def __init__(self, message_bus: MessageBus):
        # ... 现有代码

        # 性能指标
        self.module_metrics: Dict[str, ModuleMetrics] = {}

    def get_metrics(self, module_id: str) -> Optional[ModuleMetrics]:
        """获取模块性能指标"""
        return self.module_metrics.get(module_id)

    def get_all_metrics(self) -> Dict[str, ModuleMetrics]:
        """获取所有模块性能指标"""
        return self.module_metrics.copy()

    def record_message_processing(self, module_id: str, duration: float, success: bool) -> None:
        """记录消息处理"""

            return
```

### 五、健康检查配置

#### 5.1 配置定义

```python
@dataclass
class HealthCheckConfig:
    """健康检查配置"""
    interval: int = 30  # 检查间隔（秒）
    max_failures: int = 3  # 最大失败次数
    recovery_delay: int = 5  # 恢复延迟（秒）
```

#### 5.2 健康检查优化

```python
class ModuleManager:
    def __init__(
        self,
        message_bus: MessageBus,
        health_check_config: HealthCheckConfig = None
    ):
        # ... 现有代码

        # 健康检查配置
        self.health_check_config = health_check_config or HealthCheckConfig()

        # 健康检查失败计数
        self.health_check_failures: Dict[str, int] = {}

    async def _health_check_loop(self) -> None:
        """健康检查循环"""
        logger.info("[ModuleManager] 健康监控循环启动")

        try:
            while True:
                for module_id in self.modules.keys():
                    await self._check_module_health(module_id)

                await asyncio.sleep(self.health_check_config.interval)

        except asyncio.CancelledError:
            logger.info("[ModuleManager] 健康监控循环已取消")
        except Exception as e:
            logger.error(f"[ModuleManager] 健康监控循环错误: {e}", exc_info=True)

    async def _auto_recovery(self, module_id: str) -> bool:
        """自动恢复故障模块"""
        logger.info(f"[ModuleManager] 尝试自动恢复模块: {module_id}")

        # 等待恢复延迟
        await asyncio.sleep(self.health_check_config.recovery_delay)

        try:
            # 尝试重启模块
            success = await self.restart_module(module_id)

            if success:
                logger.info(f"[ModuleManager] 模块恢复成功: {module_id}")
                # 重置失败计数
                self.health_check_failures[module_id] = 0
                # 更新状态
                self.module_states[module_id].healthy = True
                self.module_states[module_id].error = None
                return True
            else:
                logger.error(f"[ModuleManager] 模块恢复失败: {module_id}")
                return False

        except Exception as e:
            logger.error(f"[ModuleManager] 自动恢复失败: {module_id}, {e}")
            return False
```

## 第四部分：单进程多组管理

### 一、方案概述

#### 1.1 核心理念

**按需实例化，集中管理，默认启动，按需扩展**

在单个进程中统一管理所有组，通过消息总线实现模块间通信，通过模块管理器实现组的动态启停和状态监控。默认只启动组1，其他组按需实例化。

#### 1.2 设计目标

- **资源优化**：只启动需要的组，节省系统资源
- **启动快速**：默认只启动组1，提高启动速度
- **按需扩展**：需要时才创建和启动其他组
- **集中控制**：通过组1统一控制其他组
- **状态一致**：状态集中存储和管理，查询快速准确
- **故障隔离**：组之间相互隔离，一个组的故障不影响其他组
- **开发友好**：支持快速重启组测试新代码

### 三、启动策略

#### 3.1 默认启动流程

**步骤**：
1. 服务启动
2. 加载配置文件
3. 创建消息总线
4. 创建模块管理器
5. 创建组1的模块（但不启动）
   - 创建 WeChat1 模块
   - 创建 IFlow1 模块
   - 创建 CommandHandler 模块
6. 设置组1的绑定关系
7. 定义组1
8. 注册其他组的定义（但不创建模块）
   - 注册组2定义
   - 注册组_simulator 定义
9. 启动组1
10. 启动健康监控
11. 启动管理接口（Unix Socket）
12. 进入运行状态

**特点**：
- 组1的模块在启动时创建
- 其他组的模块只在需要时创建
- 所有组的定义都注册到管理器
- 健康监控持续运行

#### 3.2 按需启动流程

**步骤**：
1. 接收启动组命令（如启动组2）
2. 检查组2是否已创建
3. 如果未创建，创建组2的模块
   - 创建 WeChat2 模块
   - 创建 IFlow2 模块
   - 设置绑定关系
4. 启动组2
5. 更新状态
6. 返回结果

**特点**：
- 延迟实例化
- 首次使用时才创建
- 避免资源浪费
- 创建后可重复启停

#### 3.3 组销毁流程

**步骤**：
1. 接收停止组命令
2. 检查组是否在运行
3. 停止组的所有模块
4. 清理资源
5. 更新状态
6. 返回结果

**可选**：
- 是否保留模块实例（用于快速重启）
- 是否完全销毁模块实例（释放资源）

### 四、控制机制

```
用户命令 → 组1的CommandHandler → 模块管理器 → 目标组
```

- 重启组：`./manage.py group-restart g2`
- 查看状态：`./manage.py group-status g2`
- 查看所有组：`./manage.py group-list`

**Unix Socket 接口**：
- 路径：`/tmp/ling-iflow.sock`
- 协议：简单的命令-响应模式
- 安全性：只有本机可以访问
- 用途：外部管理工具控制

**命令格式**：
```
start <group_name>
stop <group_name>
restart <group_name>
status <group_name>
list
```

### 五、状态管理

#### 5.1 状态存储机制

**存储位置**：模块管理器内部的数据结构

**存储内容**：
- 模块状态
  - 运行状态：运行中/已停止
  - 健康状态：健康/不健康
  - 性能指标：启动时间、处理时间、消息数量
  - 错误信息：最近一次错误
- 组状态
  - 组内所有模块的状态汇总
  - 组的运行状态
  - 组的健康状态
- 状态历史
  - 状态变化记录
  - 时间戳
  - 变更原因

#### 5.2 状态更新机制

**更新方式**：
1. 模块状态变化时，通过回调通知管理器
2. 管理器更新内部状态存储
3. 管理器触发状态变更通知
4. 记录状态历史

**触发场景**：
- 模块启动/停止
- 健康检查结果变化
- 错误发生/恢复
- 性能指标更新

#### 5.3 状态查询机制

**查询流程**：
1. 接收状态查询请求
2. 从管理器的状态存储中读取
3. 返回缓存的状态
4. 不需要向模块发起实时查询

**优势**：
- 响应速度快（微秒级）
- 不影响模块运行
- 状态一致性好
- 减少模块负担

### 六、工作流程

#### 6.1 日常运行流程

```
1. 服务启动
   ↓
2. 只启动组1
   ↓
3. 组1提供正常服务
   ↓
4. 健康监控持续运行
   ↓
5. 状态持续更新
   ↓
6. 用户通过组1使用服务
```

#### 6.2 测试新代码流程

```
1. 组1正常运行中
   ↓
2. 用户通过组1发送命令：/start-group g2
   ↓
3. 组2按需实例化并启动
   ↓
4. 用户修改代码
   ↓
5. 用户通过组1发送命令：/restart-group g2
   ↓
6. 组2重启并加载新代码
   ↓
7. 用户测试组2
   ↓
8. 测试通过后，用户通过组1发送命令：/restart-group g1
   ↓
9. 组1重启并加载新代码
   ↓
10. 用户通过组1发送命令：/stop-group g2
   ↓
11. 组2停止（可选）
```

#### 6.3 状态查询流程

```
1. 用户发送命令：/group-status g2
   ↓
2. CommandHandler 解析命令
   ↓
3. 调用模块管理器的状态查询接口
   ↓
4. 管理器从状态存储中读取
   ↓
5. 返回状态给用户
   ↓
6. 整个过程不向组2发起实时查询
```

#### 6.4 异常恢复流程

```
1. 健康监控检测到模块异常
   ↓
2. 记录异常状态
   ↓
3. 触发自动恢复
   ↓
4. 尝试重启模块
   ↓
5. 检查恢复结果
   ↓
6. 如果成功，更新状态为健康
   ↓
7. 如果失败，增加失败计数
   ↓
8. 如果达到最大失败次数，停止尝试并告警
```

## 总结

本文档整合了 MessageBus 消息总线、ModuleManager 模块管理器、状态管理优化和单进程多组管理的核心设计，构成了 Ling-iflow 项目的完整架构。

### 核心特点

1. **消息总线（MessageBus）**
   - 职责单一：专注于消息路由
   - 解耦清晰：模块间通过消息通信
   - 扩展灵活：支持点对点路由和广播发布

2. **模块管理器（ModuleManager）**
   - 集中管理：统一管理模块生命周期
   - 状态感知：实时监控模块健康状态
   - 自动恢复：检测异常并自动恢复

3. **状态管理优化**
   - 统一接口：所有模块实现健康检查
   - 集中监控：ModuleManager 统一监控
   - 分级恢复：不同级别的异常采用不同策略

4. **单进程多组管理**
   - 按需实例化：只创建需要的模块
   - 默认启动：只启动组1，提高启动速度
   - 集中控制：通过组1统一控制其他组

### 设计原则

- **单一职责**：每个组件职责明确
- **职责分离**：控制逻辑与业务逻辑分离
- **依赖倒置**：模块不直接依赖，通过消息总线通信
- **开闭原则**：添加新功能无需修改核心代码
- **异步优先**：所有操作使用 async/await

### 关键优势

1. **架构清晰**：分层设计，职责明确
2. **易于维护**：组件独立，降低耦合
3. **灵活扩展**：支持新模块和新功能
4. **稳定可靠**：健康监控和自动恢复
5. **开发友好**：支持快速测试和迭代

这个架构设计满足了当前项目需求，并为未来扩展预留了充分的空间。
