# 消息模拟器和测试工具方案

## 概述

### 背景

当前项目的测试依赖于 MockWeChatModule（模拟企业微信模块），这种方式存在以下问题：

1. 测试与特定渠道耦合，不易扩展
2. 添加新渠道需要修改测试代码
3. 测试工具与项目耦合，不够独立
4. 缺乏通用的消息测试机制

### 目标

创建一个通用的消息模拟器渠道，配合独立的测试工具，用于测试 iflow 模块的核心功能，不依赖具体的企业微信或其他社交渠道。

### 核心概念

**MessageSimulator（消息模拟器）**
- 作为项目的一个渠道模块
- 通用性强，不模拟任何特定渠道
- 通过 Socket 接收测试工具的消息
- 通过 Socket 发送 iflow 的回复给测试工具

**TestClientTool（测试客户端工具）**
- 独立的可执行程序
- 模拟用户发送消息，接收并显示 iflow 的回复
- 支持交互模式和命令行模式
- 完全独立于项目运行

## 架构设计

### 目录结构

```
src/modules/
├── channel/           # 渠道目录
│   ├── __init__.py
│   ├── wechat.py      # WeChatChannel
│   └── simulator.py   # SimulatorChannel（新增）
├── common/            # 通用组件
│   ├── converter.py   # MessageConverter（复用）
│   └── notifications.py
├── command/           # 命令处理
├── iflow/             # iflow 模块
└── wechat/            # 企业微信模块
    └── module.py      # WeChatModule

tools/
└── test_client.py     # 测试客户端工具（独立）
```

### 整体架构

```
TestClientTool (客户端)
        ↓
   TCP 连接
        ↓
SimulatorChannel (服务端)
        ↓
    MessageBus
        ↓
   IFlowModule
```

### 组件关系

**三个核心组件**：

**MessageSimulator**
- 位置：src/modules/channel/simulator.py
- 类型：渠道（SimulatorChannel）
- 角色：TCP 服务端
- 功能：接收测试工具消息，发送 iflow 回复

2. **TestClientTool**
   - 位置：tools/test_client.py
   - 类型：独立可执行程序
   - 角色：TCP 客户端
   - 功能：模拟用户交互，发送消息，显示回复

3. **Socket 通信**
   - 协议：TCP
   - 格式：JSON + 长度前缀
   - 模式：长连接
   - 特性：实时、可靠、高效

### 与现有架构集成

**集成方式**：
- SimulatorChannel 作为渠道放在 `src/modules/channel/` 目录
- 创建 SimulatorModule 使用 SimulatorChannel
- 作为普通模块注册到 MessageBus
- 使用标准的模块绑定机制与 IFlowModule 通信
- 复用 MessageConverter 进行消息转换
- 不需要修改 MessageBus 或 IFlowModule
- 不影响现有的 WeChatModule

**兼容性**：
- 可以与 WeChatModule 同时存在
- 通过配置选择使用哪个渠道
- 方便切换测试环境

**测试覆盖**：
- 单元测试：测试 SimulatorChannel 的核心功能
- 集成测试：测试完整的消息流转
- 替代现有的 MockWeChatModule 测试

## Socket 通信协议

### 消息格式

使用 JSON 格式封装消息，易于扩展和调试。

**消息结构**：
- 消息头：包含消息类型、消息 ID、时间戳
- 消息体：包含具体的数据内容
- 消息尾：包含校验信息（可选）

### 消息类型

**1. 控制消息**

心跳消息：
```
{
  "type": "heartbeat",
  "id": "hb_001",
  "timestamp": "2026-03-15T20:30:10Z"
}
```

握手消息（客户端 → 服务端）：
```
{
  "type": "handshake",
  "id": "hs_001",
  "timestamp": "2026-03-15T20:30:00Z",
  "client_version": "1.0.0",
  "client_id": "test_client_001"
}
```

握手确认（服务端 → 客户端）：
```
{
  "type": "handshake_ack",
  "id": "hs_ack_001",
  "timestamp": "2026-03-15T20:30:00Z",
  "server_version": "1.0.0",
  "server_id": "simulator_001"
}
```

关闭连接消息：
```
{
  "type": "close",
  "id": "close_001",
  "timestamp": "2026-03-15T20:35:00Z",
  "reason": "user_requested"
}
```

**2. 用户消息**（客户端 → 服务端）

发送消息：
```
{
  "type": "user_message",
  "id": "msg_001",
  "timestamp": "2026-03-15T20:30:00Z",
  "content": "你好",
  "metadata": {
    "user_id": "test_user",
    "chat_id": "test_chat",
    "is_group": false
  }
}
```

命令消息：
```
{
  "type": "command",
  "id": "cmd_001",
  "timestamp": "2026-03-15T20:31:00Z",
  "command": "get_stats",
  "params": {}
}
```

**3. 回复消息**（服务端 → 客户端）

文本回复：
```
{
  "type": "reply_message",
  "id": "reply_001",
  "request_id": "msg_001",
  "timestamp": "2026-03-15T20:30:05Z",
  "content": "你好！有什么可以帮助你？",
  "metadata": {
    "message_type": "text",
    "scope": "reply"
  }
}
```

状态通知：
```
{
  "type": "status_notification",
  "id": "status_001",
  "timestamp": "2026-03-15T20:30:02Z",
  "status": "generating",
  "metadata": {
    "request_id": "msg_001"
  }
}
```

错误通知：
```
{
  "type": "error_notification",
  "id": "error_001",
  "timestamp": "2026-03-15T20:30:10Z",
  "error_code": "timeout",
  "error_message": "请求超时",
  "metadata": {
    "request_id": "msg_001"
  }
}
```

### 传输机制

**消息封装**：
1. 将消息序列化为 JSON 字符串
2. 计算消息字节数（使用 UTF-8 编码）
3. 将字节数转换为 4 字节的长度字段（网络字节序）
4. 将长度字段和消息内容组合

**接收流程**：
1. 读取 4 字节的长度字段
2. 将长度字段转换为整数
3. 根据长度读取完整消息
4. 解析 JSON 消息
5. 验证消息格式

**发送流程**：
1. 将消息对象序列化为 JSON
2. 计算 JSON 字节数
3. 将字节数转换为 4 字节的长度字段
4. 先发送长度字段
5. 再发送消息内容

### 网络配置

**端口选择**：
- 默认端口：19999
- 支持端口冲突检测
- 支持自动选择可用端口

**连接参数**：
- 地址：localhost（默认）
- 端口：19999（默认）
- 超时时间：30 秒
- 心跳间隔：30 秒
- 最大连接数：10（可选）

## SimulatorChannel 详细设计

### 核心职责

1. 监听 TCP 端口，接受客户端连接
2. 管理多个客户端连接（可选）
3. 接收客户端发送的消息
4. 将消息转换为标准格式（使用 MessageConverter），发送到 MessageBus
5. 接收 MessageBus 返回的回复
6. 将回复通过 TCP 发送给对应的客户端
7. 处理连接的建立、维护和关闭

### 模块组成

**1. Socket 服务端**
- 监听指定端口
- 接受新的连接
- 为每个连接创建独立的处理器
- 管理连接列表

**2. 连接处理器**
- 处理单个客户端的所有消息
- 解析接收到的消息
- 发送消息到 MessageBus
- 接收回复并发回客户端
- 处理心跳和超时

**3. 消息转换**
- 复用 MessageConverter 进行 Socket 消息与标准 Message 格式的转换
- 注册 simulator 的入站/出站转换器
- 统一的消息转换逻辑

**4. 连接管理器**
- 维护活跃连接列表
- 处理连接的建立和断开
- 处理连接超时和错误

### 工作流程

**启动流程**：
1. 创建 TCP socket
2. 绑定到指定端口
3. 开始监听
4. 启动接受连接的后台任务
5. 记录服务端就绪状态

**接收消息流程**：
1. 连接处理器从 socket 读取数据
2. 读取 4 字节的消息长度
3. 根据长度读取完整消息
4. 解析 JSON 消息
5. 验证消息格式
6. 转换为 MessageBus 消息
7. 发送到 MessageBus

**发送回复流程**：
1. 从 MessageBus 接收回复
2. 转换为 Socket 消息格式
3. 序列化为 JSON
4. 计算消息长度
5. 写入长度字段（4 字节）
6. 写入消息内容
7. 确保发送成功

**关闭流程**：
1. 停止接受新连接
2. 关闭所有活跃连接
3. 通知所有客户端
4. 关闭服务端 socket
5. 清理资源

### 状态管理

**服务端状态**：
- 未启动
- 监听中
- 已停止

**连接管理**：
- 活跃连接列表
- 连接 ID 映射
- 连接统计信息

**消息统计**：
- 发送消息数
- 接收消息数
- 错误消息数

**性能指标**：
- 当前连接数
- 消息吞吐量
- 平均响应时间

### 错误处理

**连接错误**：
- 记录错误日志
- 关闭异常连接
- 通知相关客户端

**消息解析错误**：
- 发送错误通知
- 不关闭连接
- 记录错误日志

**发送失败**：
- 重试机制（最多 3 次）
- 超过次数后关闭连接
- 记录错误日志

**超时处理**：
- 心跳检测（每 30 秒）
- 超时自动关闭连接
- 通知客户端

## TestClientTool 详细设计

### 核心职责

1. 连接到 MessageSimulator 服务端
2. 提供交互式用户界面
3. 接收用户输入，转换为消息发送
4. 接收服务端回复，显示给用户
5. 管理连接状态
6. 提供命令行操作接口

### 运行模式

**1. 交互模式**

界面设计：
```
==================================================
消息模拟器测试工具
==================================================
连接状态: 已连接 (localhost:19999)
当前对话: test_user
消息统计: 发送 0, 接收 0
================================================--
输入消息（输入 /help 查看命令）:
> _
```

用户交互：
- 提示符显示当前状态
- 用户输入消息后按回车发送
- 工具等待回复，显示结果
- 支持多行输入（使用反斜杠换行）
- 显示发送和接收的消息
- 显示消息的时间戳

**2. 命令行模式**

命令格式：
```
test-client [选项] [参数]
```

支持选项：
- `--host <hostname>`：服务端主机地址（默认：localhost）
- `--port <port>`：服务端端口（默认：19999）
- `--mode <mode>`：运行模式（interactive 或 batch）
- `--send <message>`：发送消息
- `--wait <seconds>`：等待回复的时间
- `--timeout <seconds>`：超时时间
- `--repeat <n>`：重复发送次数
- `--file <filename>`：从文件读取消息
- `--output <filename>`：保存输出到文件
- `--verbose`：显示详细日志
- `--quiet`：静默模式

使用示例：
```bash
# 交互模式
test-client --mode interactive

# 发送单条消息
test-client --send "你好"

# 发送多条消息
test-client --send "你好" --send "介绍一下你自己"

# 从文件读取消息
test-client --file messages.txt

# 重复发送消息
test-client --send "你好" --repeat 5

# 保存输出
test-client --send "你好" --output reply.txt
```

配置文件位置：config.json

```json
{
  "simulator_channel": {
    "enabled": true,
    "host": "localhost",

    "max_connections": 10,
```

## 与现有代码的关系

### 与 MockWeChatModule 的关系

**替换关系**：
- SimulatorModule 可以替代 MockWeChatModule
- 提供更通用的测试能力
- 不模拟任何特定渠道

**区别**：
- MockWeChatModule：模拟企业微信，用于集成测试
- SimulatorModule：通用模拟器，用于功能测试
- 架构优势：SimulatorModule 与 WeChatModule 使用相同的架构模式

### 与 WeChatModule 的关系

**架构一致性**：
- 两者使用相同的架构模式
- WeChatModule = WeChatChannel + 通用组件
- SimulatorModule = SimulatorChannel + 通用组件
- 都复用 MessageConverter

**并行关系**：
- 两者可以同时存在
- 通过配置选择使用哪个
- 互不影响

**互补关系**：
- WeChatModule：用于生产环境
- SimulatorModule：用于测试和开发

### 与 MessageBus 的关系

**集成关系**：
- MessageSimulator 作为普通模块注册
- 使用标准的消息路由机制
- 不修改 MessageBus

## 优势总结

### 1. 通用性强

- 不依赖具体渠道
- 可以测试任何渠道以外的功能
- 适用于多种测试场景

### 2. 独立性高

- 测试工具完全独立
- 不依赖项目运行环境
- 可以单独开发和维护

### 3. 易于实现

- Socket 通信成熟可靠
- 不需要复杂的依赖
- 易于调试和维护

### 4. 可扩展性好

- 支持添加新功能
- 可以升级通信机制
- 可以扩展为多客户端

### 5. 改动最小

- 只需在 `src/modules/channel/` 添加 SimulatorChannel
- 创建 SimulatorModule 集成 SimulatorChannel
- 复用 MessageConverter，减少重复代码
- 不修改现有代码
- 风险可控

### 6. 架构统一

- 与 WeChatModule 使用相同的架构模式
- Channel + Module 的分离设计
- 便于理解和维护
- 降低学习成本

- 心跳机制
- 自动重连
- 超时处理

### 风险 3：消息格式兼容性

**应对**：
- 版本协商
- 向后兼容
- 格式验证

### 风险 4：并发连接管理

**应对**：
- 连接池管理
- 资源限制
- 优雅降级

## 总结

本方案设计了一个通用的消息模拟器和测试工具，使用 Socket 通信实现实时、高效的消息传输。该方案具有通用性强、独立性高、易于实现、可扩展性好、改动最小、架构统一等优势，能够满足项目测试和开发的需求。

**架构优势**：
- SimulatorChannel 放在 `src/modules/channel/` 目录，与 WeChatChannel 同级
- 复用 MessageConverter 进行消息转换，减少重复代码
- 与 WeChatModule 使用相同的架构模式（Channel + Module）
- 便于理解和维护，降低学习成本

通过分阶段实施，可以逐步完善功能，降低风险。最终可以替代现有的 MockWeChatModule，提供更强大、更灵活的测试能力。
