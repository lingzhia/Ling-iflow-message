# 模块管理器设计方案

## 概述

ModuleManager（模块管理器）是 Ling-iflow 项目的控制层组件，负责模块生命周期管理、状态监控、健康检查和消息应答检查。与 MessageBus 配合，实现控制逻辑和业务逻辑的分离。

---

## 核心理念

- **职责分离**：控制逻辑（ModuleManager）与业务逻辑（MessageBus）分离
- **集中管理**：统一管理所有模块的生命周期和状态
- **状态感知**：实时监控模块健康状态和运行状态
- **错误处理**：在发送前检查接收方状态，提供友好的错误响应

---

## 设计背景

### 当前问题

1. **启动逻辑分散**：模块创建、注册、启动逻辑分散在多个地方
2. **状态管理缺失**：没有统一的模块状态管理
3. **错误处理不足**：消息发送前不检查接收方状态
4. **健康监控缺失**：没有自动化的健康检查机制
5. **启动顺序固定**：无法灵活控制模块启动顺序

### 解决方案

创建独立的 ModuleManager 组件，负责：
- 模块生命周期管理
- 模块状态管理
- 健康监控
- 消息应答检查
- 启动顺序控制

## 功能划分

### ModuleManager 职责

**核心职责**：

1. **模块生命周期管理**
   - 创建模块实例
   - 销毁模块实例
   - 启动模块
   - 停止模块
   - 重启模块

2. **模块注册协调**
   - 创建模块后注册到消息总线
   - 销毁模块前从消息总线注销
   - 设置模块的消息总线引用

3. **模块状态管理**
   - 记录模块运行状态
   - 记录模块健康状态
   - 记录模块启动时间
   - 记录模块停止时间

4. **健康监控**
   - 定期检查模块健康状态
   - 检测模块异常
   - 触发状态变更通知

5. **启动顺序控制**
   - 定义模块启动顺序
   - 按顺序启动模块
   - 按顺序停止模块

6. **依赖管理**
   - 定义模块依赖关系
   - 启动前检查依赖
   - 确保依赖满足

7. **组管理**
   - 定义模块组
   - 按组启动模块
   - 按组停止模块

8. **消息应答检查**
   - 路由前检查接收方状态
   - 检查模块是否可用
   - 生成错误响应

9. **IFlow 状态管理**
   - 记录 iflow 生成状态
   - 记录生成持续时间
   - 检查 iflow 可用性

10. **故障恢复**
    - 自动重启故障模块
    - 尝试恢复异常模块
    - 记录恢复日志

### MessageBus 职责

**核心职责**（保持简单）：

1. **模块注册**
   - 注册模块实例
   - 注销模块实例
   - 查询模块列表

2. **绑定管理**
   - 建立模块间绑定关系
   - 解除绑定关系
   - 查询绑定关系

3. **消息路由**
   - 根据绑定关系路由消息
   - 直接发送到指定模块
   - 发布消息到主题

4. **发布订阅**
   - 订阅主题
   - 取消订阅
   - 发布消息

## 职责边界

### MessageBus 负责

| 功能 | 说明 | 边界 |
|------|------|------|
| 模块注册 | 维护模块注册表 | 只管理注册表，不负责创建 |
| 消息路由 | 根据绑定关系路由 | 不检查模块状态 |
| 绑定管理 | 管理模块绑定关系 | 只管理关系，不管理依赖 |
| 发布订阅 | 实现发布订阅机制 | 不关心订阅者的状态 |

### ModuleManager 负责

| 功能 | 说明 | 边界 |
|------|------|------|
| 模块创建 | 创建模块实例 | 创建后注册到消息总线 |
| 模块启动 | 启动模块 | 启动前检查依赖 |
| 状态管理 | 管理模块状态 | 独立的状态存储 |
| 健康监控 | 监控模块健康 | 不修改消息总线 |
| 依赖管理 | 管理模块依赖 | 独立的依赖配置 |
| 消息应答 | 检查接收方状态 | 检查后再路由 |

## 交互流程

### 1. 模块创建和注册流程

```
外部管理工具
    ↓
模块管理器创建模块
    ↓
模块管理器初始化模块
    ↓
模块管理器注册模块到消息总线
    ↓
模块管理器设置模块的消息总线引用
    ↓
模块管理器启动模块
    ↓
模块开始运行
```

### 2. 消息发送流程（带应答检查）

```
WeChatModule 发送消息
    ↓
调用模块管理器的发送方法
    ↓
模块管理器检查接收方状态
    ↓
┌─────────────────────────────────────┐
│ 接收方不存在                         │
│ → 返回错误响应                       │
└─────────────────────────────────────┘

┌─────────────────────────────────────┐
│ 接收方存在但状态异常                 │
│ → 返回错误响应                       │
└─────────────────────────────────────┘

┌─────────────────────────────────────┐
│ 接收方存在且状态正常                 │
│ → 调用消息总线路由                   │
└─────────────────────────────────────┘
    ↓
消息总线路由到目标模块
    ↓
目标模块接收并处理消息
```

### 3. 模块启动流程

```
外部管理工具启动组
    ↓
模块管理器解析组配置
    ↓
模块管理器检查依赖关系
    ↓
模块管理器按启动顺序启动模块
    ↓
每个模块启动前检查依赖
    ↓
依赖满足则启动，否则等待
    ↓
所有模块启动完成
```

### 4. 健康监控流程

```
模块管理器启动健康监控
    ↓
定期检查每个模块的健康状态
    ↓
┌─────────────────────────────────────┐
│ 模块状态正常                         │
│ → 继续监控                           │
└─────────────────────────────────────┘

┌─────────────────────────────────────┐
│ 模块状态异常                         │
│ → 记录异常状态                       │
│ → 触发状态变更通知                   │
│ → 尝试自动恢复                       │
└─────────────────────────────────────┘
```

## 核心方法

### 模块生命周期管理

| 方法 | 说明 | 返回值 |
|------|------|--------|
| `create_module(type, config)` | 创建模块 | BaseModule |
| `destroy_module(module_id)` | 销毁模块 | bool |
| `start_module(module_id)` | 启动模块 | bool |
| `stop_module(module_id)` | 停止模块 | bool |
| `restart_module(module_id)` | 重启模块 | bool |

### 状态管理

| 方法 | 说明 | 返回值 |
|------|------|--------|
| `get_module_status(module_id)` | 获取模块状态 | Dict |
| `get_all_status()` | 获取所有模块状态 | Dict |
| `is_module_running(module_id)` | 检查模块是否运行 | bool |
| `is_module_healthy(module_id)` | 检查模块是否健康 | bool |

### 健康监控

| 方法 | 说明 | 返回值 |
|------|------|--------|
| `start_health_monitor()` | 启动健康监控 | None |
| `stop_health_monitor()` | 停止健康监控 | None |
| `check_module_health(module_id)` | 检查模块健康 | Dict |

### 启动控制

| 方法 | 说明 | 返回值 |
|------|------|--------|
| `start_group(group_name)` | 启动指定组 | bool |
| `stop_group(group_name)` | 停止指定组 | bool |
| `start_with_order(module_ids)` | 按顺序启动 | bool |
| `stop_with_order(module_ids)` | 按顺序停止 | bool |

### 依赖管理

| 方法 | 说明 | 返回值 |
|------|------|--------|
| `check_dependencies(module_id)` | 检查依赖 | bool |
| `get_dependencies(module_id)` | 获取依赖列表 | List |
| `add_dependency(module_id, dep_id)` | 添加依赖 | bool |

### 消息应答检查

| 方法 | 说明 | 返回值 |
|------|------|--------|
| `send_with_check(message)` | 发送消息并检查 | Dict |
| `check_receiver(module_id)` | 检查接收方 | Dict |
| `generate_error_response(error_type)` | 生成错误响应 | Dict |

### IFlow 状态管理

| 方法 | 说明 | 返回值 |
|------|------|--------|
| `get_iflow_status(module_id)` | 获取 iflow 状态 | Dict |
| `is_iflow_available(module_id)` | 检查 iflow 可用性 | bool |
| `update_iflow_state(module_id, state)` | 更新 iflow 状态 | None |

## 优势

### 1. 职责清晰

- **消息总线**：专注于消息路由，保持简单
- **模块管理器**：专注于模块管理，功能集中
- **边界明确**：两者职责不重叠

### 2. 易于维护

- **独立演进**：两个组件可以独立开发和测试
- **降低耦合**：修改一个不影响另一个
- **易于调试**：问题定位更清晰

### 3. 灵活扩展

- **功能扩展**：新功能添加到合适的组件
- **性能优化**：可以针对不同组件优化
- **技术升级**：可以独立升级组件

### 4. 便于测试

- **单元测试**：每个组件可以独立测试
- **集成测试**：测试组件间的协作
- **模拟测试**：可以模拟组件进行测试

## 总结

### 核心原则

**职责分离，边界清晰**

- **消息总线**：消息路由专家，保持简单
- **模块管理器**：模块管理专家，功能集中
- **协作关系**：模块管理器控制模块，模块通过消息总线通信

### 关键优势

1. **单一职责**：每个组件职责明确
2. **低耦合**：组件间依赖最小化
3. **高内聚**：相关功能集中管理
4. **易扩展**：新功能易于添加

这个方案既能满足需求，又能保持架构的清晰和可维护性。
