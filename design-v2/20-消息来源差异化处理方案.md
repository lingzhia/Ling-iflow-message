# 消息来源差异化处理方案

## 一、问题背景

### 1.1 问题描述

当前 IFlowModule 完整记录 iflow 返回的所有消息（✦ 和 ✻），无论请求消息来自哪里。但是，对于不同来源的请求消息，回复消息的发送方式应该有所区别：

1. **企业微信/模拟器等渠道发送的消息**：
   - 有明确来源（`from_module` 不为空）
   - 期望：实时响应，逐条发送回复消息

2. **用户在 tmux 中手动输入的消息**：
   - 无明确来源（未经过接口，MessageStore 中无记录）
   - 期望：完整回复，避免碎片化信息

### 1.2 当前问题

**问题1：所有回复消息都逐条发送**
- 用户手动输入时，也会收到多条碎片化消息
- 缺乏完整的上下文体验

**问题2：无法区分请求来源**
- IFlowMonitor 提取回复消息时，不知道请求消息的来源
- 无法智能选择发送方式

## 二、核心思想

**根据请求消息的来源状态，决定回复消息的发送方式：**

- **有明确来源** → 逐条实时发送（流式模式）
- **无明确来源** → 等待完整后整合发送（缓冲模式）

## 三、判断依据

### 3.1 消息来源判断

**判断标准**：请求消息的 `source` 字段（来自 MessageStore）

**判断时机**：每次扫描 tmux 输出，提取到请求消息时

**判断方法**：
1. IFlowMonitor 扫描 tmux 输出，提取请求消息（以 `>` 开头的内容）
2. 在 MessageStore 中查找匹配的记录（根据消息内容精确匹配）
3. 检查匹配记录的 `source` 字段：
   - `source` 不为空 → 有明确来源
   - `source` 为空或未找到 → 无明确来源

### 3.2 匹配规则

**精确匹配**：
- 消息内容完全相同
- 状态为 PROCESSING（处理中）
- 时间窗口：5分钟内（避免误匹配）

## 四、两种模式

### 4.1 流式模式（Stream Mode）

**触发条件**：
- 请求消息匹配到 MessageStore 中的记录
- 该记录的 `source` 字段不为空

**发送行为**：
- 每提取到一条 ✦ 消息 → 立即发送到 `source` 指定的模块
- ✻ 消息不发送（被过滤）
- 每条消息独立发送，不等待其他消息

**适用场景**：
- 企业微信发送的消息
- 模拟器发送的消息
- 任何通过接口进入的消息

**用户体验**：
- 实时看到回复
- 逐条到达
- 感觉流畅

### 4.2 缓冲模式（Buffer Mode）

**触发条件**：
- 请求消息未匹配到 MessageStore 中的记录
- 或者匹配记录的 `source` 字段为空

**发送行为**：
- 每提取到一条 ✦ 消息 → 暂存到缓冲区
- ✻ 消息不处理
- 生成结束时（GENERATING → IDLE）→ 整合缓冲区的所有 ✦ 消息为一条
- 发送整合后的消息到消息总线（receiver 为空）

**适用场景**：
- 用户在 tmux 中手动输入的消息
- 任何不经过接口直接进入 iflow 的消息

**用户体验**：
- 等待完整回复
- 一次性收到
- 内容完整

## 五、完整流程

### 5.1 场景A：企业微信发送消息（流式模式）

```
步骤1：消息接收
  用户 → 企业微信 → WeChatChannel → MessageBus → IFlowModule
  → IFlowModule.send()
  → MessageStore.add(source="wechat_bot1", content="1+1=?")
  → 注入到 iflow

步骤2：请求消息扫描
  IFlowMonitor 扫描 tmux 输出
  → 提取请求消息："> 1+1=?"
  → MessageStore.find_by_content("1+1=?")
  → 找到匹配记录（source="wechat_bot1"）
  → 判断：有明确来源
  → 设置模式：流式模式（STREAM_MODE）

步骤3：回复消息处理
  iflow 回复：
  ✦ 1+1=2 → IFlowMonitor 提取 → 立即发送到 wechat_bot1
  ✻ 思考中... → IFlowMonitor 提取 → 不发送（过滤）
  ✦ 详细解释... → IFlowMonitor 提取 → 立即发送到 wechat_bot1

步骤4：用户收到
  企业微信用户收到 2 条消息，实时到达
```

### 5.2 场景B：tmux 手动输入（缓冲模式）

```
步骤1：消息发送
  用户在 tmux 中输入："1+1=?"
  → 消息直接进入 iflow
  → MessageStore 中无记录（未经过接口）

步骤2：请求消息扫描
  IFlowMonitor 扫描 tmux 输出
  → 提取请求消息："> 1+1=?"
  → MessageStore.find_by_content("1+1=?")
  → 未找到匹配记录
  → 判断：无明确来源
  → 设置模式：缓冲模式（BUFFER_MODE）

步骤3：回复消息处理
  iflow 回复：
  ✦ 1+1=2 → IFlowMonitor 提取 → 暂存到缓冲区
  ✻ 思考中... → IFlowMonitor 提取 → 不处理
  ✦ 详细解释... → IFlowMonitor 提取 → 暂存到缓冲区

步骤4：生成结束
  状态变化：GENERATING → IDLE
  → IFlowMonitor._flush_buffered_messages()
  → 整合缓冲区："1+1=2\n详细解释..."
  → 发送到消息总线（receiver=""）

步骤5：订阅者收到
  订阅者收到 1 条整合后的消息
```

## 六、实现要点

### 6.1 MessageStore 扩展

**新增字段**：
```python
@dataclass
class MessageRecord:
    # ... 现有字段 ...
    requires_buffering: bool = False  # 是否需要缓冲回复（无来源时为 True）
    buffered_replies: List[str] = field(default_factory=list)  # 缓冲的回复内容
```

**新增方法**：
- `find_by_content(content: str)` - 根据内容查找消息记录
- `add_buffered_reply(message_id: str, reply_content: str)` - 添加缓冲的回复
- `get_buffered_replies(message_id: str)` - 获取缓冲的回复

### 6.2 IFlowMonitor 扩展

**新增字段**：
```python
class IFlowMonitor:
    _send_mode: str  # 发送模式：STREAM_MODE 或 BUFFER_MODE
    _current_request_record: Optional[MessageRecord]  # 当前请求的记录
```

**修改方法**：
- `_extract_messages()` - 提取请求消息时，匹配 MessageStore，判断发送模式
- `_send_message()` - 根据 send_mode 决定立即发送或缓冲

**新增方法**：
- `_send_immediately()` - 立即发送消息（流式模式）
- `_buffer_message()` - 缓冲消息（缓冲模式）
- `_flush_buffered_messages()` - 发送缓冲的消息（生成结束时调用）

### 6.3 状态变化处理

**生成结束时刷新缓冲区**：
```python
async def _handle_state_change(old_state: IFlowState, new_state: IFlowState):
    if old_state == IFlowState.GENERATING and new_state == IFlowState.IDLE:
        if self._send_mode == "BUFFER_MODE":
            await self._flush_buffered_messages()
        self._send_mode = "STREAM_MODE"
        self._current_request_record = None
```

## 七、关键差异

| 项目 | 流式模式 | 缓冲模式 |
|------|---------|---------|
| 触发条件 | 请求有明确来源 | 请求无明确来源 |
| 发送时机 | 每条立即发送 | 生成结束后整合发送 |
| 发送目标 | 特定来源模块 | 消息总线（广播） |
| 消息数量 | 多条（逐条） | 1条（整合） |
| 用户体验 | 实时响应 | 完整交付 |

## 八、优势

### 8.1 用户体验优化
- **企业微信**：实时看到回复，感觉流畅
- **手动输入**：获得完整回复，避免碎片信息

### 8.2 逻辑清晰
- 有来源 = 实时响应
- 无来源 = 完整交付

### 8.3 自动判断
- 系统自动检测消息来源
- 无需人工配置
- 智能切换发送模式

### 8.4 向后兼容
- 有来源的消息保持原有逻辑（流式发送）
- 无来源的消息使用新逻辑（缓冲发送）

## 九、风险评估

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|----------|
| 消息匹配失败 | 中 | 中 | 使用精确匹配 + 时间窗口 + 状态过滤 |
| 缓冲区泄漏 | 低 | 高 | 生成结束时自动清空 |
| 状态同步问题 | 低 | 中 | 使用状态机确保一致性 |
| 性能影响 | 低 | 低 | 缓冲区大小可控，发送模式切换开销小 |
