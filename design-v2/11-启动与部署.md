# 启动与部署方案

## 一、项目启动方案设计

### 1.1 当前启动流程分析

#### 现有实现

1. 创建 MessageBus
2. 创建并注册 IFlowModule
3. 创建并注册 WeChatModule
4. 设置绑定关系
5. 启动 IFlowModule
6. 启动 WeChatModule

#### 存在的问题

| 问题 | 说明 |
|------|------|
| 缺少健康检查机制 | 无法判断模块是否真正就绪 |
| 缺少依赖验证 | 未验证系统依赖是否满足 |
| 启动失败处理不完善 | 失败后缺乏重试和降级策略 |
| 没有优雅降级策略 | 部分组件失败时整体崩溃 |
| 启动状态可视化不足 | 难以了解启动进度 |

### 1.2 完整启动方案

#### 1.2.1 模块依赖关系

| 顺序 | 模块 | 依赖关系 |
|------|------|----------|
| 1 | MessageBus | 核心，无依赖 |
| 2 | IFlowModule | 依赖 MessageBus |
| 3 | WeChatModule | 依赖 MessageBus |

**依赖规则：**

- MessageBus 必须先启动（消息路由核心）
- IFlowModule 和 WeChatModule 可以并行启动（无相互依赖）
- 绑定关系在所有模块注册后设置

#### 1.2.2 健康检查机制

**IFlowModule 健康检查项：**

| 检查项 | 说明 |
|--------|------|
| tmux_session | tmux 会话是否存在 |
| iflow_process | iflow 进程是否运行 |
| workspace | 工作目录是否存在 |
| monitor | 监控器是否运行 |

**WeChatModule 健康检查项：**

| 检查项 | 说明 |
|--------|------|
| http_server | HTTP 服务器是否监听 |
| config | 配置是否完整 |
| crypto | 加密配置是否有效 |
| message_bus | 消息总线是否连接 |

**MessageBus 健康检查项：**

| 检查项 | 说明 |
|--------|------|
| modules | 是否已有模块注册 |
| bindings | 是否已有绑定关系 |
| subscribers | 订阅者数量 |
| running | 运行状态 |

#### 1.2.3 启动流程优化

##### 阶段 1: 预检查

| 检查项 | 说明 |
|--------|------|
| 配置文件检查 | 检查配置文件是否存在，必要字段是否完整 |
| 系统依赖检查 | 检查 tmux 等系统依赖是否安装 |
| 端口占用检查 | 检查回调端口是否被占用 |

##### 阶段 2: 初始化模块

| 步骤 | 说明 |
|------|------|
| 1 | 创建消息总线 |
| 2 | 创建并注册 IFlowModule |
| 3 | 创建并注册 WeChatModule |
| 4 | 设置绑定关系 |
| 5 | 模块健康检查 |

##### 阶段 3: 启动模块

| 特性 | 说明 |
|------|------|
| 并行启动 | IFlowModule 和 WeChatModule 可并行启动 |
| 重试机制 | 启动失败时自动重试（默认3次，间隔5秒） |
| 状态总结 | 启动完成后输出状态总结 |

#### 1.2.4 优雅降级策略

##### 降级场景

| 场景 | 降级策略 | 说明 |
|------|---------|------|
| IFlowModule 启动失败 | 仅启动 WeChatModule | WeChat 可以接收消息但无法处理 |
| WeChatModule 启动失败 | 仅启动 IFlowModule | 可以通过 tmux 直接使用 iflow |
| 部分实例失败 | 跳过失败实例，启动其他实例 | 多实例部署时的高可用策略 |
| 端口占用 | 尝试使用备用端口 | 自动切换到备用端口 |

#### 1.2.5 完整启动流程

```
启动流程

1. 预检查阶段
   ├── 检查配置文件
   ├── 检查系统依赖（tmux）
   └── 检查端口占用
   ↓
2. 初始化阶段
   ├── 创建 MessageBus
   ├── 创建并注册 IFlowModule
   ├── 创建并注册 WeChatModule
   ├── 设置绑定关系
   └── 模块健康检查
   ↓
3. 启动阶段
   ├── 并行启动 IFlowModule（带重试）
   ├── 并行启动 WeChatModule（带重试）
   └── 启动状态总结
   ↓
4. 状态检查
   ├── 打印启动状态概览
   └── 判断是否可以正常运行
   ↓
5. 运行阶段
   ├── 监控模块健康状态
   └── 异常时触发降级策略
```

## 二、IFlow 启动就绪检查方案

### 2.1 问题背景

在测试过程中发现，`IFlowController.check_iflow_running()` 方法在 iflow 启动后立即返回 `True`，但实际上 iflow 仍处于"生成中"状态，无法接受消息。

**关键问题：**

- UI 界面已显示（输入框、欢迎消息、版本号）
- iflow 一直显示 "生成中" 进度条，持续 20 秒
- `check_iflow_running()` 只检查 UI，没有检查"生成中"状态
- 工具在 iflow 未就绪时发送消息，导致消息丢失

### 2.2 解决方案

#### 2.2.1 添加 `check_iflow_ready()` 方法

**检查条件：**

| 条件 | 说明 |
|------|------|
| 1 | tmux 会话存在 |
| 2 | UI 已就绪（检测到输入框、欢迎消息、版本号） |
| 3 | 不在"生成中"状态（没有进度条） |
| 4 | 输入框可用 |

#### 2.2.2 修改 `start_iflow()` 使用 `check_iflow_ready()`

- 使用 `check_iflow_ready()` 替代 `check_iflow_running()`
- 等待所有检查条件满足后才返回就绪

#### 2.2.3 添加 `wait_for_ready()` 方法（IFlowModule）

- 等待 iflow 完全就绪
- 支持超时保护（默认60秒）
- 提供 `is_ready` 属性用于快速检查

### 2.3 完整的时间线

```
工具.start()
  ↓
模块.start()
  ↓
controller.start_iflow()
  ↓
启动 iflow 进程
  ↓
等待 check_iflow_ready() 返回 True  ✅ 确保不在"生成中"
  ↓
monitor.start() + 等待 3 秒初始化
  ↓
模块启动完成
  ↓
等待 wait_for_ready()  ✅ 再次确认就绪
  ↓
工具启动完成  ✅ iflow 完全就绪，可以发送消息
```

### 2.4 关键改进

| 改进 | 说明 |
|------|------|
| 双重检查 | 启动时检查一次，发送消息前再检查一次 |
| 等待机制 | 工具启动后等待 iflow 完全就绪 |
| 状态查询 | 提供 `is_ready` 属性用于快速检查 |
| 超时保护 | 设置合理的超时时间（60秒） |
| 详细日志 | 记录就绪状态，便于调试 |

### 2.5 实施计划

#### 阶段 1: 修改 IFlowController（P0）

|------|------|
| 添加 `check_iflow_ready()` 方法 | 检查 iflow 真正就绪 |

#### 阶段 2: 修改 IFlowModule（P0）

## 四、渠道配置与管理策略

### 4.1 配置文件的作用

**配置文件作为信息库**

`config.json` 中的 `bots` 和 `simulator_channels` 是一个渠道信息库，包含所有可用的渠道配置，但**不要求所有渠道都必须启动**。

**配置文件的作用：**

| 作用 | 说明 |
|------|------|
| 信息存储 | 存储所有渠道的配置信息 |
| 按需使用 | 可以查询并使用配置创建渠道实例 |
| 灵活管理 | 不要求所有渠道都启动 |

### 4.2 渠道实例管理原则

**核心原则：**

1. **只跟踪已启动的实例**
   - 只跟踪通过命令明确启动的渠道
   - 不自动启动所有 enabled=true 的渠道

2. **状态显示规则**
   - 只显示已启动渠道的状态
   - 不显示未启动渠道的任何状态信息
   - 避免误导用户

3. **默认启动行为**
   - 不指定渠道时，只启动第一个 enabled=true 的渠道（默认渠道）
   - 必须明确指定才能启动其他渠道

### 4.3 启动命令设计

#### 4.3.1 默认启动行为

```bash
# 只启动第一个 enabled=true 的渠道
./manage.py start
```

**启动流程：**
1. 读取配置文件
2. 找到第一个 enabled=true 的渠道
3. 创建并启动该渠道
4. 只跟踪已启动的渠道

#### 4.3.2 指定渠道启动

```bash
./manage.py start --channel bot1
./manage.py start --channel bot2
./manage.py start --channel simulator1
```

#### 4.3.3 启动所有渠道（可选）

```bash
# 启动所有渠道（需要明确指定）
./manage.py start -a
```

#### 4.3.4 查看可用渠道

```bash
./manage.py start --channel ls
```

### 4.6 配置管理策略

#### 4.6.1 配置文件设计原则

1. **信息集中化**
   - 所有渠道配置集中在 `config.json`
   - 便于统一管理和版本控制

2. **按需启用**
   - `enabled` 字段表示该渠道是否可用
   - 不要求所有渠道都启动

3. **灵活扩展**
   - 可以添加新渠道配置
   - 不影响现有渠道

#### 4.6.2 配置文件维护

**添加新渠道：**
1. 编辑配置文件
2. 添加新渠道配置
3. 可以选择启动新渠道

**禁用渠道：**
1. 编辑配置文件
2. 设置 enabled 为 false
3. 停止已启动的渠道

## 五、渠道配置简化方案

### 5.1 方案背景

在实施过程中发现，原有的 `enabled` 字段设计存在以下问题：

1. **配置复杂**：需要手动设置 `enabled` 字段来控制渠道是否可用
2. **灵活性不足**：无法启动未启用的渠道，导致测试困难
3. **状态混乱**：配置文件中同时包含配置信息和运行状态
4. **用户困惑**：用户不理解为什么配置了渠道却无法启动

### 5.2 简化方案设计

#### 核心原则

1. **去除 enabled 字段**：配置文件只包含配置信息，不包含运行状态
2. **第一个渠道默认**：不指定渠道时，使用配置文件中的第一个渠道
3. **明确指定优先**：指定渠道时，启动指定的渠道
4. **配置纯粹化**：配置文件变成纯粹的"信息库"

#### 行为定义

**不指定渠道时：**
- 启动配置文件中的**第一个渠道**
- 按照配置文件中的顺序：先 `bots`，后 `simulator_channels`
- 第一个渠道通常是 `bot1`

**指定渠道时：**
- 启动指定的渠道
- 渠道必须在配置文件中存在
- 无论渠道在配置文件中的位置如何，都可以被启动

**查看可用渠道：**
```bash
./manage.py start --channel ls
```

**输出示例：**
```
配置文件中的所有渠道:
  渠道名                  类型         状态         tmux会话
  -----------------------------------------------------------------
  bot1                 📱企业微信      可用       bot1+iflow
  bot2                 📱企业微信      可用       bot2+iflow
  simulator1           🔧模拟器       可用       simulator1+iflow

默认渠道: bot1（第一个渠道）
```

### 5.3 对比表格

| 项目 | 修改前 | 修改后 |
|------|--------|--------|
| 配置文件 | 包含 enabled 字段 | 不包含 enabled 字段 |
| 默认行为 | 启动第一个 enabled=true 的渠道 | 启动第一个渠道 |
| 指定渠道 | 只能启动 enabled=true 的渠道 | 可以启动任何渠道 |
| 状态显示 | 显示"已启用/未启用" | 显示"可用" |
| 配置复杂度 | 较高（需要设置 enabled） | 较低（无需设置 enabled） |
| 使用灵活性 | 受限（受 enabled 限制） | 灵活（所有渠道可用） |
| 测试便利性 | 差（需要修改配置） | 好（直接启动） |

## 六、Tmux 会话管理功能

### 6.1 功能概述

为 manage.py 新增 tmux 会话管理功能，支持查看、进入和关闭 tmux 会话。

### 6.2 功能需求

| 功能 | 说明 |
|------|------|
| 查询 tmux 会话列表 | 列出所有 tmux 会话（包括项目相关和其他会话） |
| 关闭指定 tmux 会话 | 根据会话名关闭特定会话 |
| 关闭全部 tmux 会话 | 一次性关闭所有或所有项目相关会话 |
| 进入 tmux 界面 | 附加到指定会话进行交互 |
| 查看会话内容 | 只读查看会话输出 |

### 6.3 命令设计

| 命令 | 说明 |
|------|------|
| `./manage.py tmux list` | 列出所有 tmux 会话 |
| `./manage.py tmux status` | 查看项目相关会话状态 |
| `./manage.py tmux kill <会话名>` | 关闭指定会话 |
| `./manage.py tmux kill-all` | 关闭所有项目相关会话 |
| `./manage.py tmux kill-all --all` | 关闭所有 tmux 会话（危险！） |
| `./manage.py tmux attach <会话名>` | 进入 tmux 会话 |
| `./manage.py tmux view <会话名>` | 查看会话内容（只读） |

### 6.4 命令详解

#### tmux list

列出所有 tmux 会话，区分项目会话和其他会话。

| 参数 | 说明 |
|------|------|
| `--config, -c` | 配置文件路径（默认：config.json） |

#### tmux status

只显示项目相关的 tmux 会话状态。

#### tmux kill

关闭指定的 tmux 会话。

| 参数 | 说明 |
|------|------|
| `session_name` | 会话名（必填） |
| `--force, -f` | 强制关闭（先发送 Ctrl+C） |

#### tmux kill-all

关闭所有项目相关或全部 tmux 会话。

| 参数 | 说明 |
|------|------|
| `--config, -c` | 配置文件路径（默认：config.json） |
| `--all, -a` | 关闭所有会话（包括非项目会话） |
| `--force, -f` | 强制关闭 |

#### tmux attach

附加到指定的 tmux 会话进行交互。

| 参数 | 说明 |
|------|------|
| `session_name` | 会话名（必填） |

**退出方式：**
- 按 `Ctrl+B` 然后按 `D` 退出会话（会话继续运行）
- 按 `Ctrl+B` 然后按 `[` 进入复制模式，按 `q` 退出

#### tmux view

只读查看 tmux 会话内容（不进入会话）。

| 参数 | 说明 |
|------|------|
| `session_name` | 会话名（必填） |
| `--lines, -n` | 显示行数（默认：50） |

### 6.5 会话命名规则

根据渠道架构简化方案，tmux 会话名使用命名规则：

| 渠道类型 | 会话名格式 | 示例 |
|----------|------------|------|
| 飞书渠道 | `{name}+iflow` | feishu1+iflow |
| 企业微信渠道 | `{name}+iflow` | wecom1+iflow |
| 模拟器渠道 | `{name}+iflow` | simulator1+iflow |

### 6.6 安全考虑

| 考虑 | 说明 |
|------|------|
| kill-all --all 需要确认 | 关闭所有 tmux 会话前需要用户确认 |
| 强制关闭提示 | 使用 `-f` 参数时会先发送 Ctrl+C 信号 |
| 会话不存在提示 | 操作不存在的会话时给出友好提示 |
