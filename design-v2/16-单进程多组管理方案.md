# 单进程多组管理方案

## 一、方案概述

### 1.1 核心理念

**按需实例化，集中管理，默认启动，按需扩展**

在单个进程中统一管理所有组，通过消息总线实现模块间通信，通过模块管理器实现组的动态启停和状态监控。默认只启动组1，其他组按需实例化。

### 1.2 设计目标

- **资源优化**：只启动需要的组，节省系统资源
- **启动快速**：默认只启动组1，提高启动速度
- **按需扩展**：需要时才创建和启动其他组
- **集中控制**：通过组1统一控制其他组
- **状态一致**：状态集中存储和管理，查询快速准确
- **故障隔离**：组之间相互隔离，一个组的故障不影响其他组
- **开发友好**：支持快速重启组测试新代码

### 2.2 层次结构

| 层级 | 职责 | 组件 |
|------|------|------|
| **管理层** | 管理模块和组的生命周期、状态和控制 | 模块管理器 |
| **通信层** | 处理模块间消息传递 | 消息总线 |
| **业务层** | 实现具体业务功能 | WeChat、IFlow、Simulator、Command 模块 |

### 2.3 模块管理器的职责

| 职责 | 说明 |
|------|------|
| **组生命周期管理** | 管理组的启动、停止、重启 |
| **按需实例化** | 根据需要创建和销毁模块 |
| **状态存储** | 存储所有模块和组的当前状态 |
| **状态更新** | 通过回调机制实时更新状态 |
| **控制接口** | 提供组的控制命令接口 |
| **健康监控** | 定期检查模块健康状态 |
| **自动恢复** | 检测到异常时自动恢复 |

## 三、启动策略

### 3.1 默认启动流程

**步骤**：
1. 服务启动
2. 加载配置文件
3. 创建消息总线
4. 创建模块管理器
5. 创建组1的模块（但不启动）
   - 创建 WeChat1 模块
   - 创建 IFlow1 模块
   - 创建 CommandHandler 模块
6. 设置组1的绑定关系
7. 定义组1
8. 注册其他组的定义（但不创建模块）
   - 注册组2定义
   - 注册组_simulator 定义
9. 启动组1
10. 启动健康监控
11. 启动管理接口（Unix Socket）
12. 进入运行状态

**特点**：
- 组1的模块在启动时创建
- 其他组的模块只在需要时创建
- 所有组的定义都注册到管理器
- 健康监控持续运行

### 3.2 按需启动流程

**步骤**：
1. 接收启动组命令（如启动组2）
2. 检查组2是否已创建
3. 如果未创建，创建组2的模块
   - 创建 WeChat2 模块
   - 创建 IFlow2 模块
   - 设置绑定关系
4. 启动组2
5. 更新状态
6. 返回结果

**特点**：
- 延迟实例化
- 首次使用时才创建
- 避免资源浪费
- 创建后可重复启停

### 3.3 组销毁流程

**步骤**：
1. 接收停止组命令
2. 检查组是否在运行
3. 停止组的所有模块
4. 清理资源
5. 更新状态
6. 返回结果

**可选**：
- 是否保留模块实例（用于快速重启）
- 是否完全销毁模块实例（释放资源）

## 四、控制机制

### 4.1 控制路径

```
用户命令 → 组1的CommandHandler → 模块管理器 → 目标组
```

### 4.2 控制命令

**通过企业微信/命令行**：
- 启动组：`/start-group g2`
- 停止组：`/stop-group g2`
- 重启组：`/restart-group g2`
- 查看状态：`/group-status g2`
- 查看所有组：`/group-list`

**通过管理工具**：
- 启动组：`./manage.py group-start g2`
- 停止组：`./manage.py group-stop g2`
- 重启组：`./manage.py group-restart g2`
- 查看状态：`./manage.py group-status g2`
- 查看所有组：`./manage.py group-list`

### 4.3 管理接口

**Unix Socket 接口**：
- 路径：`/tmp/ling-iflow.sock`
- 协议：简单的命令-响应模式
- 安全性：只有本机可以访问
- 用途：外部管理工具控制

**命令格式**：
```
start <group_name>
stop <group_name>
restart <group_name>
status <group_name>
list
```

## 五、状态管理

### 5.1 状态存储机制

**存储位置**：模块管理器内部的数据结构

**存储内容**：
- 模块状态
  - 运行状态：运行中/已停止
  - 健康状态：健康/不健康
  - 性能指标：启动时间、处理时间、消息数量
  - 错误信息：最近一次错误
- 组状态
  - 组内所有模块的状态汇总
  - 组的运行状态
  - 组的健康状态
- 状态历史
  - 状态变化记录
  - 时间戳
  - 变更原因

### 5.2 状态更新机制

**更新方式**：
1. 模块状态变化时，通过回调通知管理器
2. 管理器更新内部状态存储
3. 管理器触发状态变更通知
4. 记录状态历史

**触发场景**：
- 模块启动/停止
- 健康检查结果变化
- 错误发生/恢复
- 性能指标更新

### 5.3 状态查询机制

**查询流程**：
1. 接收状态查询请求
2. 从管理器的状态存储中读取
3. 返回缓存的状态
4. 不需要向模块发起实时查询

**优势**：
- 响应速度快（微秒级）
- 不影响模块运行
- 状态一致性好
- 减少模块负担

## 六、工作流程

### 6.1 日常运行流程

```
1. 服务启动
   ↓
2. 只启动组1
   ↓
3. 组1提供正常服务
   ↓
4. 健康监控持续运行
   ↓
5. 状态持续更新
   ↓
6. 用户通过组1使用服务
```

### 6.2 测试新代码流程

```
1. 组1正常运行中
   ↓
2. 用户通过组1发送命令：/start-group g2
   ↓
3. 组2按需实例化并启动
   ↓
4. 用户修改代码
   ↓
5. 用户通过组1发送命令：/restart-group g2
   ↓
6. 组2重启并加载新代码
   ↓
7. 用户测试组2
   ↓
8. 测试通过后，用户通过组1发送命令：/restart-group g1
   ↓
9. 组1重启并加载新代码
   ↓
10. 用户通过组1发送命令：/stop-group g2
   ↓
11. 组2停止（可选）
```

### 6.3 状态查询流程

```
1. 用户发送命令：/group-status g2
   ↓
2. CommandHandler 解析命令
   ↓
3. 调用模块管理器的状态查询接口
   ↓
4. 管理器从状态存储中读取
   ↓
5. 返回状态给用户
   ↓
6. 整个过程不向组2发起实时查询
```

### 6.4 异常恢复流程

```
1. 健康监控检测到模块异常
   ↓
2. 记录异常状态
   ↓
3. 触发自动恢复
   ↓
4. 尝试重启模块
   ↓
5. 检查恢复结果
   ↓
6. 如果成功，更新状态为健康
   ↓
7. 如果失败，增加失败计数
   ↓
8. 如果达到最大失败次数，停止尝试并告警
```

## 七、配置结构

### 7.1 组定义

**配置文件示例**：
```json
{
  "groups": {
    "g1": {
      "modules": ["wechat_bot1", "iflow_iflow1"],
      "default": true,
      "auto_start": true,
      "description": "默认组，提供企业微信服务"
    },
    "g2": {
      "modules": ["wechat_bot2", "iflow_iflow2"],
      "default": false,
      "auto_start": false,
      "description": "测试组，用于测试新功能"
    },
    "g_simulator": {
      "modules": ["simulator_simulator1", "iflow_iflow1"],
      "default": false,
      "auto_start": false,
      "description": "模拟器组，用于开发和测试"
    }
  }
}
```

**配置说明**：
- `modules`：组包含的模块 ID 列表
- `default`：是否为默认组（只有组1为 true）
- `auto_start`：是否自动启动（只有组1为 true）
- `description`：组的描述信息

### 7.2 模块配置

**每个组的模块配置独立**：
- 组1的 WeChat 模块配置（端口 8787）
- 组1的 IFlow 模块配置（tmux 会话 iflow）
- 组2的 WeChat 模块配置（端口 8788）
- 组2的 IFlow 模块配置（tmux 会话 iflow2）

## 十、关键设计决策

### 决策 1：为什么默认只启动组1？

**原因**：
- 大部分情况下只需要一个组提供服务
- 减少资源消耗（内存、CPU）
- 提高启动速度
- 简化默认配置
- 降低故障面

**影响**：
- 启动更快
- 资源占用更少
- 需要时可以快速启动其他组

### 决策 2：为什么状态要存储而不是实时查询？

**原因**：
- 避免频繁查询影响模块性能
- 状态已经通过回调自动更新，准确性高
- 查询响应更快（微秒级 vs 毫秒级）
- 减少模块负担，让模块专注于业务
- 状态一致性好，避免并发问题

**影响**：
- 状态查询更快
- 模块运行更流畅
- 状态一致性更好

### 决策 3：为什么通过组1控制其他组？

**原因**：
- 组1始终运行，随时可用
- 统一的控制入口，用户不需要切换
- 简化使用流程，降低学习成本
- 利用现有的命令处理机制
- 便于权限管理

**影响**：
- 使用更简单
- 控制更统一
- 扩展更容易

### 决策 4：为什么使用 Unix Socket 而不是 HTTP？

**原因**：
- 性能更好（本地通信开销小）
- 安全性更高（只能本机访问）
- 实现更简单
- 不需要额外的网络端口
- 避免网络攻击风险

**影响**：
- 性能更好
- 安全性更高
- 实现更简单

## 十二、总结

本方案提供了一个完整的单进程多组管理解决方案，具有以下特点：

1. **按需实例化**：只创建需要的模块，节省资源
2. **集中管理**：统一的状态管理和控制接口
3. **默认启动**：只启动组1，提高启动速度
4. **按需扩展**：需要时才启动其他组
5. **状态存储**：状态集中管理，查询快速准确
6. **故障隔离**：组之间相互隔离，提高稳定性

这个方案既保持了原有的架构优势，又增强了动态管理能力，能够满足测试新代码、快速迭代等需求，同时提供了更好的资源利用和用户体验。
