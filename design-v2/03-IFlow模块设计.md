# IFlow 模块设计文档

## 概述

### 设计理念

**模块实例与 tmux/iflow 生命周期同步**

- 创建 IFlowModule 实例 → 自动创建对应的 tmux 会话并启动 iflow
- 销毁 IFlowModule 实例 → 自动停止 iflow 并销毁 tmux 会话

### 核心职责

| 职责 | 说明 |
|------|------|
| 生命周期管理 | 模块实例与 tmux/iflow 同步启动/停止 |
| 进程管理 | 通过 tmux 启动、停止、重启 iflow CLI |
| 状态管理 | 检测 iflow 空闲/生成中状态，生成中时拒绝新消息 |
| 消息注入 | 将消息发送到 iflow 进行处理 |
| 输出监控 | 持续监听 iflow 的 tmux 输出，提取回复 |
| 消息分类 | 按 ✦ 标记分类消息（回复/其他） |
| 消息归属 | 记录消息来源，回复时指定接收方 |
| 交互记录 | 完整记录所有交互信息 |
| 订阅通知 | 通过订阅机制通知关注方 |

## 模块组成

### 1. IFlowController - 进程管理层

#### 职责

管理 tmux 会话和 iflow 进程，实现完整的生命周期管理。

#### 核心功能

| 功能 | 说明 |
|------|------|
| 启动 iflow | 创建 tmux 会话并启动 iflow CLI |
| 停止 iflow | 停止 iflow 进程 |
| 发送消息 | 通过 tmux send-keys 将消息注入到 iflow |
| 捕获输出 | 读取 tmux pane 内容 |
| 检查状态 | 检查 iflow 是否运行/就绪 |
| 销毁会话 | 销毁 tmux 会话 |

#### 发送消息流程

1. **就绪检查** - 发送前先检查 iflow 是否真正准备好接受输入
2. **清除输入框** - 发送 C-c 清除当前输入框（等待 0.2 秒）
3. **发送内容** - 发送消息内容（等待 1.0 秒）
4. **确认发送** - 发送回车键

#### 就绪检查原则

**为什么要检查就绪状态？**

- tmux 会话存在 ≠ iflow 真正可用
- iflow 可能处于启动过程中的过渡状态
- 需要确保输入框真正可用

**就绪检查要素**：

1. tmux 会话存在
2. UI 已就绪（检测到输入框、欢迎消息、版本号）
3. 不在"生成中"状态
4. 输入框可用

#### 会话名称管理

- **延迟分配原则**：会话名称在首次启动时才分配，而非构造时
- **自动命名**：如果未指定会话名称，自动生成（如 iflow1, iflow2）
- **冲突避免**：分配前检查已存在的会话，自动选择未使用的序号

### 2. IFlowMonitor - 消息同步层

#### 职责

监控 iflow 输出并提取消息，实现消息同步。

#### 状态定义

| 状态 | 说明 | 可接受新消息 |
|------|------|-------------|
| **空闲** (IDLE) | iflow 等待输入 | ✅ 是 |
| **生成中** (GENERATING) | iflow 正在处理/生成回复 | ❌ 否 |

#### 状态检测原则

**检测依据**：iflow 状态指示器（位于界面底部状态栏）

- **"生成中"** - 正在生成回复（**唯一判断标准**）
- **"按esc取消"** - 可取消操作
- **时间指示器** - 如 `6m 37s`

**检测规则**：

1. 查找包含"生成中"的行
2. 必须包含状态指示器特征（"按esc取消"或时间格式）
3. 排除"上下文剩余"等无关行

**时间格式正则**：`\d+[ms]\s*\d+s`

#### 初始化保护机制

**问题**：模块启动后 3 秒内，iflow 可能处于初始化状态，状态检测可能不准确

**解决方案**：启动后 3 秒内跳过所有状态检测和消息提取

#### 双模式监控策略

| 模式 | 触发条件 | 提取行数 | 检测频率 |
|------|---------|---------|---------|
| 轻量级 | IDLE 状态 | **20 行** | 0.5 秒 |
| 完整 | GENERATING 状态 | 1000 行 | 0.5 秒 |

**性能提升**：IDLE 状态下性能提升 50 倍

#### 消息分类

| 标记 | 类型 | 说明 |
|------|------|------|
| `✦` | 回复 | 正式回复内容 |
| `✻` | 思考 | 思考过程内容 |

#### TUI 界面过滤原则

**目的**：过滤掉 iflow 的 TUI 界面元素，只保留实际消息内容

**TUI 界面特征**：

- 包含 "生成中"
- 包含 "思考:"
- 包含 "上下文剩余"
- 是分隔符（---, ══, ────）

**判断逻辑**：如果行包含消息标记（✦ 或 ✻），则不是 TUI 界面行

#### 消息提取策略

1. **提取用户消息**：找到以 `>` 开头的行，作为消息分割点
2. **跳过 TUI 行**：过滤掉界面元素
3. **识别标记行**：检测 ✦ 和 ✻ 标记
4. **收集延续内容**：收集标记行后的缩进内容（消息延续）

### 3. SessionManager - 会话管理器

#### 职责

管理 iflow 的会话文件，提供会话查询、创建等功能。

#### 核心功能

| 功能 | 说明 |
|------|------|
| 获取最新会话 | 获取最新的 session 文件路径 |
| 获取所有会话 | 获取 session 文件列表 |
| 创建新会话 | 清除上下文，创建新会话 |
| 删除会话 | 删除指定的 session 文件 |
| 获取会话信息 | 获取当前会话的详细信息 |

#### 会话目录组织

**目录结构**：`~/.iflow/projects/<项目路径>/`

- 按项目路径组织会话
- 每个项目有独立的会话目录

#### 会话文件命名

- 格式：`session-<session_id>.jsonl`
- 按修改时间排序，最新的在前

### 4. MessageStore - 消息库

#### 职责

记录消息来源、管理消息状态，提供消息匹配和缓冲能力。

#### 消息记录结构

| 字段 | 类型 | 说明 |
|------|------|------|
| message_id | str | 消息唯一标识 |
| source | str | 来源模块 ID（空表示无来源） |
| content | str | 消息内容 |
| scope | str | 返回范围（reply_only / all） |
| status | str | pending / processing / completed |
| created_at | datetime | 创建时间 |
| processing_at | datetime | 开始处理时间 |
| completed_at | datetime | 完成时间 |
| reply_count | int | 回复数量 |
| metadata | dict | 其他元数据（chat_id, user_id, is_group） |
| requires_buffering | bool | 是否需要缓冲回复 |
| buffered_replies | list | 缓冲的回复内容列表 |

#### 来源识别

| 来源 | 说明 |
|------|------|
| `wechat_bot1` | 企业微信机器人1 |
| `tool_xxx` | 运维工具 |
| `""` (空) | 无来源（用户在 iflow 直接输入） |

#### 消息匹配原则

**背景**：用户发送消息后，iflow 界面会显示发送的内容。我们需要从 tmux 输出中找到这条消息，来关联请求和回复。

**匹配策略**：

1. **短消息（≤20字符）**：精确匹配完整内容
2. **长消息（>20字符）**：匹配前 20 字符（前缀匹配）
3. **状态过滤**：只匹配 PROCESSING 状态的消息
4. **时间窗口**：5 分钟内创建的消息

**目的**：判断消息来源（有明确来源 vs 无来源），决定使用哪种发送模式

#### 来源差异化处理

**判断逻辑**：

```
收到用户消息
    ↓
记录到 MessageStore（包含 source 字段）
    ↓
iflow 返回内容
    ↓
Monitor 从 tmux 捕获发送的消息
    ↓
用捕获的内容去 MessageStore 匹配
    ↓
├─ 匹配到记录，且 source 非空 → 有明确来源
└─ 匹配到记录，但 source 为空 → 无明确来源
   └─ 匹配不到记录 → 无明确来源（用户直接在 iflow 输入）
```

### 5. InteractionLogger - 交互记录器

#### 职责

记录所有交互信息，持久化存储。

**重要**：交互记录中的**所有消息内容均从 tmux 读取**，而不是使用模块收到的原始内容。这样可以确保日志准确反映 tmux 中实际发生的内容。

#### 日志格式

**发送消息**：
```json
{
  "timestamp": "2024-03-15T10:30:00",
  "direction": "sent",
  "message_type": null,
  "content": "帮我写一个Python脚本",
  "module_id": "iflow_iflow1"
}
```

**接收消息**：
```json
{
  "timestamp": "2024-03-15T10:30:05",
  "direction": "received",
  "message_type": "reply",
  "content": "好的，这是脚本...",
  "module_id": "iflow_iflow1"
}
```

#### 字段说明

| 字段 | 说明 |
|------|------|
| timestamp | ISO 格式时间戳 |
| direction | 方向：`sent`（发送）或 `received`（接收） |
| message_type | 消息类型：`reply`（回复）、`thought`（思考）或 `null`（原始消息） |
| content | 消息内容 |
| module_id | 模块标识 |

#### 日志存储策略

**双模式存储**：

| 模式 | 触发时机 | 文件格式 | 说明 |
|------|---------|---------|------|
| 追加模式 | 每次交互完成 | JSONL（每行一个 JSON） | 持续记录，不丢失历史 |
| 覆盖模式 | 模块停止 | 完整 JSON | 保留完整会话快照 |

**日志目录**：`logs/interactions/`

---

### 6. IFlowModule - 消息交互层

#### 职责

与消息总线交互，管理消息流转，协调各组件工作。

#### 消息处理流程

**入站流程（外部 → iflow）**：

```
收到消息
    ↓
解析消息体，提取 source、content、scope
    ↓
检查 iflow 状态
    ↓
├─ iflow 生成中 → 返回拒绝响应
└─ iflow 空闲
   ├─ 记录到消息库（status=processing）
   ├─ 记录发送日志（从 tmux 捕获实际发送内容）
   └─ 发送给 iflow
```

**出站流程（iflow → 外部）**：

```
监控捕获 iflow 输出
    ↓
提取消息，分类（回复 / 思考）
    ↓
判断发送模式（流式 / 缓冲）
    ↓
├─ 流式模式：立即发送
└─ 缓冲模式：积累消息，等待生成结束
    ↓
完整记录到交互日志
    ↓
查询消息库，获取当前处理的消息来源
    ↓
构造输出消息
    ↓
发送到消息总线
    ↓
通知订阅者
```

## 状态管理

### 生成中拒绝机制

```
收到新消息请求
    ↓
检查 iflow 状态
    ↓
├─ 状态 = 生成中 → 返回拒绝响应
└─ 状态 = 空闲 → 正常处理消息
```

### 状态检测顺序

```
IFlowMonitor 监控状态
    ↓
├─ 检测到 "生成中" 关键字
│  ├─ 状态：IDLE → GENERATING
│  ├─ 记录生成开始时间
│  └─ 触发状态变更回调
└─ iflow 正在生成
   └─ "生成中" 不再显示
      ├─ 等待稳定 3 次扫描
      ├─ 状态：GENERATING → IDLE
      ├─ 记录生成持续时间
      ├─ 触发状态变更回调
      └─ 生成结束处理
         ├─ 查询消息库 processing 状态记录
         ├─ 构造 COMPLETE 消息
         ├─ 通知订阅者
         └─ 更新状态为 completed
```

### 连续检测原则

**问题**：状态检测可能因界面闪烁而误判

**解决方案**：连续 3 次扫描都检测不到 "生成中" 才确认生成结束

## 消息处理

### 消息分类

| 标记 | 类型 | 说明 |
|------|------|------|
| `✦` | 回复 | 正式回复内容 |
| `✻` | 思考 | 思考过程内容 |
| 其他 | 其他 | 其他输出 |

### 回复模式（reply_mode）

**控制发送行为**，与消息记录分离。

| 模式 | 说明 | 发送内容 |
|------|------|---------|
| `reply_only` | 仅回复（默认） | ✦ 标记的消息 |
| `all_messages` | 全部 | ✦ + ✻ + 其他所有消息 |

**设计原则**：

- `reply_mode` 是**全局设置**，由用户通过 `/scope` 命令控制
- `scope` 是**消息级别属性**，用于记录消息的来源范围
- Monitor 记录所有消息，不关心 reply_mode
- IFlowModule 根据 reply_mode 决定是否发送

### 记录原则

**所有消息都完整记录**：

- ✦ 回复消息 → 记录
- ✻ 思考消息 → 记录
- 其他输出 → 记录
- 记录位置：InteractionLogger + MessageStore
- 记录时机：不受 reply_mode 影响

### 延迟记录原则

**目的**：保证记录的消息是完整的，不会记录中间版本

**规则**：

- 消息1出现：不记录（可能不完整）
- 消息2出现：记录消息1（此时消息1已完整）
- 消息3出现：记录消息2（此时消息2已完整）

**实现**：只有 2 条或更多消息时才开始记录；最后一条消息在生成结束时记录

### 消息去重

**双重去重机制**：

| 策略 | 说明 | 优势 |
|------|------|------|
| 字符串定位（优先） | 使用标记行字符串作为唯一标识 | 快速、准确 |
| 哈希定位（备用） | 使用内容哈希精确匹配 | 准确区分内容相同但标记不同的消息 |

**定位流程**：

1. 首先尝试使用标记行字符串定位
2. 如果找到匹配的字符串，认为是同一条消息
3. 如果找不到匹配的字符串，计算内容哈希，再次定位
4. 如果仍然找不到，认为是新消息

### 消息归属原则

1. 每次对话都有唯一的 message_id
2. 回复时使用请求时的 source 作为 receiver
3. 支持多轮对话，每次对话独立归属

## 消息来源差异化处理

### 两种发送模式

| 模式 | 触发条件 | 发送行为 |
|------|---------|---------|
| **流式模式** (STREAM_MODE) | 有明确来源的消息 | 逐条立即发送 |
| **缓冲模式** (BUFFER_MODE) | 无明确来源的消息 | 积累消息，生成结束后整合发送 |

### 设计背景

**问题**：用户在 iflow 中直接输入消息时，这些消息没有外部来源标识。如果按流式模式逐条发送，可能导致消息格式混乱。

**解决方案**：

- 有明确来源：流式发送，保持实时性
- 无明确来源：缓冲发送，整合后以清晰格式发送

### 缓冲模式消息格式

**无来源消息**：

```
未知来源消息回复结束！
原请求消息内容是：<原始消息>
回复内容如下：

回复 1/2：

```...回复内容...```

回复 2/2：

```...回复内容...```
```

## 完整消息链路

### 概述

一次完整的消息处理流程，从用户发送消息开始，到 iflow 完成回复并结束。

### 场景设定

用户通过企业微信发送一条消息："帮我写一个 Python 脚本"，配置为 reply_only 模式。

### 完整流程

#### 阶段 1：消息接收与注入

1. **用户发送消息** - 用户在企业微信中输入消息，消息通过企业微信 API 回调到 WeChatChannel
2. **消息路由** - WeChatChannel 调用 send_to_bus()，MessageBus 将消息路由到 IFlowModule
3. **消息预处理** - IFlowModule 检查当前状态，如果是 GENERATING 则拒绝消息
4. **记录消息** - IFlowModule 调用 MessageStore 记录入站消息
5. **消息注入** - IFlowModule 通过 tmux send-keys 将消息注入到 iflow CLI
6. **日志记录** - IFlowModule 从 tmux 捕获实际发送的消息，记录到 InteractionLogger

#### 阶段 2：状态变更与生成中检测

7. **生成中状态检测** - IFlowMonitor 检测到 "生成中" 关键字，状态从 IDLE 切换到 GENERATING
8. **通知状态变更** - IFlowMonitor 发布状态变更通知，ModuleManager 更新模块状态

#### 阶段 3：消息记录与发送（GENERATING 状态）

9. **提取消息** - IFlowMonitor 进入完整提取模式，提取 tmux 输出最后 1000 行
10. **延迟记录原则** - 只记录到第二条消息出现后才发送第一条
11. **来源匹配** - Monitor 从 tmux 捕获发送消息，与 MessageStore 匹配，判断来源
12. **发送模式选择** - 根据来源选择流式或缓冲模式
13. **scope 过滤** - 根据 reply_mode 过滤消息，✻ 标记的消息被过滤

#### 阶段 4：结束检测与最后消息处理

14. **生成中消失检测** - "生成中" 从 tmux 输出中消失
15. **连续检测（3次扫描）** - 确认 "生成中" 真的结束了
16. **记录并发送最后一条消息** - 发送最后一条 ✦ 标记的消息
17. **刷新缓冲区** - 如果是缓冲模式，发送所有缓冲消息

#### 阶段 5：消息记录完成

18. **状态变更** - 状态从 GENERATING 切换到 IDLE
19. **完成通知** - 发送 COMPLETE 消息，通知订阅者
20. **更新状态** - MessageStore 更新消息状态为 completed
21. **保存日志** - InteractionLogger 保存本次交互记录

## 故障排查

### 问题 1：iflow 启动失败

**可能原因**：

1. tmux 未安装
2. iflow CLI 未安装或未登录
3. 网络问题
4. 配置文件错误

**解决方案**：

```bash
# 检查 tmux
tmux -V

# 检查 iflow
iflow --version

# 测试 iflow 手动启动
tmux new-session -s test 'iflow --model kimi-k2.5'
```

### 问题 2：消息发送失败

**可能原因**：

1. iflow 未启动
2. tmux 会话已销毁
3. 状态检测错误

**解决方案**：

```bash
# 检查 tmux 会话
tmux ls

# 检查 iflow 进程
ps aux | grep iflow

# 重新启动
python tools/iflow_interactive_tool.py --clean
```

### 问题 3：消息重复显示

**可能原因**：

1. 钩子和消息总线双重调用
2. 去重机制失效

**解决方案**：检查去重机制是否正常工作

### 问题 4：状态检测错误

**可能原因**：

1. 状态检测误判
2. 用户消息包含"生成中"

**解决方案**：使用正则表达式精确匹配

### 问题 5：性能问题

**可能原因**：

1. 提取行数过多
2. 处理频率过高

**解决方案**：使用双模式监控

### 问题 6：会话保持失败

**可能原因**：

1. 第一次执行使用了 `--cleanup`
2. tmux 会话被外部销毁
3. iflow 进程异常退出

## 总结

### 核心特性

1. **自动化生命周期**：模块与 tmux/iflow 完全同步
2. **完整记录**：所有消息都记录，不丢失任何信息
3. **灵活过滤**：reply_mode 参数控制发送内容
4. **状态管理**：生成中时拒绝新消息
5. **消息归属**：记录消息来源，支持多轮对话
6. **订阅机制**：通过订阅通知关注方
7. **性能优化**：双模式监控，性能提升 50 倍
8. **延迟记录**：保证消息完整性
9. **双重去重**：字符串定位 + 哈希定位
10. **来源差异化**：流式/缓冲双模式处理

### 设计原则总结

| 原则 | 说明 |
|------|------|
| 就绪检查原则 | 发送消息前必须确认 iflow 真正可用 |
| 延迟记录原则 | 只有消息完整后才记录，避免中间版本 |
| 双重去重原则 | 字符串定位为主，哈希定位为辅 |
| 来源差异化原则 | 有来源用流式，无来源用缓冲 |
| 连续检测原则 | 3 次扫描确认状态变化，避免误判 |
| 初始化保护原则 | 启动后 3 秒内跳过检测 |
| 日志一致性原则 | 从 tmux 捕获实际内容，不使用原始消息 |
