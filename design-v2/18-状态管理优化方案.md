# 状态管理优化方案

## 概述

本方案优化 ModuleManager 的状态管理功能，解决当前双重监控、状态不准确、恢复机制混乱等问题，确保系统能准确检测模块异常并及时恢复。

---

## 背景问题

当前状态管理存在以下问题：

### 1. 双重监控，不协调
- IFlowModule 有自己的监控任务，每 60 秒检查一次
- ModuleManager 也有健康监控，每 30 秒检查一次
- 两者独立运行，没有信息共享，可能导致冲突

### 2. 健康检查不准确
- ModuleManager 的健康检查依赖模块的 `health_check()` 方法
- 但 IFlowModule 没有实现这个方法
- 默认返回"健康"，实际可能 tmux/iflow 已崩溃

### 3. 状态上报不完整
- IFlowModule 只在状态变化时（idle/generating）通知 ModuleManager
- 崩溃、未运行等异常状态没有上报机制
- ModuleManager 无法感知真实状态

### 4. 恢复机制混乱
- IFlowModule 内部有自动重启逻辑
- ModuleManager 也有自动恢复机制
- 可能同时尝试恢复，产生冲突

### 5. 其他模块缺失监控
- WeChatChannel、SimulatorChannel 等没有健康检查
- 这些模块异常时无法被检测和恢复

---

## 关键问题场景

### 场景 1：tmux/iflow 崩溃
- IFlowModule 的监控任务会检测到并尝试重启
- ModuleManager 的健康检查认为模块健康（因为默认返回 true）
- 用户发送消息时，ModuleManager 认为接收方可用，实际 iflow 未运行
- 用户只收到"正在处理中..."，没有后续回复

### 场景 2：WeChatChannel 崩溃
- 完全没有健康检查机制
- ModuleManager 认为模块健康
- 无法自动恢复，需要手动重启

---

## 优化方案

### 核心原则

1. **统一健康检查接口**
   - 所有模块必须实现健康检查方法
   - 返回真实的健康状态和详细信息

2. **集中式监控管理**
   - 移除模块内部监控任务
   - ModuleManager 统一负责健康监控和恢复
   - 避免双重监控和冲突

3. **状态实时上报**
   - 模块检测到异常时主动通知 ModuleManager
   - ModuleManager 健康检查作为后备机制
   - 确保状态准确性

4. **分级恢复策略**
   - 轻度异常：模块自行处理（如 token 刷新）
   - 严重异常：ModuleManager 强制重启
   - 多次失败：标记为不可用，停止自动恢复

---

## 优化内容

### 1. IFlowModule 实现真实健康检查

**检查项**：
- 模块是否运行
- tmux 会话是否存在
- iflow 进程是否运行
- iflow 是否就绪（可选，更严格）

**返回信息**：
- 健康状态（true/false）
- 不健康原因（tmux_session_not_found、iflow_not_running 等）
- 详细信息（tmux 会话名、当前状态等）

### 2. 移除 IFlowModule 内部监控任务

**改动**：
- 删除 `_monitor_task()` 方法
- 停止创建内部监控任务
- 依赖 ModuleManager 统一监控

**优势**：
- 避免双重监控
- 状态统一管理
- 减少代码复杂度

### 3. 修改 ModuleManager 健康检查

**改进点**：
- 对于没有实现健康检查的模块，检查运行状态作为后备
- 默认不再假设模块健康，而是基于实际状态
- 增强日志，记录健康检查详情

**处理逻辑**：
- 优先调用模块的 `health_check()` 方法
- 如果模块未实现，检查 `running` 属性
- 如果都没有，返回不健康（保守策略）

### 4. WeChatChannel 实现健康检查

**检查项**：
- 模块是否运行
- HTTP 客户端是否初始化
- access_token 是否过期（自动刷新）
- 回调服务是否运行（可选）

**自动恢复**：
- token 过期时自动刷新
- HTTP 客户端异常时尝试重新初始化

### 5. 增强自动恢复策略

**恢复流程**：
1. 停止模块
2. 等待配置的延迟时间
3. 重启模块
4. 检查恢复结果

**失败处理**：
- 记录失败次数
- 达到最大失败次数时停止自动恢复
- 标记模块为不可用状态
- 记录错误信息

**恢复成功**：
- 重置失败计数
- 更新模块状态为健康
- 记录恢复日志

### 6. 优化状态变更通知

**通知内容**：
- 模块 ID
- 新状态（healthy/unhealthy）
- 详细信息（原因、错误详情等）

**调用时机**：
- 健康检查发现状态变化时
- 自动恢复成功/失败时
- 模块主动上报异常时

**回调机制**：
- 支持多个状态回调函数
- 同时调用所有回调
- 捕获回调异常，不影响主流程

---

## 优化后的优势

### 1. 状态准确
- 基于真实的健康检查结果
- 不再依赖假设或默认值
- 用户发送消息时能准确判断接收方状态

### 2. 及时恢复
- 检测到异常立即尝试恢复
- 减少服务中断时间
- 提高系统可用性

### 3. 避免冲突
- 移除模块内部监控
- ModuleManager 统一管理
- 恢复过程可控

### 4. 易于扩展
- 其他模块可以轻松实现健康检查
- 统一的接口和流程
- 便于维护和调试

### 5. 用户体验
- 用户能立即收到明确的错误通知
- 不再出现"正在处理中..."后没有回复的情况
- 异常自动恢复，减少人工干预

## Status 命令优化

### 问题背景

原始的 `/status` 命令会显示所有配置的模块，包括：
- 未启动的 bot
- 未创建的 tmux 会话
- 已停止的模块

这导致用户看到很多不相关的信息，影响用户体验。

### 优化方案

**优化目标：**
- 只显示已启动的模块（running=True）
- 过滤未启动的 bot 和未创建的 tmux 会话
- 移除不必要的运行状态图标（因为只显示已启动的，总是 ✅）

**实现逻辑：**
```python
async def _cmd_status(self, args: str, chat_id: str) -> str:
    """状态命令 - 查看所有已启动模块的状态"""
    if not self.bus:
        return "❌ 消息总线未初始化"
    
    status_lines = ["**服务状态** 📊\n"]
    
    # 获取所有模块状态
    if self.manager:
        all_status = self.manager.get_all_status()
        
        if not all_status:
            status_lines.append("❌ 没有可用的模块")
            return "\n".join(status_lines)
        
        # 只显示已启动的模块
        started_modules = {
            module_id: status 
            for module_id, status in all_status.items()
            if status['running']
        }
        
        if not started_modules:
            status_lines.append("ℹ️ 当前没有启动的模块")
            return "\n".join(status_lines)
        
        # 按模块类型分组显示（只显示已启动的）
        # ... 其余逻辑不变
```

**关键改进：**
1. **过滤逻辑：**
   ```python
   started_modules = {
       module_id: status 
       for module_id, status in all_status.items()
       if status['running']
   }
   ```

2. **无启动模块提示：**
   ```python
   if not started_modules:
       status_lines.append("ℹ️ 当前没有启动的模块")
       return "\n".join(status_lines)
   ```

3. **移除运行状态图标：**
   ```python
   # 原来：
   running_icon = "✅" if status['running'] else "❌"
   status_lines.append(f"- {running_icon} {module_id}")
   
   # 现在：
   status_lines.append(f"- ✅ {module_id}")  # 只显示已启动的，所以总是 ✅
   ```

### 优化效果

**优化前：**
```
**服务状态** 📊

**IFlow 模块** 🤖
- ❌ iflow_bot1
  健康状态: ❌

**企业微信渠道** 💬
- ❌ wechat_bot1
  健康状态: ❌
```

**优化后：**
```
**服务状态** 📊

ℹ️ 当前没有启动的模块
```

**当有模块启动时：**
```
**服务状态** 📊

**IFlow 模块** 🤖
- ✅ iflow_bot1
  健康状态: ✅ [💤 空闲]
  启动时间: 2026-03-17 10:30:15
  启动耗时: 12.41s

**企业微信渠道** 💬
- ✅ wechat_bot1
  健康状态: ✅
  启动时间: 2026-03-17 10:30:00
```

### 用户体验提升

**清晰的反馈：**
- 用户能立即看到哪些模块正在运行
- 不会被无关的信息干扰
- 状态显示更简洁明了

**易于判断：**
- 只显示活跃的模块
- 避免显示"僵尸"模块
- 状态信息更准确

**更好的可读性：**
- 移除冗余的运行状态图标
- 界面更清爽
- 关键信息更突出
