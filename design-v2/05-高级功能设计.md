# 高级功能设计

## 一、方案概述

### 1.1 背景

Ling-iflow 项目提供了三个核心的高级功能，用于增强系统的可用性、可测试性和管理能力：

1. **命令系统**：提供统一的命令解析和执行机制，支持多种类型的命令（会话管理、状态查询、渠道管理等），易于扩展新的命令，支持命令透传（未知命令传递给 iflow 处理）。

2. **tmux 管理功能**：提供统一的 tmux 会话管理接口，通过命令行命令实现对 tmux 会话的管理，支持会话列表查询、创建、删除功能。

3. **消息模拟器**：提供通用的消息测试机制，使用 Socket 通信实现实时、高效的消息传输，不依赖具体的企业微信或其他社交渠道，用于测试 iflow 模块的核心功能。

### 1.2 核心目标

**命令系统目标：**
- 提供统一的命令解析和执行机制
- 支持多种类型的命令（会话管理、状态查询、渠道管理等）
- 易于扩展新的命令
- 支持命令透传（未知命令传递给 iflow 处理）
- 提供友好的帮助和错误提示

**tmux 管理功能目标：**
- 提供统一的 tmux 会话管理接口
- 通过命令行命令实现对 tmux 会话的管理
- 支持会话列表查询、创建、删除功能
- 提供友好的用户界面和错误提示

**消息模拟器目标：**
- 创建一个通用的消息模拟器渠道
- 配合独立的测试工具，用于测试 iflow 模块的核心功能
- 不依赖具体的企业微信或其他社交渠道
- 支持实时、高效的消息传输

### 1.3 设计原则

**单一职责原则**
- CommandHandler 只负责命令解析和执行
- SimulatorChannel 只负责 Socket 通信和消息转换
- 各功能模块独立，职责清晰

**职责清晰**
- 命令处理独立于具体业务模块
- 每个命令有明确的职责和功能
- 命令结果格式统一

**易于扩展**
- 支持动态注册自定义命令
- 提供清晰的命令注册接口
- 支持命令别名和参数
- 支持添加新的 tmux 操作
- 支持扩展 Socket 通信功能

**透传机制**
- 未知命令自动透传给 iflow 处理
- 保留 iflow 原生命令的完整性
- 避免命令冲突

**安全性优先**
- tmux 会话删除是危险操作，需要明确的用户确认
- Socket 通信支持认证和加密（未来扩展）
- 提供详细的警告信息
- 记录所有管理操作的日志

**/new - 开始新会话**

**功能：**

**使用方法：**

**实现逻辑：**
```python
async def _cmd_new(self, args: str, chat_id: str) -> str:
    """新建会话命令"""
    if not self.bus:
        return "❌ 消息总线未初始化"
    
    # 查找 iflow 模块并创建新会话
    for module_id, module in self.bus.modules.items():
        if module_id.startswith("iflow_") and hasattr(module, 'create_new_session'):
            result = module.create_new_session()
            if result.get("success"):
                return "✅ 已开始新会话，下次命令将从空白上下文开始"
            else:
                return f"❌ 创建新会话失败: {result.get('message', '未知错误')}"
    
    return "❌ 没有可用的 iflow 模块"
```

**返回结果：**
- 成功：`✅ 已开始新会话，下次命令将从空白上下文开始`
- 失败：`❌ 创建新会话失败: <错误信息>`
- 无模块：`❌ 没有可用的 iflow 模块`

### 2.3 命令解析和执行流程

#### 命令解析

**parse_command() 方法**
```python
def parse_command(self, content: str) -> Dict[str, Any]:
    """解析用户消息，提取命令
    
    Args:
        content: 用户发送的消息
        
    Returns:
        解析结果字典，格式：
        {
            "is_command": bool,
            "cmd_type": str,  # "command" or "message"
            "cmd_name": Optional[str],
            "cmd_args": Optional[str],
            "raw_content": str
        }
    """
    content = content.strip()
    
    # 检查是否为命令（以 / 开头）
    if content.startswith("/"):
        parts = content.split(maxsplit=1)
        cmd_name = parts[0].lower()
        cmd_args = parts[1] if len(parts) > 1 else ""
        
        return {
            "is_command": True,
            "cmd_type": "command",
            "cmd_name": cmd_name,
            "cmd_args": cmd_args,
            "raw_content": content
        }
    
    # 普通消息
    return {
        "is_command": False,
        "cmd_type": "message",
        "cmd_name": None,
        "cmd_args": content,
        "raw_content": content
    }
```

**解析规则：**
1. 以 `/` 开头的消息为命令
2. 命令名不区分大小写（自动转换为小写）
3. 命令和参数用空格分隔
4. 参数可以为空

**示例：**
- `/new` → 命令名：`/new`，参数：空
- `/status` → 命令名：`/status`，参数：空
- `/history iflow_bot1` → 命令名：`/history`，参数：`iflow_bot1`
- `/channel start bot1` → 命令名：`/channel`，参数：`start bot1`
- `你好` → 非命令，普通消息

#### 命令执行

**execute() 方法**
```python
async def execute(self, parsed: Dict[str, Any], chat_id: str = "") -> Optional[str]:
    """执行命令
    
    Args:
        parsed: 解析后的命令
        chat_id: 聊天 ID
        
    Returns:
        命令执行结果（回复消息），如果不是命令则返回 None
    """
    if not parsed.get("is_command"):
        return None
    
    cmd_name = parsed.get("cmd_name", "")
    cmd_args = parsed.get("cmd_args", "")
    
    # 检查命令是否存在
    if cmd_name in self._commands:
        try:
            result = await self._commands[cmd_name](cmd_args, chat_id)
            return result
        except Exception as e:
            logger.error(f"执行命令 {cmd_name} 失败: {e}", exc_info=True)
            return f"❌ 执行命令失败: {e}"
    
    # 未知命令：透传给 iflow 处理
    logger.info(f"未知命令，透传给 iflow: {cmd_name} {cmd_args}")
    return None
```

**执行流程：**
1. 检查是否为命令（`is_command`）
2. 检查命令是否已注册（`cmd_name in self._commands`）
3. 执行命令处理函数
4. 捕获异常并返回错误信息
5. 未知命令返回 `None`（透传给 iflow）

## 五、消息模拟器

### 4.1 概述

#### 背景

当前项目的测试依赖于 MockWeChatModule（模拟企业微信模块），这种方式存在以下问题：

1. 测试与特定渠道耦合，不易扩展
2. 添加新渠道需要修改测试代码
3. 测试工具与项目耦合，不够独立
4. 缺乏通用的消息测试机制

#### 目标

创建一个通用的消息模拟器渠道，配合独立的测试工具，用于测试 iflow 模块的核心功能，不依赖具体的企业微信或其他社交渠道。

#### 核心概念

**MessageSimulator（消息模拟器）**
- 作为项目的一个渠道模块
- 通用性强，不模拟任何特定渠道
- 通过 Socket 接收测试工具的消息
- 通过 Socket 发送 iflow 的回复给测试工具

**TestClientTool（测试客户端工具）**
- 独立的可执行程序
- 模拟用户发送消息，接收并显示 iflow 的回复
- 支持交互模式和命令行模式
- 完全独立于项目运行

### 4.2 架构设计

#### 目录结构

```
src/modules/
├── channel/           # 渠道目录
│   ├── __init__.py
│   ├── wechat.py      # WeChatChannel
│   └── simulator.py   # SimulatorChannel（新增）
├── common/            # 通用组件
│   ├── converter.py   # MessageConverter（复用）
│   └── notifications.py
├── command/           # 命令处理

└── wechat/            # 企业微信模块
    └── module.py      # WeChatModule

tools/
└── test_client.py     # 测试客户端工具（独立）
```

#### 整体架构

```

        ↓
   TCP 连接
        ↓
SimulatorChannel (服务端)
        ↓
    MessageBus
        ↓
   IFlowModule
```

#### 组件关系

**三个核心组件：**

1. **SimulatorChannel**
   - 位置：src/modules/channel/simulator.py
   - 类型：渠道（SimulatorChannel）
   - 角色：TCP 服务端
   - 功能：接收测试工具消息，发送 iflow 回复

2. **TestClientTool**
   - 位置：tools/test_client.py
   - 类型：独立可执行程序
   - 角色：TCP 客户端
   - 功能：模拟用户交互，发送消息，显示回复

3. **Socket 通信**
   - 协议：TCP
   - 格式：JSON + 长度前缀
   - 模式：长连接
   - 特性：实时、可靠、高效

#### 与现有架构集成

**集成方式：**
- SimulatorChannel 作为渠道放在 `src/modules/channel/` 目录
- 创建 SimulatorModule 使用 SimulatorChannel
- 作为普通模块注册到 MessageBus
- 使用标准的模块绑定机制与 IFlowModule 通信
- 复用 MessageConverter 进行消息转换
- 不需要修改 MessageBus 或 IFlowModule
- 不影响现有的 WeChatModule

**兼容性：**
- 可以与 WeChatModule 同时存在
- 通过配置选择使用哪个渠道
- 方便切换测试环境

**测试覆盖：**
- 单元测试：测试 SimulatorChannel 的核心功能
- 集成测试：测试完整的消息流转
- 替代现有的 MockWeChatModule 测试

### 4.3 Socket 通信协议

#### 消息格式

**消息结构：**
- 消息头：包含消息类型、消息 ID、时间戳
- 消息体：包含具体的数据内容
- 消息尾：包含校验信息（可选）

#### 消息类型

**1. 控制消息**

心跳消息：
```json
{
  "type": "heartbeat",
  "id": "hb_001",
  "timestamp": "2026-03-15T20:30:10Z"
}
```

握手消息（客户端 → 服务端）：
```json
{
  "type": "handshake",
  "id": "hs_001",
```

握手确认（服务端 → 客户端）：
```json
{
  "type": "handshake_ack",
  "id": "hs_ack_001",
  "timestamp": "2026-03-15T20:30:00Z",
  "server_version": "1.0.0",
  "server_id": "simulator_001"
}
```

关闭连接消息：
```json
{
  "type": "close",
  "id": "close_001",
  "timestamp": "2026-03-15T20:35:00Z",
  "reason": "user_requested"
}
```

**2. 用户消息**（客户端 → 服务端）

发送消息：
```json
{
  "type": "user_message",
```


**3. 回复消息**（服务端 → 客户端）

```json
{
  "type": "reply_message",
```

```json
  "metadata": {
    "request_id": "msg_001"
  }
}
```

#### 传输机制

**消息封装：**
1. 将消息序列化为 JSON 字符串
2. 计算消息字节数（使用 UTF-8 编码）
3. 将字节数转换为 4 字节的长度字段（网络字节序）
4. 将长度字段和消息内容组合

**接收流程：**
1. 读取 4 字节的长度字段
2. 将长度字段转换为整数
3. 根据长度读取完整消息
4. 解析 JSON 消息
5. 验证消息格式

**发送流程：**
1. 将消息对象序列化为 JSON
2. 计算 JSON 字节数
3. 将字节数转换为 4 字节的长度字段
4. 先发送长度字段
5. 再发送消息内容

#### 网络配置

**端口选择：**
- 默认端口：19999
- 支持端口冲突检测
- 支持自动选择可用端口

**连接参数：**
- 地址：localhost（默认）
- 端口：19999（默认）
- 超时时间：30 秒
- 心跳间隔：30 秒
- 最大连接数：10（可选）

### 4.4 SimulatorChannel 详细设计

#### 核心职责

1. 监听 TCP 端口，接受客户端连接
2. 管理多个客户端连接（可选）
3. 接收客户端发送的消息
4. 将消息转换为标准格式（使用 MessageConverter），发送到 MessageBus
5. 接收 MessageBus 返回的回复
6. 将回复通过 TCP 发送给对应的客户端
7. 处理连接的建立、维护和关闭

#### 模块组成

**1. Socket 服务端**
- 监听指定端口
- 接受新的连接
- 为每个连接创建独立的处理器
- 管理连接列表

**2. 连接处理器**
- 处理单个客户端的所有消息
- 解析接收到的消息
- 发送消息到 MessageBus
- 接收回复并发回客户端
- 处理心跳和超时

**3. 消息转换**
- 复用 MessageConverter 进行 Socket 消息与标准 Message 格式的转换
- 注册 simulator 的入站/出站转换器
- 统一的消息转换逻辑

**4. 连接管理器**
- 维护活跃连接列表
- 处理连接的建立和断开
- 处理连接超时和错误

#### 工作流程

**启动流程：**
1. 创建 TCP socket
2. 绑定到指定端口
3. 开始监听
4. 启动接受连接的后台任务
5. 记录服务端就绪状态

**接收消息流程：**
1. 连接处理器从 socket 读取数据
2. 读取 4 字节的消息长度
3. 根据长度读取完整消息
4. 解析 JSON 消息
5. 验证消息格式
6. 转换为 MessageBus 消息
7. 发送到 MessageBus

**发送回复流程：**
1. 从 MessageBus 接收回复
2. 转换为 Socket 消息格式
3. 序列化为 JSON
4. 计算消息长度
5. 写入长度字段（4 字节）
6. 写入消息内容
7. 确保发送成功

**关闭流程：**
1. 停止接受新连接
2. 关闭所有活跃连接
3. 通知所有客户端
4. 关闭服务端 socket
5. 清理资源

#### 状态管理

**服务端状态：**
- 未启动
- 监听中
- 已停止

**连接管理：**
- 活跃连接列表
- 连接 ID 映射
- 连接统计信息

**消息统计：**
- 发送消息数
- 接收消息数
- 错误消息数

**性能指标：**
- 当前连接数
- 消息吞吐量
- 平均响应时间

#### 错误处理

**连接错误：**
- 记录错误日志
- 关闭异常连接
- 通知相关客户端

**消息解析错误：**
- 发送错误通知
- 不关闭连接
- 记录错误日志

**发送失败：**
- 重试机制（最多 3 次）
- 超过次数后关闭连接
- 记录错误日志

**超时处理：**
- 心跳检测（每 30 秒）
- 超时自动关闭连接
- 通知客户端

### 4.9 与现有代码的关系

#### 与 MockWeChatModule 的关系

**替换关系：**
- SimulatorModule 可以替代 MockWeChatModule
- 提供更通用的测试能力
- 不模拟任何特定渠道

**区别：**
- MockWeChatModule：模拟企业微信，用于集成测试
- SimulatorModule：通用模拟器，用于功能测试
- 架构优势：SimulatorModule 与 WeChatModule 使用相同的架构模式

#### 与 WeChatModule 的关系

**架构一致性：**
- 两者使用相同的架构模式
- WeChatModule = WeChatChannel + 通用组件
- SimulatorModule = SimulatorChannel + 通用组件
- 都复用 MessageConverter

**并行关系：**
- 两者可以同时存在
- 通过配置选择使用哪个
- 互不影响

**互补关系：**
- WeChatModule：用于生产环境
- SimulatorModule：用于测试和开发

#### 与 MessageBus 的关系

**集成关系：**
- MessageSimulator 作为普通模块注册
- 使用标准的消息路由机制
- 不修改 MessageBus
