# 总体架构设计

## 重构目标

将 Ling-iflow 从紧耦合架构升级到基于消息总线的松耦合架构，实现：

- 三大核心模块独立（企业微信、消息总线、iflow）
- 模块间通过消息总线通信
- 支持动态绑定和扩展
- 保持旧版本功能完整

---

## 核心理念

基于**发布-订阅模式**和**消息总线**架构，实现模块解耦。

---

## 三大核心模块

### 1. 企业微信消息模块

**职责**：纯粹的企业微信 API 封装

- 接收企业微信消息（通过 HTTP 回调）
- 发送消息到企业微信（通过 API）
- 不处理业务逻辑，不依赖其他模块

**特点**：独立运行，只关注企业微信交互

---

### 2. 消息分发模块（消息总线）

**职责**：模块间消息路由和分发

- 管理所有模块的注册
- 维护机器人和 iflow 的绑定关系
- 根据绑定信息智能转发消息
- 支持消息广播机制

**特点**：解耦核心，不关心消息内容

---

### 3. iflow 消息模块

**职责**：iflow CLI 的完整管理

- 通过 tmux 启动和管理 iflow
- 持续监听 iflow 的输出
- 接收外部消息并注入到 iflow
- 广播 iflow 的所有回复

**特点**：独立管理 iflow，不关心消息来源

---

## 架构关系

```
消息分发模块（消息总线）
    ↓ 注册
企业微信模块 1 ←──────┐
企业微信模块 2 ←──────┤
iflow 模块 1   ←──────┤
iflow 模块 2   ←──────┘
```

**绑定关系**：
- 企业微信模块 1 ↔ iflow 模块 1
- 企业微信模块 2 ↔ iflow 模块 2

---

## 消息流向

### 企业微信 → iflow

1. 企业微信模块接收消息
2. 发送到消息总线
3. 总线根据绑定关系路由到对应 iflow 模块
4. iflow 模块注入到 iflow CLI

### iflow → 企业微信

1. iflow 模块监听到新回复
2. 广播到消息总线
3. 总线通知绑定的企业微信模块
4. 企业微信模块发送到企业微信

---

## 核心优势

### 解耦清晰
- 每个模块职责单一
- 模块间通过消息总线通信
- 不直接依赖

### 扩展性强
- 添加新机器人：注册新企业微信模块
- 添加新渠道：实现标准模块接口
- 添加新 iflow：注册新 iflow 模块

### 灵活性高
- 支持多对多绑定
- 支持动态绑定/解绑
- 支持消息广播

### 易于维护
- 模块独立开发测试
- 故障隔离
- 代码职责明确

## 模块标识与多实例机制

### 核心标识符

每个模块有两个关键标识：

| 标识符 | 用途 | 使用者 |
|--------|------|--------|
| `module_id` | MessageBus 区分不同模块 | 消息路由、绑定关系 |
| `tmux_session` | 标识要连接的 tmux 会话 | IFlowController |

### module_id 命名规范

建议采用 `<类型>_<名称>` 格式：

```
wechat_bot1    # 企业微信模块
wechat_bot2
iflow_bot1     # iflow 模块
iflow_bot2
```

### 多实例创建示例

```python
from src.core.bus import MessageBus
from src.modules.wechat.module import WeChatModule
from src.modules.iflow.module import IFlowModule

# 创建消息总线
bus = MessageBus()

# 创建两个独立的消息通道
# 通道1: 微信bot1 ↔ iflow1
wechat1 = WeChatModule(
    module_id="wechat_bot1",
    corp_id="xxx",
    agent_id="111",
    secret="xxx",
    callback_port=8787
)
iflow1 = IFlowModule(
    module_id="iflow_bot1",
    tmux_session="iflow1",
    model="kimi-k2.5"
)

# 通道2: 微信bot2 ↔ iflow2
wechat2 = WeChatModule(
    module_id="wechat_bot2",
    corp_id="yyy",
    agent_id="222",
    secret="yyy",
    callback_port=8788
)
iflow2 = IFlowModule(
    module_id="iflow_bot2",
    tmux_session="iflow2",
    model="kimi-k2.5"
)

# 注册所有模块
bus.register_module(wechat1)
bus.register_module(iflow1)
bus.register_module(wechat2)
bus.register_module(iflow2)

# 设置绑定关系
bus.bind("wechat_bot1", "iflow_bot1")  # 微信bot1 发送的消息 → iflow_bot1
bus.bind("iflow_bot1", "wechat_bot1")  # iflow_bot1 的回复 → 微信bot1
bus.bind("wechat_bot2", "iflow_bot2")
bus.bind("iflow_bot2", "wechat_bot2")
```

### 消息路由流程

```
消息到达 MessageBus.route()
        │
        ▼
检查 source_module 的绑定关系
        │
        ▼
bindings[source_module] → target_module_id
        │
        ▼
modules[target_module_id].receive(message)
```

### tmux 会话隔离

IFlowController 通过 `-t` 参数指定 tmux 会话：

```python
# 所有 tmux 命令都带 session 参数
await asyncio.create_subprocess_exec(
    "tmux", "send-keys", "-t", self.tmux_session, message
)
```

这确保不同的 IFlowModule 实例操作不同的 tmux 会话，互不干扰。

## 与现有架构对比

### 现有架构问题
- 职责不清：BotIntegration 同时处理企业微信、tmux 监控、命令解析
- 耦合严重：企业微信模块直接依赖 iflow 模块
- 扩展困难：添加新的消息渠道需要修改核心代码
- 职责重叠：SyncManager 和 BotIntegration 功能有重叠

### 新架构优势
- 松耦合：模块间通过消息总线通信
- 高内聚：相关功能集中在同一模块
- 易扩展：添加新功能无需修改现有代码
- 易测试：每个模块可以独立测试
