# 总体架构设计

## 设计理念

基于**发布-订阅模式**和**消息总线**架构，实现模块解耦。将项目划分为 **5 大模块组**，各司其职，通过 MessageBus 通信。

---

## 模块划分总览

按职责分为 **5 大模块组**：

| 模块组 | 职责 | 代表模块 |
|--------|------|---------|
| **渠道层 (Channel)** | 与外部平台交互 | WeChatChannel, FeishuChannel, SimulatorChannel |
| **消息总线 (Message Bus)** | 模块间消息路由 | MessageBus |
| **IFlow/tmux 交互层** | 控制 tmux 中的 iflow CLI | IFlowModule, IFlowController, IFlowMonitor |
| **通用组件 (Common)** | 各渠道可复用的功能 | MessageConverter, NotificationManager |
| **命令与控制层** | 命令处理 + 模块生命周期管理 | CommandHandler, ModuleManager |

---

## 1. 渠道层（Channel）

**职责**：与外部平台（企业微信、飞书、模拟器等）进行消息收发。

| 模块 | 文件 | 功能 |
|------|------|------|
| **WeChatChannel** | `src/modules/channel/wechat.py` | 企业微信消息收发（HTTP 回调接收 + API 发送），包含加解密、消息确认、去重机制 |
| **FeishuChannel** | `src/modules/channel/feishu.py` | 飞书消息收发（WebSocket 长连接），支持文本/卡片/图片/表情，使用 lark-oapi SDK |
| **SimulatorChannel** | `src/modules/channel/simulator.py` | Socket 测试渠道，用于开发调试，通过 Socket 接收测试工具消息 |

**设计原则**：
- 渠道只负责与平台交互，不处理业务逻辑
- 通过 MessageConverter 将平台消息转换为标准格式
- 各渠道独立，互不依赖

---

## 2. 消息总线（Message Bus）

**职责**：模块间消息路由和分发，实现模块解耦。

| 模块 | 文件 | 功能 |
|------|------|------|
| **MessageBus** | `src/core/bus.py` | 核心消息总线，实现发布-订阅模式。负责模块注册、绑定关系管理、消息路由、广播 |

**核心能力**：
- 模块注册/注销
- 绑定关系管理（channel ↔ iflow）
- 消息路由（根据绑定关系转发）
- 广播机制

---

## 3. IFlow/tmux 交互层

**职责**：控制 tmux 中的 iflow CLI，实现与 iflow 的交互。

| 模块 | 文件 | 功能 |
|------|------|------|
| **IFlowModule** | `src/modules/iflow/module.py` | IFlow 主模块，集成 controller 和 monitor，连接消息总线 |
| **IFlowController** | `src/modules/iflow/controller.py` | 直接与 tmux 交互：启动/停止 iflow、注入消息（send-keys） |
| **IFlowMonitor** | `src/modules/iflow/monitor.py` | 持续监听 tmux 输出（capture-pane），检测 iflow 新回复并广播 |
| **SessionManager** | `src/modules/iflow/session_manager.py` | tmux 会话管理：创建/删除/查询会话 |
| **MessageStore** | `src/modules/iflow/message_store.py` | 消息存储：去重、上下文管理 |
| **InteractionLogger** | `src/modules/iflow/logger.py` | 交互日志记录 |

**设计原则**：
- Controller 负责"写"（注入消息到 tmux）
- Monitor 负责"读"（监听 tmux 输出）
- 两者通过 MessageStore 共享状态

---

## 4. 通用组件（Common）

**职责**：可被各渠道复用的通用功能。

| 模块 | 文件 | 功能 |
|------|------|------|
| **MessageConverter** | `src/modules/common/converter.py` | 消息格式转换：将平台原始消息 ↔ 标准 Message 格式 |
| **NotificationManager** | `src/modules/common/notifications.py` | 通知管理：启动/停止通知、状态通知、模板渲染 |

---

## 5. 命令与控制层

**职责**：命令处理和模块生命周期管理。

| 模块 | 文件 | 功能 |
|------|------|------|
| **CommandHandler** | `src/modules/command/handler.py` | 命令处理器，解析并执行命令（`/help` `/status` `/new` `/sessions` 等） |
| **ModuleManager** | `src/core/manager.py` | 模块管理器，统一管理所有模块的生命周期（启动/停止/健康检查） |

---

## 消息流向

### 外部消息 → iflow

```
外部平台 → 渠道 → MessageConverter → MessageBus → IFlowModule → tmux/iflow
```

### iflow 回复 → 外部平台

```
tmux/iflow → IFlowMonitor → MessageBus → 渠道 → 外部平台
```

## 模块标识与多实例机制

### 核心标识符

每个模块有两个关键标识：

| 标识符 | 用途 | 使用者 |
|--------|------|--------|
| `module_id` | MessageBus 区分不同模块 | 消息路由、绑定关系 |
| `tmux_session` | 标识要连接的 tmux 会话 | IFlowController |

### module_id 命名规范

采用 `<类型>_<名称>` 格式：

| 类型 | 示例 | 说明 |
|------|------|------|
| wechat | `wechat_bot1` | 企业微信渠道模块 |
| feishu | `feishu_feishu1` | 飞书渠道模块 |
| simulator | `simulator_sim1` | 模拟器渠道模块 |
| iflow | `iflow_bot1` | iflow 处理模块 |

### tmux_session 命名规范

采用 `<渠道名>+iflow` 格式：

| 渠道名 | tmux_session |
|--------|--------------|
| bot1 | `bot1+iflow` |
| feishu1 | `feishu1+iflow` |
| simulator1 | `simulator1+iflow` |

### 绑定关系

渠道模块与 iflow 模块双向绑定：

```
wechat_bot1 ←→ iflow_bot1
feishu_feishu1 ←→ iflow_feishu1
simulator_sim1 ←→ iflow_sim1
```

- 渠道模块 → iflow 模块：用户消息路由
- iflow 模块 → 渠道模块：AI 回复路由

## 核心优势

| 优势 | 说明 |
|------|------|
| **职责清晰** | 5 大模块组各司其职，边界明确 |
| **松耦合** | 模块间通过 MessageBus 通信，不直接依赖 |
| **扩展性强** | 新增渠道只需实现 Channel 接口，复用通用组件 |
| **灵活性高** | 支持多渠道绑定、支持动态绑定/解绑 |
| **易于维护** | 模块独立开发测试，故障隔离 |

### 解耦清晰
- 每个模块职责单一
- 模块间通过消息总线通信
- 不直接依赖

### 扩展性强
- 添加新渠道：注册新渠道模块
- 添加新 iflow：注册新 iflow 模块
- 添加新命令：扩展 CommandHandler

### 灵活性高
- 支持多对多绑定
- 支持动态绑定/解绑
- 支持消息广播

### 易于维护
- 模块独立开发测试
- 故障隔离
- 代码职责明确

---

## 与现有架构对比

### 现有架构问题
- 职责不清：BotIntegration 同时处理企业微信、tmux 监控、命令解析
- 耦合严重：企业微信模块直接依赖 iflow 模块
- 扩展困难：添加新的消息渠道需要修改核心代码
- 职责重叠：SyncManager 和 BotIntegration 功能有重叠

### 新架构优势
- 松耦合：模块间通过消息总线通信
- 高内聚：相关功能集中在同一模块
- 易扩展：添加新功能无需修改现有代码
- 易测试：每个模块可以独立测试

---

## 风险和应对

### 风险 1：消息总线性能瓶颈
- **应对**: 使用异步处理和批处理
- **优先级**: 高

### 风险 2：旧功能缺失
- **应对**: 对比测试确保功能完整
- **优先级**: 高

### 风险 3：消息格式不兼容
- **应对**: 统一消息格式，版本管理
- **优先级**: 中

### 风险 4：重构周期过长
- **应对**: 分阶段实施，小步快跑
- **优先级**: 中

---

## 总结

这个方案实现了**松耦合、高内聚**的架构，大大提升了系统的可维护性和可扩展性。

**核心特性**：
- 三大核心模块独立（企业微信、消息总线、iflow）
- 模块间通过消息总线通信
- 支持动态绑定和扩展
- 支持多实例管理
- 支持多渠道架构
- 模块管理器统一管理模块生命周期
- 完整的测试覆盖
- 详细的文档支持

**架构优势**：
- 解耦清晰 - 每个模块职责单一
- 扩展性强 - 添加新功能无需修改现有代码
- 灵活性高 - 支持多对多绑定和动态绑定
- 易于维护 - 模块独立开发测试，故障隔离
