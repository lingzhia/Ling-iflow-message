## 一、架构演进

### 1.1 演进历程

```
第一阶段：微信模块增强
├── 基于 BaseModule 的新架构
├── WeChatModule 职责清晰
├── 消息确认、去重、详细日志
└── 启动/停止通知、Message 对象规范化

第二阶段：渠道架构重构
├── 组件化拆分
├── 提取通用组件（MessageConverter、NotificationManager）
├── 渠道最小化设计
└── 通用组件复用

第三阶段：多渠道支持
├── 支持企业微信、模拟器等多种渠道
├── 配置抽象化
├── 灵活的启动方式
└── 向后兼容

第四阶段：渠道架构简化
├── 去掉 groups 配置
├── 去掉 tmux_sessions 配置
├── 以渠道为中心
└── 命名规则统一
```

### 1.2 当前架构

```
服务进程
├── 消息总线（MessageBus）
├── 模块管理器（ModuleManager）
├── 渠道 bot1
│   ├── WeChatChannel（企业微信渠道）
│   ├── MessageConverter（消息转换器）
│   ├── NotificationManager（通知管理器）
│   ├── IFlowModule（iflow 模块）
│   └── CommandHandler（命令处理器）
├── 渠道 bot2
│   ├── WeChatChannel
│   ├── MessageConverter
│   ├── NotificationManager
│   ├── IFlowModule
│   └── CommandHandler
└── 渠道 simulator1
    ├── SimulatorChannel（模拟器渠道）
    ├── MessageConverter
    ├── NotificationManager
    ├── IFlowModule
    └── CommandHandler
```

### 1.3 设计原则

**核心原则**：
- **渠道最小化**：渠道只负责与平台交互
- **组件复用**：通用功能提取为独立组件
- **职责分离**：每个组件职责单一
- **易于扩展**：新增渠道只需实现平台交互
- **配置抽象化**：通过配置支持多种渠道
- **向后兼容**：保持现有功能不变

## 二、新旧架构对比

### 2.1 旧版本架构

```
WechatWorkChannel（企业微信 API）
         ↓
BotIntegration（核心逻辑：命令、会话、消息处理）
         ↓
IFlowController（tmux 管理）
```

**特点**：
- 功能集中，耦合度高
- 命令处理、消息转换、通知逻辑混杂
- 扩展困难
- 测试复杂

### 2.2 新版本架构

```
WeChatModule（企业微信消息收发）
         ↕
MessageBus（消息路由、绑定）
         ↕
IFlowModule（iflow 管理、监控）
```

**特点**：
- 模块独立，职责单一
- 通过消息总线通信
- 组件复用，易于扩展
- 测试友好

### 2.3 架构优势

| 方面 | 旧架构 | 新架构 |
|------|--------|--------|
| 职责划分 | 职责混杂 | 职责清晰 |
| 模块耦合 | 紧耦合 | 松耦合 |
| 扩展性 | 扩展困难 | 易于扩展 |
| 测试性 | 测试困难 | 测试友好 |
| 维护性 | 维护成本高 | 维护成本低 |
| 代码复用 | 重复代码多 | 通用组件复用 |

## 四、核心组件设计

### 4.1 MessageConverter（消息转换器）

#### 职责

- 将平台原始消息转换为标准 Message 格式
- 将标准 Message 格式转换为平台消息格式
- 提供统一的消息转换接口

#### 主要方法

```python
class MessageConverter:
    def from_platform_message(
        self,
        platform_msg: Dict,
        module_id: str,
        metadata: Optional[Dict] = None
    ) -> Message:
        """从平台消息创建标准 Message"""

    def to_platform_message(
        self,
        message: Message
    ) -> Dict:
        """从标准 Message 创建平台消息"""

    def extract_content(
        self,
        platform_msg: Dict
    ) -> str:
        """提取消息内容"""

    def extract_metadata(
        self,
        platform_msg: Dict
    ) -> Dict:
        """提取元数据"""
```

#### 设计要点

- 支持多种平台消息格式
- 提供默认值和容错处理
- 支持自定义转换规则
- 可以扩展支持新平台

#### 使用示例

```python
converter = MessageConverter()

# 接收企业微信消息
wechat_msg = {"content": "你好", "sender_id": "user1", ...}
message = converter.from_platform_message(wechat_msg, "wechat_bot1", {...})

# 发送回复到企业微信
reply_msg = converter.to_platform_message(message)
await wechat_channel.send_message(reply_msg["content"], reply_msg["chat_id"])
```

- **文件**：`src/modules/common/converter.py`

## 五、渠道实现

### 5.1 WeChatChannel（企业微信渠道）

#### 职责

- 接收企业微信回调
- 解析消息内容
- 发送消息到企业微信
- 处理企业微信特定的消息格式

#### 主要功能

##### 1. 消息确认机制

**实现位置**：`src/modules/channel/wechat.py` - `_process_callback_async()`

**设计思路**：
- 收到企业微信消息后，立即发送确认消息
- 确认消息内容：`✅ 收到消息\n\n正在处理中...\n\n消息内容: {content[:100]}`

**实现方式**：
```python
async def _process_callback_async(self, body: str) -> None:
    """异步处理回调消息"""
    # ... 解析消息 ...

    # 消息确认机制：立即发送确认消息
    if content:
        confirmation = f"✅ 收到消息\n\n正在处理中...\n\n消息内容: {content[:100]}{'...' if len(content) > 100 else ''}"
        await self.send_message(confirmation, chat_id, is_group)
        logger.info(f"[WeChatChannel] 已发送消息确认到 {chat_id}")

    # 调用消息处理器
    if self._message_handler:
        await self._message_handler({...})
```

##### 2. 消息去重机制

**实现位置**：`src/modules/channel/wechat.py` - `_is_duplicate_message()`

**设计思路**：
- 使用 MsgId 进行去重
- 维护一个消息 ID 缓存（TTL: 1小时）
- 定期清理过期缓存

**实现方式**：
```python
async def _is_duplicate_message(self, msg_id: str) -> bool:
    """检查是否为重复消息"""
    current_time = time.time()

    # 清理过期缓存
    self._processed_msg_ids = {
        k: v for k, v in self._processed_msg_ids.items()
        if current_time - v < 3600
    }

    if msg_id in self._processed_msg_ids:
        return True

    self._processed_msg_ids[msg_id] = current_time
    return False
```

##### 3. 详细日志

**实现位置**：`src/modules/channel/wechat.py`

**设计思路**：
- 收到消息时打印详细信息
- 发送消息时打印详细信息
- 便于调试和问题排查

**实现方式**：
```python
# 收到消息日志
logger.info(
    f"[WeChatChannel] 收到企业微信消息\n"
    f"  来源: {from_user_name}\n"
    f"  类型: {'群聊' if is_group else '私聊'}\n"
    f"  消息类型: {msg_type}\n"
    f"  消息内容: {content[:200] if content else ''}"
)

# 发送消息日志
logger.info(
    f"[WeChatChannel] 发送消息到企业微信\n"
    f"  接收者: {chat_id}\n"
    f"  类型: {'群聊' if is_group else '私聊'}\n"
    f"  消息内容: {content[:200] if content else ''}"
)
```

## 七、架构简化

### 7.1 简化目标

**核心原则：以渠道为中心，简化配置**

- 去掉 `groups` 配置，直接管理渠道
- 去掉 `tmux_sessions` 配置，使用命名规则
- 去掉 `workspace` 和 `model` 配置，使用默认值
- 命令行参数从 `-g` (group) 改为 `-c` (channel)
- iflow 与渠道绑定，使用命名规则

### 7.2 设计理念

**"一个渠道，一个 iflow"**

- 每个渠道对应一个 iflow 实例
- iflow 会话名：`渠道名+iflow`
- iflow 使用默认配置（当前目录、glm-4.7、--yolo）
- 简化配置，提升用户体验

### 7.3 配置变化对比

| 配置项 | 旧配置 | 新配置 | 说明 |
|--------|--------|--------|------|
| `workspace` | `"~/.iflow"` | **去掉** | 使用当前目录 |
| `model` | `"glm-4.7"` | **去掉** | 使用默认模型 |
| `tmux_session` | `"iflow1"` | **去掉** | 使用渠道命名 |
| `tmux_sessions` | 数组配置 | **去掉** | 使用命名规则 |
| `groups` | 对象配置 | **去掉** | 基于渠道管理 |
| `bots[].tmux_session` | `"iflow1"` | `"wechat_bot1+iflow"` | 命名规则 |
| `simulator_channels[].tmux_session` | `"iflow1"` | `"simulator1+iflow"` | 命名规则 |

### 7.4 命名规则

#### 渠道命名

- 企业微信：`wechat_bot1`, `wechat_bot2`
- 模拟器：`simulator1`, `simulator2`

#### iflow 会话命名

- `wechat_bot1+iflow`
- `wechat_bot2+iflow`
- `simulator1+iflow`

#### 模块 ID 命名

- 渠道模块：`wechat_bot1`, `wechat_bot2`, `simulator1`
- iflow 模块：`iflow_wechat_bot1+iflow`, `iflow_wechat_bot2+iflow`, `iflow_simulator1+iflow`

### 7.5 优势分析

| 优势 | 说明 |
|------|------|
| **配置简化** | 去掉冗余配置，只保留必要的渠道配置 |
| **逻辑清晰** | 以渠道为中心，逻辑更直观 |
| **命名一致** | iflow 会话名与渠道名关联 |
| **易于理解** | 新用户更容易理解和使用 |
| **扩展简单** | 添加新渠道只需在 bots 或 simulator_channels 中添加配置 |
| **维护简单** | 减少代码复杂度，易于维护 |
| **减少耦合** | 去掉组的概念，直接管理渠道 |

## 十二、常见问题

### Q1: 如何升级到新版本？

**A:**
1. 备份当前配置文件
2. 更新配置文件格式（去掉 groups、tmux_sessions 等）
3. 更新命令脚本中的参数：`-g` → `-c`
4. 重启服务

### Q2: 如果我需要不同的工作目录怎么办？

**A:**
在新方案中，工作目录默认使用当前目录。如需不同的工作目录：
```bash
cd /path/to/workspace
./manage.py start
```

### Q3: 如何添加新渠道？

**A:**
参考 [十一、扩展指南](#十一扩展指南)，主要包括：
1. 实现 Channel 类
2. 添加配置段
3. 添加创建逻辑
4. 测试验证

### Q4: 默认渠道是什么？

**A:**
默认渠道是配置文件中第一个启用的企业微信渠道（`bots` 中 `enabled: true` 的第一个）。

### Q5: 如何启动多个渠道？

**A:**
使用 `-a` 参数启动所有渠道：
```bash
./manage.py start -a
```

### Q6: 前台运行有什么用？

**A:**
使用 `-f` 参数前台运行，适合开发和调试场景，可以实时查看日志输出。

### Q7: 如何查看可用渠道？

**A:**
使用 `-c ls` 参数列出所有可用渠道：
```bash
./manage.py start -c ls
```

### Q8: 消息确认机制是如何工作的？

**A:**
当收到企业微信消息时，系统会立即发送一条确认消息，告知用户消息已收到，正在处理中。这提升了用户体验，避免用户重复发送消息。

### Q9: 消息去重机制是如何工作的？

**A:**
系统使用 MsgId 进行去重，维护一个消息 ID 缓存（TTL: 1小时）。如果收到重复的 MsgId，系统会忽略该消息。

### Q10: 如何自定义通知内容？

**A:**
参考 [十一、扩展指南](#十一扩展指南) 中的自定义通知模板部分。
