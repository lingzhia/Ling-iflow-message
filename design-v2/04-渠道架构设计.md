# 渠道架构设计

## 文档概述

本文档阐述了 Ling-iflow 项目渠道架构的通用设计，包括架构演进、核心理念、组件设计和配置说明。

---

## 一、架构演进

### 1.1 演进历程

**第一阶段：微信模块增强**
- 基于 BaseModule 的新架构，功能解耦
- WeChatChannel 职责清晰
- 消息确认、去重、详细日志
- 启动/停止通知、Message 对象规范化

**第二阶段：渠道架构重构**
- 组件化拆分
- 提取通用组件（MessageConverter、NotificationManager）
- 渠道最小化设计
- 通用组件复用

**第三阶段：多渠道支持**
- 支持企业微信、飞书、模拟器等多种渠道
- 配置抽象化
- 灵活的启动方式
- 向后兼容

**第四阶段：渠道架构简化**
- 去掉 groups 配置
- 去掉 tmux_sessions 配置
- 以渠道为中心
- 命名规则统一

### 1.2 当前架构

服务进程包含以下组件：

- 消息总线（MessageBus）
- 模块管理器（ModuleManager）
- 渠道 bot1（WeChatChannel、MessageConverter、NotificationManager、IFlowModule、CommandHandler）
- 渠道 bot2（结构同 bot1）
- 渠道 simulator1（SimulatorChannel、MessageConverter、NotificationManager、IFlowModule、CommandHandler）

### 1.3 设计原则

**核心原则**：

| 原则 | 说明 |
|------|------|
| 渠道最小化 | 渠道只负责与平台交互 |
| 组件复用 | 通用功能提取为独立组件 |
| 职责分离 | 每个组件职责单一 |
| 易于扩展 | 新增渠道只需实现平台交互 |
| 配置抽象化 | 通过配置支持多种渠道 |
| 向后兼容 | 保持现有功能不变 |

### 1.4 tmux 会话配置

**实际实现**：

| 配置项 | 说明 |
|--------|------|
| tmux_session | 可选配置项 |
| 默认值 | `{channel_name}+iflow`，例如 `wechat_bot1+iflow` |
| 配置方式 | 用户可在渠道配置中手动指定，也可使用默认值 |
| 命名规则 | 如果使用默认值，会话名与渠道名关联，便于识别 |

**会话名生成规则**：
- 企业微信：`wechat_{name}+iflow`，例如 `wechat_bot1+iflow`
- 飞书：`feishu_{name}+iflow`，例如 `feishu_feishu1+iflow`
- 模拟器：`simulator_{name}+iflow`，例如 `simulator_sim1+iflow`

## 二、新旧架构对比

### 2.1 旧版本架构

```
WechatWorkChannel（企业微信 API）
         ↓
BotIntegration（核心逻辑：命令、会话、消息处理）
         ↓
IFlowController（tmux 管理）
```

**特点**：
- 功能集中，耦合度高
- 命令处理、消息转换、通知逻辑混杂
- 扩展困难
- 测试复杂

### 2.2 新版本架构

```
WeChatChannel（企业微信消息收发）
         ↕
MessageBus（消息路由、绑定）
         ↕
IFlowModule（iflow 管理、监控）
```

**特点**：
- 模块独立，职责单一
- 通过消息总线通信
- 组件复用，易于扩展
- 测试友好

### 2.3 架构优势

| 方面 | 旧架构 | 新架构 |
|------|--------|--------|
| 职责划分 | 职责混杂 | 职责清晰 |
| 模块耦合 | 紧耦合 | 松耦合 |
| 扩展性 | 扩展困难 | 易于扩展 |
| 测试性 | 测试困难 | 测试友好 |
| 维护性 | 维护成本高 | 维护成本低 |
| 代码复用 | 重复代码多 | 通用组件复用 |

## 四、核心组件设计

### 4.1 MessageConverter（消息转换器）

#### 职责

- 将平台原始消息转换为标准 Message 格式
- 将标准 Message 格式转换为平台消息格式
- 提供统一的消息转换接口

#### 主要方法

| 方法 | 说明 |
|------|------|
| `from_platform_message()` | 从平台消息创建标准 Message |
| `to_platform_message()` | 从标准 Message 创建平台消息 |
| `create_wechat_inbound_message()` | 创建企业微信入站消息 |
| `create_wechat_outbound_message()` | 创建企业微信出站消息 |
| `create_iflow_inbound_message()` | 创建 iflow 入站消息 |
| `create_iflow_outbound_message()` | 创建 iflow 出站消息 |

#### 设计要点

- 支持多种平台消息格式
- 提供默认值和容错处理
- 支持自定义转换规则
- 可以扩展支持新平台

#### 实现位置

- **文件**：`src/modules/common/converter.py`

---

### 4.2 NotificationManager（通知管理器）

#### 职责

- 发送启动通知
- 发送停止通知
- 管理通知模板

#### 主要方法

| 方法 | 说明 |
|------|------|
| `send_startup_notification()` | 发送启动通知 |
| `send_shutdown_notification()` | 发送停止通知 |
| `render_template()` | 渲染通知模板 |
| `register_template()` | 注册自定义模板 |
| `register_notification_handler()` | 注册通知处理器 |

#### 模板系统

默认模板：

- `startup` - 正常启动通知
- `startup_with_error` - 异常启动通知
- `shutdown` - 停止通知

#### 设计要点

- 支持模板变量替换
- 支持自定义通知处理器
- 通过处理器实现发送到不同平台

#### 实现位置

- **文件**：`src/modules/common/notifications.py`

#### 使用情况

| 渠道 | 是否使用 | 说明 |
|------|---------|------|
| WeChatChannel | ✅ 使用 | 通过 handler 发送到企业微信 |
| FeishuChannel | ✅ 使用 | 通过 handler 发送到飞书 |
| SimulatorChannel | ❌ 不使用 | 测试场景不需要通知 |

## 六、各渠道详细设计

### 6.1 WeChatChannel 详细设计

#### 消息接收流程

1. 企业微信服务器通过 HTTP POST 推送消息到回调地址
2. 回调服务器验证签名（如果配置了加解密）
3. 解析 XML 格式的消息
4. 检查是否重复消息（使用 MsgId）
5. 发送消息确认（提升用户体验）
6. 解析命令，如果是内置命令则执行
7. 将消息转换为标准格式发送到消息总线

#### 消息发送流程

1. 从消息总线接收需要发送的消息
2. 提取消息内容和聊天 ID
3. 刷新 access_token（如需要）
4. 调用企业微信 API 发送消息

#### 消息确认机制

收到用户消息后，立即发送确认：

```
✅ 收到消息
正在处理中...
消息内容: xxx...
```

让用户知道消息已被系统接收。

#### 消息去重机制

使用 MsgId 作为唯一标识，缓存 1 小时内已处理的消息 ID，避免重复处理。

#### 加解密机制

支持企业微信消息加解密：
- 使用 AES CBC 模式解密
- 验证消息签名
- PKCS7 unpadding

### 6.2 FeishuChannel 详细设计

#### 消息接收流程

1. 使用 WebSocket 长连接接收飞书推送
2. 事件分发到对应处理器
3. 解析消息内容（支持多种类型）
4. 检查白名单（如果配置）
5. 检查是否重复消息
6. 添加表情反应作为确认
7. 解析命令，如果是内置命令则执行
8. 将消息转换为标准格式发送到消息总线

#### 消息发送流程

1. 从消息总线接收需要发送的消息
2. 提取消息内容和接收者 ID
3. 将文本转换为飞书交互卡片格式
4. 调用飞书 SDK 发送消息

#### 消息确认机制

收到用户消息后，添加点赞表情反应（THUMBSUP），让用户知道消息已被系统收到。

#### 消息去重机制

使用 message_id 作为唯一标识，OrderedDict 缓存 1 小时内已处理的消息 ID，最多缓存 1000 条。

#### 白名单机制

可配置 `allow_from` 列表，限制只有列表中的用户可以与机器人交互。支持飞书 open_id 格式。

#### 支持的消息类型

| 类型 | 说明 | 处理方式 |
|------|------|---------|
| text | 文本消息 | 直接提取 text 字段 |
| post | 富文本消息 | 解析并提取文本和资源 |
| image | 图片 | 下载并保存到本地 |
| audio | 音频 | 下载并保存到本地 |
| file | 文件 | 下载并保存到本地 |
| share_chat | 分享会话 | 提取会话信息 |
| share_user | 分享用户 | 提取用户信息 |
| interactive | 交互卡片 | 提取卡片内容 |
| system | 系统消息 | 提取系统提示 |
| merge_forward | 合并转发 | 提取合并内容 |

#### 通知发送策略

启动/停止通知优先发送到配置的 `notify_user_id`，其次使用最近联系人（用户最后一次发送消息的 ID）。

### 6.3 SimulatorChannel 详细设计

#### 消息接收流程

1. 启动 Socket 服务器监听连接
2. 客户端连接后加入连接列表
3. 接收客户端消息（自定义协议）
4. 解析 JSON 格式消息
5. 解析命令，如果是内置命令则执行
6. 将消息转换为标准格式发送到消息总线

#### 消息发送流程

1. 从消息总线接收需要发送的消息
2. 发送到所有已连接的客户端

#### Socket 通信协议

- 消息格式：4 字节长度 + JSON 内容
- 长度使用大端序无符号整数
- 支持心跳和关闭消息

#### 支持的客户端消息类型

| 类型 | 说明 |
|------|------|
| user_message | 用户消息，发送到消息总线 |
| heartbeat | 心跳消息，保持连接 |
| close | 关闭连接 |

#### 支持的服务端消息类型

| 类型 | 说明 |
|------|------|
| bot_message | 机器人回复 |
| reply_message | iflow 回复 |

## 七、架构简化

### 7.1 简化目标

**核心原则：以渠道为中心，简化配置**

- 去掉 `groups` 配置，直接管理渠道
- 去掉 `tmux_sessions` 配置，使用命名规则
- 去掉 `workspace` 和 `model` 配置，使用默认值
- 命令行参数从 `-g` (group) 改为 `-c` (channel)
- iflow 与渠道绑定，使用命名规则

### 7.2 设计理念

**"一个渠道，一个 iflow"**

- 每个渠道对应一个 iflow 实例
- iflow 会话名：`{channel_name}+iflow`
- 飞书 iflow 会话名：`feishu_{channel_name}+iflow`
- iflow 使用默认配置（当前目录、默认模型、--yolo）
- 简化配置，提升用户体验

### 7.3 配置变化对比

| 配置项 | 旧配置 | 新配置 | 说明 |
|--------|--------|--------|------|
| `workspace` | 旧配置路径 | **去掉** | 使用当前目录 |
| `model` | 指定模型 | **去掉** | 使用默认模型 |
| `tmux_session` | 手动指定 | **去掉** | 使用渠道命名规则 |
| `tmux_sessions` | 数组配置 | **去掉** | 使用命名规则 |
| `groups` | 对象配置 | **去掉** | 基于渠道管理 |

### 7.4 命名规则

**渠道命名**
- 企业微信：`wechat_{name}`
- 模拟器：`simulator_{name}`
- 飞书：`feishu_{name}`

**iflow 会话命名**
- `{channel_name}+iflow`
- 例如：`wechat_bot1+iflow`, `simulator_sim1+iflow`

**模块 ID 命名**
- 渠道模块：`wechat_bot1`, `wechat_bot2`, `simulator_sim1`
- iflow 模块：`iflow_wechat_bot1`, `iflow_simulator_sim1`

### 7.5 优势分析

| 优势 | 说明 |
|------|------|
| **配置简化** | 去掉冗余配置，只保留必要的渠道配置 |
| **逻辑清晰** | 以渠道为中心，逻辑更直观 |
| **命名一致** | iflow 会话名与渠道名关联 |
| **易于理解** | 新用户更容易理解和使用 |
| **扩展简单** | 添加新渠道只需在配置中添加 |
| **维护简单** | 减少代码复杂度，易于维护 |
| **减少耦合** | 去掉组的概念，直接管理渠道 |

## 八、扩展指南

### 8.1 添加新渠道

#### 步骤 1：实现 Channel 类

在 `src/modules/channel/` 创建新渠道文件，继承 BaseModule，实现以下核心方法：

- `_on_start()`：启动时的初始化
- `_on_stop()`：停止时的清理
- `_on_receive()`：接收消息处理
- `send_message()`：发送消息到平台
- `set_message_handler()`：设置消息处理器

#### 步骤 2：添加配置支持

在配置文件中添加新渠道类型的配置段。

#### 步骤 3：添加创建逻辑

在 `bot.py` 中添加新渠道类型的创建逻辑。

#### 步骤 4：测试验证

- 单元测试新渠道
- 集成测试
- 功能测试

### 8.2 添加新命令

#### 步骤 1：注册命令

在 `CommandHandler` 中调用 `register_command()` 注册新命令。

#### 步骤 2：实现命令处理

实现命令处理方法，接收 Message 对象和参数。

#### 步骤 3：测试

在各渠道中测试新命令。

### 8.3 自定义通知模板

#### 步骤 1：创建模板

在 `NotificationManager` 的 TEMPLATES 字典中添加自定义模板。

#### 步骤 2：渲染模板

调用 `render_template()` 方法，传入模板名和上下文变量。

#### 步骤 3：发送通知

调用 `send_*_notification()` 方法发送通知。

## 九、常见问题

### Q1: 如何升级到新版本？

1. 备份当前配置文件
2. 更新配置文件格式（去掉 groups、tmux_sessions 等）
3. 更新命令脚本中的参数：`-g` → `-c`
4. 重启服务

### Q2: 如果我需要不同的工作目录怎么办？

在新方案中，工作目录默认使用当前目录。如需不同的工作目录，切换到对应目录后启动即可。

### Q3: 如何添加新渠道？

参考扩展指南部分，主要包括：
1. 实现 Channel 类
2. 添加配置段
3. 添加创建逻辑
4. 测试验证

### Q4: 默认渠道是什么？

默认渠道是配置文件中第一个启用的企业微信渠道（`bots` 中 `enabled: true` 的第一个）。

### Q5: 如何启动多个渠道？

使用 `-a` 参数启动所有渠道：
```bash
./manage.py start -a
```

### Q6: 前台运行有什么用？

使用 `-f` 参数前台运行，适合开发和调试场景，可以实时查看日志输出。

### Q7: 如何查看可用渠道？

使用 `-c ls` 参数列出所有可用渠道：
```bash
./manage.py start -c ls
```

### Q8: 飞书渠道为什么使用 WebSocket 而不是回调？

飞书的 WebSocket 模式是官方推荐的方式：
- 无需公网 IP 或反向代理
- 支持消息主动推送
- 自动重连
- 延迟更低

### Q9: 消息确认机制在不同渠道有什么不同？

| 渠道 | 确认方式 |
|------|---------|
| WeChatChannel | 发送文本确认 "✅ 收到消息\n正在处理中..." |
| FeishuChannel | 添加点赞表情反应（THUMBSUP） |
| SimulatorChannel | 不需要确认（测试场景） |

## 十、总结

### 10.1 架构优势

| 优势 | 说明 |
|------|------|
| **职责清晰** | 每个组件职责单一，易于理解和维护 |
| **易于扩展** | 新增渠道只需实现平台交互，复用通用组件 |
| **组件复用** | MessageConverter 可被所有渠道复用 |
| **通知分离** | NotificationManager 实现通知逻辑与渠道的分离 |
| **配置简化** | 去掉冗余配置，以渠道为中心 |
| **易于测试** | 组件独立，易于单元测试和集成测试 |
| **向后兼容** | 保持现有功能不变，平滑升级 |

### B. 术语表

| 术语 | 说明 |
|------|------|
| **渠道** | 与外部平台交互的模块，如企业微信、飞书、模拟器等 |

| **绑定** | 建立两个模块之间的消息路由关系 |

| **消息确认** | 收到消息后告知用户已收到的机制 |
| **消息去重** | 避免重复处理同一消息的机制 |
