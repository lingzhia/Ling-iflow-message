本文档记录 Ling-iflow 项目中发现的技术问题和修复方案。

## 一、消息来源差异化处理

### 1.1 问题背景

当前 IFlowModule 完整记录 iflow 返回的所有消息（✦ 和 ✻），无论请求消息来自哪里。但是，对于不同来源的请求消息，回复消息的发送方式应该有所区别：

1. **企业微信/飞书/模拟器等渠道发送的消息**：
   - 有明确来源（MessageStore 中有记录且 source 字段不为空）
   - 期望：实时响应，逐条发送回复消息

2. **用户在 tmux 中手动输入的消息**：
   - 无明确来源（MessageStore 中无记录或 source 字段为空）
   - 期望：完整回复，避免碎片化信息

### 1.2 核心思想

**根据请求消息的来源状态，决定回复消息的发送方式：**

| 来源状态 | 发送方式 |
|----------|----------|
| 有明确来源 | 逐条实时发送（流式模式） |
| 无明确来源 | 等待完整后整合发送（缓冲模式） |

### 1.3 两种模式

#### 流式模式（Stream Mode）

**触发条件**：
- 请求消息匹配到 MessageStore 中的记录
- 该记录的 source 字段不为空

**发送行为**：
- 每提取到一条 ✦ 消息 → 立即发送到目标对话
- ✻ 消息不发送（被过滤）
- 每条消息独立发送，不等待其他消息

#### 缓冲模式（Buffer Mode）

**触发条件**：
- 请求消息未匹配到 MessageStore 中的记录
- 或者匹配记录的 source 字段为空

**发送行为**：
- 每提取到一条 ✦ 消息 → 暂存到缓冲区
- ✻ 消息不处理
- 生成结束时（GENERATING → IDLE）→ 整合缓冲区的所有 ✦ 消息为一条
- 发送整合后的消息到消息总线（receiver 为空，广播模式）

**无来源消息格式增强**：
为帮助用户理解消息来源，整合消息会添加说明前缀：
```
未知来源消息回复结束！
原请求消息内容是：{原始请求}
回复内容如下：
{整合后的回复内容}
```

### 1.4 优势

| 优势 | 说明 |
|------|------|
| 用户体验优化 | 渠道消息实时响应，手动输入获得完整回复 |
| 逻辑清晰 | 有来源=实时响应，无来源=完整交付 |
| 自动判断 | 系统自动检测消息来源 |
| 向后兼容 | 有来源的消息保持原有逻辑 |

## 二、/scope 命令历史消息重复问题修复

### 2.1 问题背景

### 2.1.1 问题描述

在使用 `/scope all` 命令切换回复模式后，历史消息会被重复发送，导致：
1. 历史消息被重复发送给用户
2. iflow 进入"生成中"状态
3. 新消息被拒绝

### 2.1.2 问题复现

| 步骤 | 操作 | 结果 |
|------|------|------|
| 1 | 发送 "1+1=?" | 收到 "1+1=2" |
| 2 | 发送 "/scope all" | 切换到全部消息模式 |
| 3 | 发送 "什么是Python？" | 收到3条消息：第一条历史消息"1+1=2"（重复！）、Python介绍、Python应用场景 |
| 4 | 新消息 | 被拒绝："iflow 生成中，请稍后再试" |

### 2.2 根本原因

**双重失效导致历史消息被重复发送：**

1. **行号过滤失效**：
   - 虽然记录了 `_last_received_line`（发给 iflow 的消息行号）
   - 但是故意不使用它来过滤消息
   - 代码注释："只更新_last_received_line，不过滤内容"

2. **缓存去重失效**：
   - 每次回复完成后清空缓存（monitor.py）
   - 缓存被清空后，历史消息通过去重检查
   - 历史消息被重复发送

### 2.3 行号固定性分析

**发现：行号不是固定的！**

```
tmux history-limit = 2000 行
```

这意味着：
1. **tmux 会保留最近的 2000 行输出**
2. **超过 2000 行后，旧内容会被删除**
3. **行号会发生变化**

**结论：行号不可靠，不能依赖行号过滤消息！**

### 2.4 解决方案

#### 方案2：保留缓存，不清空（推荐）

**核心思想：**
- 不清空缓存，利用现有的去重机制
- 定期清理旧缓存，控制内存占用

**实现步骤：**

1. **修改缓存清空逻辑**
   - 注释掉缓存清空代码，保留现有去重机制

2. **添加缓存清理机制**
   - 实现 `_cleanup_cache` 方法
   - 设置最大缓存大小（如100条）
   - 保留最近的 max_cache_size/2 条消息
   - 在添加新消息后调用清理

3. **可选：检测新会话开始**
   - 检测 tmux 输出中的新提示符
   - 检测用户发送了 /new 命令
   - 在检测到新会话时清空缓存

**方案优点：**

| 优点 | 说明 |
|------|------|
| 简单可靠 | 利用现有的去重机制 |
| 不依赖行号 | 不受 tmux history-limit 影响 |
| 内存可控 | 定期清理旧缓存 |
| 性能良好 | 集合查找 O(1) 时间复杂度 |

**方案缺点：**

| 缺点 | 说明 |
|------|------|
| 缓存增长 | 缓存会一直增长到清理阈值 |
| 内存占用 | 需要占用额外内存存储哈希值 |
| 清理时机 | 需要选择合适的清理时机 |

#### 方案对比

| 方案 | 描述 | 优点 | 缺点 | 可靠性 |
|------|------|------|------|--------|
| 方案1 | 使用行号过滤 | 简单直接 | 行号不可靠 | ❌ 不可靠 |
| 方案2 | 保留缓存，不清空 | 利用现有机制 | 缓存增长 | ✅ 可靠 |
| 方案3 | 使用消息内容定位 | 不依赖行号 | 内容可能变化 | ⚠️ 中等 |
| 方案4 | 双重保障 | 结合多种机制 | 实现复杂 | ✅ 可靠 |

### 2.7 设计文档更新

**消息去重原则（更新）：**

| 项目 | 修改前 | 修改后 |
|------|--------|--------|
| 缓存管理 | 每次回复完成后清空 | 保留缓存，定期清理 |
| 缓存清理时机 | GENERATING→IDLE | 达到阈值时清理 |
| 最大缓存大小 | 1000 条 | 100 条（可配置） |
| 保留数量 | 500 条 | 50 条 |
| 行号过滤 | 不使用（故意） | 不使用（不可靠） |

**缓存管理策略（新增）：**

| 配置项 | 值 | 说明 |
|--------|-----|------|
| max_cache_size | 100 | 最大缓存大小 |
| keep_count | 50 | 保留数量 |
| 清理条件 | len(cache) > max_cache_size | 缓存超过阈值时清理 |

### 2.8 风险评估

| 风险 | 可能性 | 影响 | 缓解措施 |
|------|--------|------|----------|
| 内存泄漏 | 低 | 中 | 定期清理缓存 |
| 消息去重失效 | 低 | 高 | 使用双重定位（字符串+哈希） |
| 缓存清理时机不当 | 中 | 低 | 选择合适的清理阈值 |
| 新会话检测失效 | 低 | 低 | 可选功能 |

## 三、总结

### 3.1 核心发现

| 发现 | 说明 |
|------|------|
| 行号不可靠 | tmux history-limit 导致行号变化 |
| 缓存清空是主要原因 | 每次回复完成后清空缓存 |
| 保留缓存是最可靠方案 | 不依赖行号，利用现有机制 |

### 3.2 推荐方案

**消息来源差异化处理**：
- 根据请求消息来源自动选择发送模式
- 有明确来源 → 流式模式
- 无明确来源 → 缓冲模式

**历史消息重复问题修复**：
- 方案2（保留缓存，不清空）
- 修改缓存清空逻辑
- 添加缓存清理机制
- 定期清理旧缓存
