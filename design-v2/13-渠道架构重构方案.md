# 渠道架构重构方案

## 概述

### 背景

当前 WeChatModule 混合了三类功能：
1. **平台特定功能**：企业微信 API 调用、消息格式转换
2. **通用业务功能**：命令处理、消息格式转换、通知
3. **模块集成功能**：与消息总线交互、生命周期管理

这种设计导致：
- 职责混杂，难以理解和维护
- 扩展困难，新增渠道需要重复实现通用功能
- 测试困难，需要模拟大量依赖

### 目标

通过组件化拆分，提取可复用的通用组件，使渠道职责清晰，易于扩展和测试。

### 核心原则

**渠道最小化**：渠道只负责与平台交互
**组件复用**：通用功能提取为独立组件
**职责分离**：每个组件职责单一
**易于扩展**：新增渠道只需实现平台交互

## 当前架构分析

### WeChatModule 结构

```
WeChatModule
├── WeChatChannel（平台交互）
├── CommandHandler（命令处理）
├── 消息转换逻辑（内嵌）
├── 通知逻辑（内嵌）
└── MessageBus 交互（内嵌）
```

### 问题识别

**1. 职责混杂**
- WeChatModule 既负责消息收发，又负责命令处理和消息转换
- 消息转换逻辑与 WeChatModule 紧耦合
- 通知逻辑分散在模块中

**2. 耦合度高**
- WeChatModule 直接依赖 MessageBus
- 平台特定的逻辑与通用逻辑混合
- 消息创建和转换逻辑分散

**3. 扩展困难**
- 新增渠道需要重复实现消息转换逻辑
- 命令处理逻辑需要每个渠道单独实现
- 难以复用通用功能

**4. 测试困难**
- 测试渠道功能需要模拟 MessageBus
- 单元测试依赖太多组件
- 难以独立测试渠道的消息收发功能

### 可复用功能识别

**通用功能（可以复用）**：
- 消息格式转换：将平台消息转为标准格式
- 命令解析和执行：处理 /help、/status 等命令
- 启动/停止通知：告知用户服务状态
- 消息分类：区分普通消息和命令消息

**平台特定功能（不能复用）**：
- 具体的 API 调用（企业微信、Telegram、钉钉各不相同）
- 具体的消息格式（每个平台的消息格式不同）
- 具体的认证方式（每个平台的认证方式不同）

## 重构方案

### 方案选择

经过分析，选择**组件化拆分方案**作为推荐方案，因为：
- 复用性高
- 改动难度适中
- 易于理解和维护
- 风险可控

### 核心组件

**1. 消息转换器（MessageConverter）**

**职责**：
- 将平台原始消息转换为标准 Message 格式
- 将标准 Message 格式转换为平台消息格式
- 提供统一的消息转换接口

**输入输出**：
- 输入：平台原始消息（Dict 或平台特定格式）
- 输出：标准 Message 对象

**复用性**：
- 所有渠道都需要消息格式转换
- 可以统一消息创建逻辑
- 减少重复代码

**2. 通知管理器（NotificationManager）**

**职责**：
- 发送启动通知
- 发送停止通知
- 发送状态通知
- 管理通知模板

**输入输出**：
- 输入：通知类型、接收者、通知内容
- 输出：发送成功/失败

**复用性**：
- 所有渠道都可能需要通知用户
- 统一的通知格式
- 便于维护通知内容

**3. CommandHandler（已有组件）**

**职责**：
- 解析命令
- 执行命令
- 返回命令结果

**复用性**：
- 已经是独立组件
- 可以直接复用
- 已经测试完善

**4. 平台渠道（Platform Channel）**

**职责**：
- 只负责与平台交互
- 接收平台原始消息
- 发送平台原始消息
- 不依赖消息总线

**输入输出**：
- 输入：平台配置
- 输出：平台原始消息

**不可复用**：
- 每个平台的 API 调用方式不同
- 每个平台的消息格式不同
- 每个平台的认证方式不同

**5. 模块集成器（Module Integrator）**

**职责**：
- 组装平台渠道、消息转换器、命令处理器
- 协调各组件工作
- 与消息总线交互
- 管理模块生命周期

**输入输出**：
- 输入：平台配置、消息总线
- 输出：完整的模块功能

**复用性**：
- 集成逻辑可以被复用
- 可以作为模板用于新渠道

## 组件详细设计

### 1. 消息转换器（MessageConverter）

**核心职责**：
- 将平台消息转换为标准 Message 格式
- 将标准 Message 格式转换为平台消息格式
- 提供统一的消息创建接口

**主要方法**：
- `from_platform_message(platform_msg, module_id, metadata)`: 从平台消息创建标准 Message
- `to_platform_message(message)`: 从标准 Message 创建平台消息
- `extract_content(platform_msg)`: 提取消息内容
- `extract_metadata(platform_msg)`: 提取元数据

**设计要点**：
- 支持多种平台消息格式
- 提供默认值和容错处理
- 支持自定义转换规则
- 可以扩展支持新平台

**使用示例**：
```python
converter = MessageConverter()

# 接收企业微信消息
wechat_msg = {"content": "你好", "sender_id": "user1", ...}
message = converter.from_platform_message(wechat_msg, "wechat_bot1", {...})

# 发送回复到企业微信
reply_msg = converter.to_platform_message(message)
await wechat_channel.send_message(reply_msg["content"], reply_msg["chat_id"])
```

### 2. 通知管理器（NotificationManager）

**核心职责**：
- 发送启动通知
- 发送停止通知
- 发送状态通知
- 管理通知模板

**主要方法**：
- `send_startup_notification(channel, user_id, **kwargs)`: 发送启动通知
- `send_shutdown_notification(channel, user_id, **kwargs)`: 发送停止通知
- `send_status_notification(channel, user_id, status, **kwargs)`: 发送状态通知
- `render_template(template_name, **context)`: 渲染通知模板

**设计要点**：
- 支持模板系统
- 支持自定义通知内容
- 支持多种通知渠道
- 提供通知历史记录

**使用示例**：
```python
notifier = NotificationManager()

# 发送启动通知
await notifier.send_startup_notification(
    channel=wechat_channel,
    user_id="user1",
    iflow_status="running"
)

# 发送停止通知
await notifier.send_shutdown_notification(
    channel=wechat_channel,
    user_id="user1"
)
```

### 3. CommandHandler（已有组件）

**现状**：
- 已经是独立组件
- 已经实现了命令解析和执行
- 可以直接复用

**复用方式**：
- 在模块集成器中使用
- 配置可用的命令列表
- 可以扩展自定义命令

### 4. 平台渠道（Platform Channel）

**核心职责**：
- 只负责与平台交互
- 接收平台原始消息
- 发送平台原始消息
- 管理平台连接

**主要方法**：
- `connect()`: 连接到平台
- `disconnect()`: 断开连接
- `send_message(content, chat_id, **kwargs)`: 发送消息
- `receive_message()`: 接收消息
- `set_message_handler(handler)`: 设置消息处理器

**设计要点**：
- 不依赖消息总线
- 不依赖标准消息格式
- 只处理平台特定的逻辑
- 提供统一的错误处理

**企业微信渠道**：
- 使用 WeChatChannel（已有）
- 只负责企业微信 API 调用
- 处理企业微信特定的消息格式

**模拟器渠道**（未来）：
- 使用 SimulatorChannel
- 只负责与测试工具通信
- 处理模拟器特定的消息格式

### 5. 模块集成器（Module Integrator）

**核心职责**：
- 组装平台渠道、消息转换器、命令处理器
- 协调各组件工作
- 与消息总线交互
- 管理模块生命周期

**主要方法**：
- `start()`: 启动模块
- `stop()`: 停止模块
- `handle_platform_message(platform_msg)`: 处理平台消息
- `handle_bus_message(message)`: 处理总线消息
- `check_iflow_status()`: 检查 iflow 状态

**设计要点**：
- 使用依赖注入组装组件
- 实现标准模块接口（BaseModule）
- 管理组件生命周期
- 协调消息流转

**使用示例**：
```python
# 组装组件
wechat_channel = WeChatChannel(config)
converter = MessageConverter()
notifier = NotificationManager()
command_handler = CommandHandler()

# 创建集成器
module = ModuleIntegrator(
    module_id="wechat_bot1",
    channel=wechat_channel,
    converter=converter,
    notifier=notifier,
    command_handler=command_handler,
    message_bus=message_bus
)

# 启动模块
await module.start()
```

## 优势总结

### 1. 职责清晰

- 平台渠道：只负责与平台交互
- 消息转换器：只负责格式转换
- 通知管理器：只负责通知
- 命令处理器：只负责命令
- 模块集成器：只负责集成

### 2. 易于扩展

- 新增渠道只需实现平台交互
- 复用通用组件
- 减少重复代码
- 加快开发速度

### 3. 易于维护

- 组件独立，易于理解和修改
- 组件可以独立测试
- 修改不影响其他组件
- 降低维护成本

### 4. 易于测试

- 组件可以独立测试
- 不需要模拟大量依赖
- 测试覆盖率提高
- 问题定位更快

### 5. 风险可控

- 分阶段实施
- 不破坏现有架构
- 保持接口兼容
- 逐步优化

## 总结

### 核心思路

通过组件化拆分，提取可复用的通用组件，使渠道职责清晰，易于扩展和测试。

### 关键组件

1. **MessageConverter**：消息格式转换
2. **NotificationManager**：通知管理
3. **CommandHandler**：命令处理（已有）
4. **Platform Channel**：平台交互
5. **Module Integrator**：组件集成

### 实施效果

- 职责清晰，易于理解
- 组件复用，易于扩展
- 测试友好，易于维护
- 风险可控，易于实施
